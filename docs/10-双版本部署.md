# 10 · 双版本部署（线上 lite / 本地 full）

> 这份文档回答一个问题：**为什么线上和本地不是同一套容器，以及怎么保证它们不变成两份代码。**
>
> 结论：**一套源码，两套部署。** 主仓库 `repair-platform` 是唯一源码；线上用
> `repair-platform-lite-deploy`（只放部署文件，不复制 Java 源码）从 Release 拉 jar。

---

## 1. 为什么拆两个版本

线上是 4C4G（可见内存约 3.7G）。完整栈的 compose 内存上限加起来 6G+：

| 组件 | 上限 |
|---|---|
| MySQL | 768M |
| app | 768M |
| Redis | 384M |
| MinIO | 256M |
| RocketMQ namesrv + broker | 384M + 1G |
| notification | 512M |
| timeout | 384M |
| Gateway | 384M |
| Nacos | 512M |
| RocketMQ Dashboard | 512M |
| Prometheus + Grafana + node-exporter | 约 704M |

完整栈在 4C4G 上**不是调参问题，是放不下**。而线上演示也不需要 Nacos / Dashboard / 监控；
核心价值是工单闭环、MQ 事件通道、通知/超时独立消费，以及**统一的网关鉴权**。

所以：

- **线上 lite（阶段 3.2 起）**：**10 个容器**，保留业务功能、MQ 与独立消费者，并保留 Gateway 做统一鉴权；
  砍掉 Nacos / Dashboard / 监控。**identity / platform 的 Bean 在 app 进程里合并装配**（不额外起容器）。
- **本地 full**：lite + `identity` + `platform` + `ticket` + `migrator`（`--profile services`）+ Nacos + Dashboard + 监控；
  用于完整架构验证和面试演示。
- **简历写 full，面试主动说线上是 lite**：这不是造假，是 4C4G 上的部署取舍。

---

## 2. 线上 lite（4C4G，阶段 3 起 10 个容器）

> 阶段 3.2/3.4 起 **identity / platform / ticket 都不单独占容器**：它们的 Bean 合并在 app 进程里，
> `GATEWAY_IDENTITY_URI` / `GATEWAY_PLATFORM_URI` / `GATEWAY_TICKET_URI` 都指向 `http://app:8080`。
> 这是 4C4G 的硬约束——再多三个 JVM 会直接超出 3.4G 预算（ADR-032 / ADR-035）。
> 上线前先按 3.4G 预算实测，超了再按 §2.2 的降级方案切回 nginx 直连。

| 容器 | 作用 | 建议上限 |
|---|---|---|
| nginx | 静态资源 + API 反代 | 64M |
| **gateway** | **统一登录校验 + 路由 + 身份头** | **256M** |
| app | 单体应用（ticket + ai + 统计 + **identity / platform 合并** + DB 兜底扫描） | 512M |
| mysql | 平台库 + 租户库 | 512M |
| redis | 会话 / 限流 / 缓存 / 工单号 | 256M |
| minio | 图片对象存储 | 256M |
| rocketmq-namesrv | MQ 注册中心 | 256M |
| rocketmq-broker | MQ Broker | 768M |
| notification | 通知消费者 | 256M |
| timeout | 超时消费者 | 256M |

合计上限约 **3.4G**，实际预计 **2.8–3.2G**。4C4G 可跑，但余量不大；必须加 swap，
并用 `docker stats` 实测。**`nginx → gateway → app`，app/notification/timeout 不 publish 端口。**

> 线上实测：timeout-service 常驻约 191M，192M 上限会被顶满；因此默认上限按 256M 配。
> RocketMQ 的 `data/rocketmq` 与 `logs/rocketmq` 在 Linux 上必须归 uid 3000（容器内
> `rocketmq` 用户）所有，否则 broker 会以 `NullPointerException` 反复重启：
> `sudo chown -R 3000:3000 data/rocketmq logs/rocketmq`。

### 2.1 关键配置

```text
SPRING_PROFILES_ACTIVE=prod,lite
GATEWAY_APP_URI=http://app:8080
# 阶段 3.2/3.4：lite 下身份域 / 平台运营域 / 工单域都在 app 进程里，三个 URI 都指 app
GATEWAY_IDENTITY_URI=http://app:8080
GATEWAY_PLATFORM_URI=http://app:8080
GATEWAY_TICKET_URI=http://app:8080
GATEWAY_PORT=8080
# 服务内验签（可选）：配了就与 GATEWAY_HMAC_SECRET 成对出现，只配一边会全站 10002 或静默不校验
# GATEWAY_HMAC_SECRET=<随机串>
# GATEWAY_HEADER_MODE=verify
REPAIR_ROCKETMQ_ENABLED=true
REPAIR_NOTIFICATION_DELIVERY=mq
REPAIR_TIMEOUT_DELIVERY=mq

# app：不消费，只做 DB 兜底
ROCKETMQ_CONSUMER_ENABLED=false
REPAIR_TIMEOUT_CONSUMER_ENABLED=false
REPAIR_TIMEOUT_BACKSTOP_ENABLED=true
REPAIR_TIMEOUT_SCHEDULER_ENABLED=true

# notification / timeout：各自消费
# notification: ROCKETMQ_CONSUMER_ENABLED=true, group=repair-notification-service
# timeout:      REPAIR_TIMEOUT_CONSUMER_ENABLED=true, REPAIR_TIMEOUT_BACKSTOP_ENABLED=false
```

**不要设置 `REPAIR_TIMEOUT_SCHEDULER_ENABLED=false`。** 在 ZSet 退役前，`TimeoutScheduler`
里同时有 ZSet 秒级消费和每分钟 DB 兜底扫描；关掉它会把兜底一起关掉。`delivery=mq` 时 ZSet
消费会自己 `return`，兜底仍需要它。阶段 3 结束后 ZSet 删除，兜底改由
`repair.timeout.scan.trigger=xxl-job|scheduled` 控制，届时同步改本节。

### 2.2 线上启停取舍

- Nacos：只做服务发现，lite 只有一个 app 实例，不需要。
- RocketMQ Dashboard：演示/排障用，线上不必需；要看消息就在本地 full 看。
- Prometheus / Grafana / node-exporter：当前线上监控三件套要停掉，给 MQ 和两个消费者腾内存。

**Gateway 保留**：`nginx → gateway → app`，gateway 只做登录校验、路由与身份头覆盖；
功能权限码与数据权限仍在 app 内。app/notification/timeout 不 publish 端口，只在内网。
如果 `docker stats` 实测超出 4C4G 预算，降级为 nginx 直连 app，由 app 自己校验 Sa-Token；
**不要同一部署混用两种鉴权路径**，降级后要在本文档记录原因与日期。

## 3. 本地 full

在 lite 基础上增加 Nacos / Dashboard / 监控，并把 gateway 从 lite 的 256M 调到 384M：

| 组件 | 上限 |
|---|---|
| Gateway（lite 256M → full 384M） | 384M |
| Nacos | 512M |
| RocketMQ Dashboard | 512M |
| Prometheus | 384M |
| Grafana | 256M |
| node-exporter | 64M |
| cAdvisor（可选） | 128M |

合计上限约 **5.3G+**，建议 8G 以上或开发机本地跑。

### 3.1 启动

```bash
cp .env.full.example .env.full
./scripts/dev-full.sh
```

`dev-full.sh` 会 `up -d --build`，确保 notification / timeout / gateway 用当前源码重建（旧镜像可能缺 MySQL 驱动等运行期依赖）。

`.env.full` 里的 `MAVEN_MIRROR` 不要删：国内 Docker 构建若走 Maven Central，`dependency:go-offline` 会卡在 TLS 中断。

本地没有正式证书时，nginx 会因为找不到 `nginx/certs/bluemalic.cn_bundle.crt` 反复重启。用自签证书即可：

```bash
MSYS_NO_PATHCONV=1 openssl req -x509 -nodes -newkey rsa:2048 -days 365 \
  -keyout nginx/certs/bluemalic.cn.key \
  -out nginx/certs/bluemalic.cn_bundle.crt \
  -subj "/CN=bluemalic.cn" \
  -addext "subjectAltName=DNS:bluemalic.cn,DNS:localhost,IP:127.0.0.1"
```

> 本地 full 的 gateway 同时接 `backend` 与 `frontend` 两个网络。app 也是双网卡，Nacos 注册的是 `frontend` 网段 IP；gateway 只接 `backend` 时 `lb://repair-app` 会连接超时（表现为 500）。这个覆盖在 `docker-compose.full.yml` 里。

等价的 compose 命令：

```bash
docker compose -f docker-compose.yml -f docker-compose.full.yml \
  --profile rocketmq --profile notification --profile timeout \
  --profile nacos --profile observability up -d
```

`docker-compose.full.yml` 用 `environment` 注入关键开关，不依赖 `.env` 是否写对；
`.env.full` 只放内存上限等覆盖项，由 `scripts/dev-full.sh` export 给 compose。

## 4. 超时：当前 MQ，ZSet 是回退

- 当前路径：`repair.timeout.delivery=mq`。登记点直接发 RocketMQ 5.x 定时消息
  （`setDeliverTimeMs`），timeout-service 消费到期消息执行三个动作。
- `cancel` 是**逻辑取消**：定时消息无法撤回，执行前用状态 CAS + `ticket_log` 判重。
- **真正的兜底是 DB 扫描**：单体里的 `TimeoutScheduler.backstop()` 每分钟逐库扫一次，
  和 ZSet/MQ 都无关。MQ 丢消息、消费者挂掉，它仍能把超时工单捞出来。
- ZSet 不删除，保留 `zset` delivery 作为故障回退；配置切回即可，不用回滚代码。

简历/面试口径：

> 超时调度最初用 Redis ZSet 做延迟队列（ZREM 多实例去重 + DB 兜底扫描），
> 后演进为 RocketMQ 5.x 定时消息，由独立 timeout-service 消费；
> 保留 ZSet 回退通道与 DB 兜底扫描。

不要说“删除 ZSet / 不再用 Redis”——Redis 还承载会话、限流、缓存、工单号。

## 5. 发布与部署仓库

### 5.1 主仓库：打 tag 出 Release

`release.yml` 在 `v*` tag 或手动触发时构建：

- `repair-app.jar`
- `repair-notification-service-exec.jar`
- `repair-timeout-service-exec.jar`
- `frontend-dist.tar.gz`（`web-admin/dist` + `miniapp-h5/dist/build/h5`）
- `source.tar.gz`（回退用）
- `sha256sums.txt`

### 5.2 部署仓库：只放部署文件

`repair-platform-lite-deploy` 不包含 Java 源码，结构：

```text
Dockerfile.runtime
docker-compose.yml
.env.example
nginx/nginx.conf
scripts/fetch-release.sh
scripts/deploy.sh
scripts/backup.sh
README.md
```

`scripts/deploy.sh <tag>`：

1. 下载 Release 资产（`fetch-release.sh`，支持 `RELEASE_BASE_URL` 镜像）
2. `sha256sum -c` 校验
3. 构建 `repair-app:<tag>` / `repair-notification-service:<tag>` / `repair-timeout-service:<tag>`
4. 保留 `previous` 镜像
5. `docker compose up -d`
6. 健康检查：app `/actuator/health`；notification/timeout 容器状态 + 消费者启动日志
7. 失败自动回滚到 `previous`

服务器上不再需要 Maven、源码树；只保留 `.env`、`data/`、`logs/`、`nginx/certs/`、前端 dist。

## 6. 内存不足时的回退顺序

4C4G 余量小，OOM 时按这个顺序退：

1. 降 broker heap/limit（512M → 384M）
2. 停 timeout-service，切回 `REPAIR_TIMEOUT_DELIVERY=zset`
3. 停 notification-service，切回 `REPAIR_NOTIFICATION_DELIVERY=sync`
4. 最后停 MQ，回到 5 容器 lite

每一步都只改配置/停容器，不需要回滚代码。

## 7. 边界（写给自己，也写给面试）

- 线上 lite 是**演示部署**，不是商业生产；没有真实用户。
- 本地 full 是**完整架构验证**，不等于线上全量运行。
- 2C2G 跑不了“lite + MQ + 独立服务”；2C2G 只能回到 5 容器 lite（无 MQ/独立服务）。
- 两套部署配置可能漂移：lite 仓库只放部署文件，以 Release tag 为契约，不复制 Java 源码。
