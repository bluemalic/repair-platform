# 03 · 接口规范文档

> 这份文档定义**所有接口共同遵守的约定**（URL、返回体、错误码、鉴权、分页、幂等），以及完整的接口清单。
> 单个接口的字段级明细由 **Knife4j 注解自动生成**（`/doc.html`），不在本文件重复维护——避免出现"文档和代码两套真相"。

---

## 1. URL 约定

```
/api/{端}/{模块}/{资源}[/{id}][/{动作}]
```

| 端前缀 | 对应前端 | 鉴权角色 |
|---|---|---|
| `/api/auth/**` | 各端共用 | 匿名（登录）/ 已登录（登出、当前用户） |
| `/api/student/**` | 学生端 H5（预留小程序） | 学生 |
| `/api/worker/**` | 维修工端 H5（**同一个 uni-app 工程**，按角色路由） | 维修工 |
| `/api/admin/**` | 后勤管理端 | 后勤管理 |
| `/api/ai/**` | 后勤管理端（数据问数） | 后勤管理 |
| `/api/tickets/**` | 各端共用 | 已登录（跨端抽象，见 §7.1） |
| `/api/files/**`、`/api/notifications/**` | 各端共用 | 已登录 |

**约定**：

- 资源用**复数名词**（`tickets` / `buildings` / `notifications`），不要用 `list`、`getById` 这类动词后缀
- 查询用 `GET` + query 参数；创建用 `POST`；全量更新用 `PUT`；部分更新用 `PATCH`；删除用 `DELETE`
- **状态跃迁类动作统一用 `POST` + 子路径**（`/dispatch`、`/accept`、`/cancel`、`/evaluate`…），因为它们不是幂等的资源替换，且都属于工单状态机的一次流转
- 路径中的 `{id}` 为雪花 ID；**所有 `Long` 类型在 JSON 中序列化为字符串**（雪花 ID 超出 JS `Number.MAX_SAFE_INTEGER`，不转字符串前端会精度丢失）

## 2. 统一返回体

```java
@Data
public class Result<T> {
    private Integer code;      // 业务状态码，0 = 成功
    private String  message;   // 提示信息
    private T       data;      // 业务数据
    private String  traceId;   // 链路追踪ID，排查问题用
}
```

```json
{
  "code": 0,
  "message": "success",
  "data": { "id": "1857392012345678", "status": 20 },
  "traceId": "a1b2c3d4e5f6"
}
```

**为什么带 traceId**：用户报错时截图给你，你凭 traceId 直接在日志里定位整条链路。面试时这句话很加分。

### 2.1 分页返回体

请求参数统一为 `pageNum`（默认 1）、`pageSize`（默认 10，上限 100）。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "total": 137,
    "pageNum": 1,
    "pageSize": 10,
    "pages": 14,
    "list": [ ]
  },
  "traceId": "a1b2c3d4e5f6"
}
```

### 2.2 JSON 序列化约定

| 项 | 约定 | 原因 |
|---|---|---|
| `Long` / `long` | 序列化为**字符串** | 雪花 ID 约 1.9×10¹⁸，超出 JS 安全整数范围 `2^53-1`，不转会精度丢失 |
| 时间 | `yyyy-MM-dd HH:mm:ss`（`Asia/Shanghai`） | 前后端统一，避免时区歧义 |
| `null` 字段 | 保留（默认序列化） | 前端字段判断更简单；分页 `list` 恒为数组不为 `null` |
| 金额 | `decimal`，序列化为数字 | 本项目暂无金额字段，约定先写下 |

### 2.3 HTTP 状态码约定

| 场景 | HTTP 状态 | body.code |
|---|---|---|
| 业务成功 | `200` | `0` |
| 业务失败（参数、状态、业务规则） | `200` | 非 0 业务码 |
| 未登录 / Token 失效 | `401` | `10002` |
| 已登录但无功能权限 | `403` | `10003` |
| 系统异常 | `500` | `10005` |

**为什么业务失败返回 200**：前端拦截器只需读 `body.code` 就能统一处理所有业务提示；`401` / `403` 单独用 HTTP 语义，是为了让前端**一个拦截器就能识别"该跳登录页"**，也便于 Nginx 和监控按状态码统计。两套语义各管一段，不混用。

## 3. 错误码表

**按模块分段，集中管理，禁止散落魔法值。** 本表是错误码的唯一来源，代码中只能引用这里的枚举。

| 区间 | 模块 |
|---|---|
| `0` | 成功 |
| `1xxxx` | 通用（参数、鉴权、系统） |
| `2xxxx` | 工单 |
| `3xxxx` | 权限与用户 |
| `4xxxx` | AI 与 SQL 安全 |
| `5xxxx` | 文件与存储 |

| 码 | 含义 | 触发场景 |
|---|---|---|
| `10001` | 参数校验失败 | `@Valid` 校验不通过 |
| `10002` | 未登录或登录已过期 | Token 缺失 / 失效 |
| `10003` | 无权限访问该资源 | **RBAC 权限不足**（没有这个功能权限） |
| `10004` | 请求过于频繁 | 限流 |
| `10005` | 系统繁忙，请稍后重试 | 兜底异常 |
| `20001` | 工单不存在 | —— |
| `20002` | 工单状态不允许该操作 | **非法状态跃迁**——这个码很关键 |
| `20003` | 该工单已被其他人接单 | 并发抢单 |
| `20004` | 无权操作他人工单 | **数据权限拦截**（有功能权限，但数据不在可见范围） |
| `20005` | 工单已评价，不可重复评价 | 幂等 |
| `20006` | 报修码无效或已失效 | 扫码 / 手动输入错误 |
| `20007` | 报修码与工单位置不一致 | 维修工扫到别的房间的码 |
| `30001` | 用户名或密码错误 | —— |
| `30002` | 账号已被禁用 | —— |
| `30003` | 租户不存在或已停用 | 登录时 `tenantCode` 无效 |
| `40001` | 自然语言无法解析为查询意图 | —— |
| `40002` | 生成的 SQL 未通过安全校验 | **安全网关拦截** |
| `40003` | 查询超时，请缩小查询范围 | 熔断 |
| `40004` | 模型服务暂时不可用 | 模型降级 |
| `50001` | 文件类型不支持 | —— |
| `50002` | 文件大小超限 | —— |
| `50003` | 文件上传失败 | MinIO 不可用 / 上传中断 |

> **`10003` 与 `20004` 的区别，面试常问**：`10003` 是**功能权限**——这个角色压根没有这个接口的权限，在 Controller 之前就被 Sa-Token 注解拦掉；`20004` 是**数据权限**——角色有这个功能，但这条数据不在他的可见范围内，由 MyBatis 拦截器在 SQL 层拦掉（受影响行数为 0 或查不到）。前者是"不能做这个动作"，后者是"不能碰这条数据"。

> 💡 面试官如果问"你怎么处理并发抢单"，答"`20003` 这个错误码 + 条件更新（`where status = 20`）兜底"——具体、可信。

## 4. 鉴权约定

- 登录成功后返回 Token，前端放 `Authorization: Bearer <token>` 请求头
- **登录方式：账号密码**（学号 / 工号），**不接微信授权登录**——`wx.login` 只有小程序有，H5 没有，用了就没法跨端
- 登录参数含 `tenantCode`（租户编码），服务端据此定位租户并校验租户状态
- 服务端用 **Sa-Token** 校验，权限注解：`@SaCheckPermission("ticket:dispatch")`
- **端前缀与角色绑定**：`/api/student/**` 只允许学生角色访问，`/api/worker/**` 只允许维修工，`/api/admin/**` 与 `/api/ai/**` 只允许后勤管理，由拦截器统一校验
- **防御双层**：Sa-Token 管功能权限（能否调这个接口），MyBatis 拦截器管数据权限（能看哪些数据）。两层都在框架层，新增接口默认继承

**`POST /api/ai/query` 响应体示例**

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "question": "上月3号楼报修最多的是什么",
    "sql": "SELECT c.name, COUNT(*) AS cnt FROM ticket t JOIN ticket_category c ON ...",
    "columns": ["类别", "报修量"],
    "rows": [["水电", 42], ["门锁", 17]],
```

- **SSE 注意事项**：浏览器原生 `EventSource` 无法设置 `Authorization` 头，因此前端用 `fetch` 流式读取并带上请求头，不使用 `EventSource`（避免把 token 拼进 URL——URL 会进访问日志）

## 6. 幂等与并发

**幂等不靠"查一下再改"，靠"条件更新 + 唯一索引兜底"。**

| 操作 | 幂等手段 |
|---|---|
| 派单 | `update ticket set status=20, worker_id=? where id=? and status=10`，受影响行数 = 0 则返回 `20002` |
| 接单 | 同上，`where status=20 and worker_id=当前用户`；被别人抢先则返回 `20003` |
| 到场 / 完工 | 条件更新 + 时间字段"仅当为空时写入"，重复请求不覆盖首次时间戳 |
| 验收评价 | `ticket_evaluation` 的 `uk_ticket` 唯一索引兜底，重复评价返回 `20005` |
| 撤销 / 驳回 / 关闭 | 条件更新，非法状态返回 `20002` |

> 为什么不用 `synchronized` 或分布式锁：单条记录的并发冲突用**数据库的条件更新**解决是最可靠的——它不依赖应用层单实例假设，也没有锁的获取和释放成本。锁只在"跨多条记录的复合判断"时才需要，本项目没有这种场景。

## 7. 关键流程约定

### 7.1 报修码（跨端抽象）

**报修码是位置码，不是工单码**：贴在房间门口，标识「楼栋 + 房间」。这是它必须跨端共用的原因——学生扫码报修和维修工扫码到场，扫的是**同一张码**，走的也是**同一个后端接口**。

| 端 | 流程 |
|---|---|
| 学生（报修） | `GET /api/tickets/by-code/{code}` → 拿到楼栋与房间，前端预填 → `POST /api/student/tickets` |
| 维修工（到场） | `GET /api/tickets/by-code/{code}` → 与当前工单的楼栋房间比对 → `POST /api/worker/tickets/{id}/arrive`（请求体带 `code`，服务端再校验一次，不一致返回 `20007`） |

- 服务端**必须再校验一次**：只靠前端比对等于没有校验
- 码为服务端生成的不透明字符串（建议 6 位数字，便于口述和手输），前端只透传、不解析
- 存储见 `02-数据库设计.md` 的 `repair_code` 表：码在租户内唯一，**「一房一码」由应用层保证**
- 生产环境的码**随机生成**，不要用顺序码——顺序码能被枚举出全部房间，等于泄露房间清单
- 报修码不存在或已停用，统一返回 `20006`

**二维码怎么来**：二维码的内容就是 `code` 字符串本身，前端用 qrcode 库渲染成图即可；管理端批量生成与打印是前端页面（P1），后端不需要额外的二维码接口。**往宿舍门口贴码是学校上线时的一次性运维动作，不是应用的运行依赖。**

### 7.2 工单状态流转

每次流转都必须：

1. 校验当前状态是否在合法跃迁表内（见 `02-数据库设计.md` §5），非法返回 `20002`
2. 用**条件更新**落库
3. 写一条 `ticket_log`（`from_status` / `to_status` / `action` / `operator_id`）
4. 给相关方插一条 `notification`（异步，失败不阻塞主流程）
5. 打关键日志（提交 / 派单 / 接单 / 核销 / AI 查询）

### 7.3 文件上传

```
POST /api/files/upload    Content-Type: multipart/form-data
```

| 约束 | 值 |
|---|---|
| 允许类型 | `jpg` / `jpeg` / `png` / `webp` |
| 大小上限 | 5 MB |
| 返回 | `{ "url": "...", "objectKey": "..." }` |
| 存储 | MinIO，按 `租户/日期/uuid.ext` 分目录 |
| 错误 | 类型不符 `50001`、超限 `50002`、上传失败 `50003` |

工单表用 `json` 字段存 URL 数组（见 02 文档的设计理由：图片只做展示、不参与查询）。

## 8. 完整示例（一个接口写全，其余照抄结构）

### 派单

```
POST /api/admin/tickets/{id}/dispatch
```

**请求头**

```
Authorization: Bearer <token>
Content-Type: application/json
```

**请求体**

```json
{
  "workerId": "1857392099999999",
  "remark": "电工班张师傅，优先处理"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| workerId | String | 是 | 维修工ID（雪花 ID，字符串传输） |
| remark | String | 否 | 派单备注，最长 255 字 |

**成功响应**

```json
{
  "code": 0,
  "message": "success",
  "data": { "ticketId": "1857392012345678", "status": 20, "dispatchTime": "2026-09-10 14:23:01" },
  "traceId": "a1b2c3d4e5f6"
}
```

**失败响应**

```json
{ "code": 20002, "message": "工单当前状态不允许派单", "data": null, "traceId": "a1b2c3d4e5f6" }
```

**幂等说明**：重复派单不会重复写流转日志——依赖「状态前置校验 + 条件更新」：第二次请求时 `status` 已不是 10，更新影响行数为 0，直接返回 `20002`。
