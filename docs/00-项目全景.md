## 1. 一句话定位

高校后勤报修 SaaS 平台：**学生扫码报修 → 后勤派单 → 师傅接单上门 → 学生验收 → 数据自动汇总**，
三个角色（学生 / 维修工 / 后勤管理）各有独立的数据可见范围，并计划支持用自然语言直接问数（M4）。

- 学生端与维修工端：同一个 uni-app 工程（先编译 H5，备案后可编小程序），按角色路由
- 后勤管理端：独立的 Vue 3 PC 后台
- 后端：单体 Spring Boot 3 + MySQL + Redis + MinIO，一套 API 同时服务三个端

### 2.2 已实现（逐项）

**认证与权限**
- Sa-Token 账号密码登录（学号 / 工号 + 租户码）、登出、当前用户
- RBAC：20 个权限点、3 个角色；`@SaCheckPermission` 注解校验（`StpInterfaceImpl` 提供权限码）
- **数据权限拦截器**（ADR-002 + ADR-008）：先按租户隔离、再按角色隔离——学生只见自己的单、维修工只见负责楼栋、后勤限本租户；
  条件由 MyBatis 拦截器注入，任何 Mapper 不手写范围条件；支持带别名 JOIN（统计的联表查询已验证）

**工单域**
- 8 状态机（10 待派单 → 20 → 30 → 40 → 50 → 60；70 撤单 / 80 驳回可重新派单），非法跃迁统一拒绝
- 三端接口：提交（报修码定位）· 撤销 · 评价 / 接单 · 驳回 · 扫码到场 · 完工 / 派单 · 驳回 · 关闭
- 每次流转写 `ticket_log`（from/to/action/operator），全程可追溯；条件更新保证并发幂等
- 报修码：`repair_code` 表 + 跨端共用接口 `GET /api/tickets/by-code/{code}`（学生扫码报修与维修工扫码到场同一个）

**站内通知**
- 通知表 + 未读数 / 标记已读 / 全部已读；发送失败不影响主流程（旁路）
- 状态变更通知由**动作 → 通知规格表**统一驱动（一处定义类型 / 标题 / 接收方）
- `sendToTenantAdmins`：按角色码 ADMIN 解析接收人，用于"提醒调度方"

**超时调度**（ADR-001 / ADR-006）
- 三个节点：24h 未接单提醒 · 48h 未处理升级 · 验收超时自动关闭（唯一会改状态的超时动作）
- **基准时间统一**：未接单与未处理都按 `dispatch_time` 起算（需求口径"从派到完工"），验收超时按评价时刻起算；
  毫秒级的 ZSet 路径与分钟级的兜底扫描**必须是同一个基准**，否则两条路径会给出不同的到期时刻
- Redis ZSet 延迟队列按节点分 key，秒级消费 + 每分钟兜底扫库；`ZREM` 返回值做多实例去重
- 兜底扫描三条硬约束：**带状态过滤**（处理过的行离开结果集，N 不随时间增长）· **只取主键** · **单轮 LIMIT 200**
- 幂等靠 `ticket_log` 判重；阈值可配（`REPAIR_TIMEOUT_*_MINUTES`），通知文案按实际阈值生成

**统计看板**
- 四个接口：总览（总量 / 平均响应 / 平均处理 / 超时率 / 满意度）· 趋势（天/周，补零）· 分布（类别/楼栋/紧急度）· 师傅工作量与按时率
- 口径写在 `docs/03`；超时口径以 `ticket_log` 的超时动作为准，不重算阈值

**安全护栏**
- 报修码防枚举（ADR-009）：接收报修码的两个接口（按码查询 / 扫码到场）按登录用户限流，
  固定窗口 60 次/分钟，超限 `10004`；计数用 Redis + Lua 保证 TTL 一定被设置
- Redis 不可用时**放行**而不是拦死（docs/01 §5 降级策略）：限流防的是滥用，不是业务正确性

**管理端基础数据（`/api/admin`）**
- **维修工管理**：列表（分页 + 状态 / 工号姓名筛选，带负责楼栋名）· 新增（工号即登录名，
  用户类型服务端写死为维修工）· 修改启停（**停用同时踢下线**，因为登录态在 Redis，不受 status 影响）·
  设置负责楼栋（**全量替换**，校验先于删除，跨租户楼栋被拒且不动原有授权）
- **楼栋 / 类别**：列表（**不分页**，含已停用，按 sort 升序）· 新增（一律启用）· 修改（PUT 提交最终状态）·
  删除（逻辑删除，**只允许删从未被引用的**：有工单 / 有师傅负责 / 有报修码就返回 `10001`）。
  "下线一项"的正式方式是**停用**——被引用的字典项一旦软删，全局逻辑删除会让引用处静默显示空名称
- **报修码**：尚未实现（契约已在 docs/03 定好）

**管理端前端（web-admin，脚手架）**
- Vue 3 + Vite + TS + Element Plus + ECharts；登录（校验角色）、工单列表（派单/驳回/关闭/筛选/分页）、统计看板（4 图）
- `api/http.ts` 统一处理后端契约：`Result.code` 解包、`Long → 字符串`、401 清 token 跳登录

**工程侧**
- 14 张表（`docs/schema.sql`）+ 演示账号脚本 `docs/dev-seed.sql`（不进生产库）
- 配置全部 `${ENV:默认值}`，密码只从环境变量读；本地 / CI / 容器同一套读取逻辑
- Dockerfile + docker-compose + nginx（已预留 `/` 与 `/h5/` 前端静态目录）+ 部署文档 `docs/05`
- 测试 70 个：状态机流转、并发幂等、数据权限、超时调度、统计口径、鉴权链路、限流边界、接口错误契约、维修工管理、字典管理

### 3.2 一条工单的端到端生命周期

| # | 谁 | 动作 | 状态 | 同时发生什么 |
|---|---|---|---|---|
| 1 | 学生 | 扫码 → 提交报修 | 10 待派单 | 写 `ticket_log(SUBMIT)`；生成工单号（Redis INCR + 唯一索引兜底） |
| 2 | 后勤 | 派单给师傅 | 20 待接单 | 通知师傅；**登记 24h 未接单提醒** |
| 3 | 维修工 | 接单 | 30 处理中 | 通知学生；撤销接单提醒；**登记 48h 未处理升级** |
| 4 | 维修工 | 扫码到场打卡 | 30（不变） | 校验报修码与工单房间一致；记录 `arrive_time` / 响应时长；通知学生 |

### 3.3 鉴权、限流与数据权限（每个请求都走）

```
请求(Authorization: Bearer <token>)
   │
   ├─ TraceIdFilter       注入 traceId 到 MDC + 响应头（贯穿全链路日志）
   │
   ├─ SaInterceptor       ① 登录态校验：无 token → 401 + 10002
   │                      ② 注解校验：@SaCheckPermission("ticket:dispatch")
   │                           └─ 回调 StpInterfaceImpl：
   │                              sys_user_role → sys_role_permission → sys_permission
   │                              角色/权限码都取启用中的；失败 → 403 + 10003
   │
   ├─ RateLimitInterceptor 只对 @RateLimit 标注的接口计数（当前=接收报修码的两个接口）
   │                        Redis 固定窗口：60 次/分钟/用户，超限 → HTTP 200 + 10004
   │                        计数键 = 用户 + 接口方法（不含路径，否则每次猜码都是新桶）
   │                        Redis 不可用 → 放行（ADR-009 / docs/01 §5 降级策略）
   │
   ├─ Controller → Service（业务规则 + 状态机 + 条件更新）
   │
   └─ MyBatis 拦截器链
        ├─ DataPermissionInterceptor（ADR-002 + ADR-008，两层）
        │     TicketDataScopeHandler 先注入租户、再按角色追加：
        │       第一层 租户 → t.tenant_id = 我的租户（后勤也不例外）
        │       第二层 角色 → 后勤：不限制｜维修工：t.building_id IN (我负责的)｜学生：t.student_id = 我
        │       通知表 → receiver_id = 我（所有人一视同仁）
        │     无登录态（定时任务）→ 两层都不注入，这是兜底扫描能跨租户的前提
        └─ PaginationInnerInterceptor（必须在数据权限之后）
```

关键点：**数据范围不写在 SQL 里**（漏一处就是越权），而由拦截器统一注入；系统上下文（定时任务、无登录态）
不注入条件——这正是超时调度能跨租户处理的原因。

### 3.4 超时调度链路

```
业务流转处登记                      Redis ZSet                      调度器（1s）
派单 → registerAccept   ──▶  ticket:timeout:ACCEPT  ──┐
接单 → registerProcess  ──▶  ticket:timeout:PROCESS ──┼─▶ ZRANGEBYSCORE 0 now
评价 → registerEval     ──▶  ticket:timeout:EVAL    ──┘        │
关闭/完工/驳回 → cancel（删 member）                          ZREM（返回 1 才处理）
                                                              │
                                                     ┌────────┴────────┐
                                                     ▼                 ▼
                                          未接单/未处理：写 ticket_log  验收超时：
                                          （20→20 / 30→30）+ 通知      条件更新 50→60
                                                                      + 通知 + 写日志
兜底：每分钟扫库（"该到期却不在 ZSet 里"）→ 走同一套动作，幂等靠 ticket_log 判重
```

### 3.5 分层与包结构

## 5. 关键约定速查

- **状态码**：10 待派单 · 20 待接单 · 30 处理中 · 40 待验收 · 50 已完成 · 60 已关闭 · 70 已撤单 · 80 已驳回
- **错误码段**：1xxxx 通用 · 2xxxx 工单 · 3xxxx 权限/账号 · 4xxxx AI · 5xxxx 文件（详见 `docs/03`）
- **超时阈值**：`REPAIR_TIMEOUT_ACCEPT_MINUTES`(1440) · `PROCESS_MINUTES`(2880) · `EVAL_MINUTES`(1440)
- **通知类型**：`TICKET_DISPATCHED/ACCEPTED/ARRIVED/FINISHED/EVALUATED/REJECTED/AUTO_CLOSED/ACCEPT_TIMEOUT/PROCESS_TIMEOUT`
- **JSON 契约**：`Long` 一律序列化成字符串（雪花 ID 精度）；分页计数字段保持数字（前端分页组件要求）
- **提交规范**：Conventional Commits；前端 scope 固定 `admin` / `h5`（将来切分历史的分界线）
- **数据可见范围**：学生=本人 · 维修工=负责楼栋 · 后勤=本租户全部

```bash
mvn -B clean package                       # 后端：测试 + 打包
java -jar target/repair-platform-0.0.1-SNAPSHOT.jar   # 起后端（8080）

cd web-admin && npm install && npm run dev # 管理端（5173，/api 代理到 8080）
```

`http://localhost:8080/doc.html` 是接口文档；环境变量与部署细节见 `docs/05-部署文档.md`。
