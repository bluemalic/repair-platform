# 01 · 需求文档（精简 PRD）

> 高校后勤维修协同平台原型的需求说明。全文只回答三件事：**为什么做、给谁做、必做的是什么**。
> 本项目基于个人观察和自主设计，尚未开展正式访谈、接入真实学校或验证市场需求；数据与素材均为虚构或自行生成。

---

## 1. 背景与痛点

**拟验证的场景**：学校可能已有企业微信、OA 或其他报修入口，本项目探索维修工单在受理、调度、处理、验收和统计之间如何形成一致的业务闭环。已有入口并不等于已经具备完整维修流程；是否确实存在下面的问题，仍需访谈和实际流程验证。

待验证的业务假设：

1. **受理信息不完整**：已有报修入口中，位置、故障现象、图片和可上门时间可能仍需人工补充。本项目用位置码、结构化表单和受理 Agent 草稿减少重复录入。
2. **工单协同存在断点**：受理、派单和处理结果可能分散在不同页面或渠道。本项目统一状态流转、参与人、通知和操作记录，验证跨角色协同。
3. **统计口径不一致**：维修量、响应时间、返工和超时可能缺少统一口径。本项目提供可追溯的统计和导出；这些指标仅辅助判断，不直接作为人员绩效结论。

**多租户的定位**：多租户是本原型用于验证账号、配置、数据隔离和学校开通流程的工程设计，尚无多校采购或真实使用依据。当前以学校作为租户，楼栋等业务数据归属学校；不把同一学校的校区直接等同于独立租户。角色与权限码由平台维护（ADR-012）。

**与现有系统的关系**：目标是探索校园系统中的维修业务域，不声称取代企业微信或 OA。现有 CAS / OAuth2 与 Mock IdP 展示认证适配能力；尚未对接真实学校的身份系统或既有报修系统。

### 1.1 阶段 0：定位与能力边界（2026-11-20）

本节记录本轮确认的定位、已核对的实现和后续建议。下面的“建议 / 待决策”不改变当前接口、状态机、部署配置和数据库；后续实现前须明确业务规则并同步契约。原有 M1～M6 等编号为历史开发里程碑，不代表本轮改造阶段。

| 事项 | 当前事实与本轮定位 | 依据 |
|---|---|---|
| 项目真实性 | 个人观察、自主设计、AI 工具辅助开发的工程原型；尚无正式访谈或真实学校使用记录；演示数据与素材为虚构或自行生成 | 项目作者说明；落地页 `web-admin/src/views/LandingView.vue` 已声明个人技术演示、非学校官方系统 |

| 公网 AI 成本 | 作者反馈公开演示账号可能可调用 AI，DeepSeek 未设独立消费额度；实际线上访问范围未核验。代码已有按用户限流、会话与步数边界、单次模型超时和调用指标，未找到统一费用预算硬限制 | `@RateLimit`、`AiChatModelProvider`、`AgentSessionStore`；不将账户余额当预算控制 |

RAG 的判定不取决于是否使用向量数据库；关键词检索同样可以用于检索增强生成。当前按具体实现描述能力，不宣称已建设完整知识治理体系或验证维修建议的专业正确性。

## 2. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| 学生 | 宿舍水电坏了、门锁坏了 | 快速报修、知道进度、能评价 |
| 维修工 | 每天接单上门 | 清楚今天要干什么、在哪、什么毛病 |
| 后勤管理 | 调度全校维修资源 | 派单合理、进度可控、数据可查 |
| 平台运营 | 给新学校开号、停用不再使用的学校 | 开一所学校就能用，不用碰数据库 |
| 系统（AI 数据助手） | 后勤管理问数 | 用一句话拿到统计结论，不用学 SQL |

**端形态**：学生端与维修工端是**同一个 uni-app 工程**（先编译 H5，备案后可编译小程序），登录后按角色路由区分；后勤管理端是独立的 Vue 3 PC 后台，**平台运营页也在这个后台里**（同一个工程、同一个登录页，只是菜单不同）。

## 3. 用户故事

> 格式：**作为 <角色>，我希望 <做什么>，以便 <获得什么价值>**

### 学生端
- 作为学生，我希望扫码就能提交报修并上传照片，以便不用打电话描述
- 作为学生，我希望**扫宿舍门口的报修码就能自动带出楼栋和房间**，以便不用手填位置
- 作为学生，我希望随时看到工单进度，以便知道师傅什么时候来
- 作为学生，我希望能撤销不再需要的报修，并让相关维修人员得知；当前允许的状态见 §4.7，目标取消规则待 §1.2 收敛
- 作为学生，我希望完工后能评价，以便反馈服务质量

### 维修工端
- 作为维修工，我希望看到派给我的工单列表，以便安排上门顺序
- 作为维修工，我希望上传处理结果和现场照片，以便留档
- 作为维修工，我希望只看到我负责的楼栋，以便不被无关工单干扰
- 作为维修工，我希望**碰上不归我处理的单能驳回并写明原因**，以便后勤改派，而不是让我空等
- 作为维修工，我希望**后勤临时抽调给我的紧急单（不在我负责楼栋）也能看到、也能走维修流程**，以便应急时不用先改配置
- 作为维修工，我希望**使用工单位置对应的报修码登记到场**，以便记录声明到场的时间；该记录不作为防代打卡或真实到场证明

### 后勤管理端
- 作为后勤管理，我希望参考类别、楼栋和候选评分手动确认派单，以便调度均衡
- 作为后勤管理，我希望看到超时工单并升级提醒，以便压住响应时长
- 作为后勤管理，我希望看到统计看板，以便考核与决策
- 作为后勤管理，我希望能直接问"上月 3 号楼报修最多的是什么"，以便不学 SQL 也能拿数据

## 4. 功能清单

### 核心功能（沿用历史范围，当前优先级以 §1.2 为准）

| 模块 | 功能点 |
|---|---|
| 账号与权限 | 三种角色账号密码登录（学号 / 工号）+ **学校统一身份认证登录**（CAS / OAuth2，阶段 7）、RBAC 菜单与按钮权限、数据可见范围隔离 |
| 租户开通 | 平台运营开通学校（建租户 + 首个后勤管理员）、启停学校、给学校加管理员 / 重置其口令 |
| 工单全流程 | 提交（图片 / 位置 / 类别 / 紧急度）→ 派单 → 接单 → 处理中 → 上传结果 → 验收评价 → 关闭；非主线动作：**驳回**（20/30/40，师傅或后勤）· **撤销**（学生，10/20/30/35/45/80）· **验收不通过**（40 → 30，打回重做）· **转派**（20/30 → 20，换人）· **待料**（30 → 35）· **无法维修**（30 → 45）· **合并重复单**（活动状态 → 75）。规则见 §4.1 / §4.7 |
| 工单状态机 | 11 状态 + 合法跃迁校验，禁止跳状态；每次流转写 `ticket_log` 可追溯 |
| 报修码 | 房间或公共区域的位置码：学生扫码带出位置，维修工扫码或手输登记声明到场；只校验位置一致性，**两端共用同一个查询接口** |
| 文件与图片 | 现场图片、维修后图片上传（MinIO），类型与大小校验，返回可访问 URL |
| 超时提醒与升级 | 24h 未接单提醒、48h 未处理升级（基准为 `dispatch_time`）；当前只有学生验收评分进入 50 后才登记自动关闭，40 长期未验收尚无超时闭环（§1.2） |
| **站内通知** | 工单状态变更时向相关方推送站内消息；**接收人按动作定，见 §4.3** |
| 统计看板 | 报修量趋势、类别分布、楼栋分布、平均响应 / 处理时长、超时率、满意度、师傅工作量 |
| **报修受理 Agent** | **多轮对话补全 → 产出工单草稿**（类别 / 紧急度 / 位置 / 描述 / 建议标题），**Agent 不写业务库**：落单仍走 `POST /api/student/tickets`，用户逐项确认后才提交（ADR-017）。工具白名单只有两个只读工具：本租户楼栋、本租户类别 |
| **智能分诊 Agent** | 对已存在的工单给出**类别 / 紧急度建议与理由**，由后勤决定是否采纳（不由 Agent 修改工单）。**基础数据**（楼栋 / 类别）由 Agent 通过工具实时读本租户的启用中数据，不硬编码进提示词 |
| 操作审计日志 | **账号与基础数据的写操作留痕**：谁、什么时候、对谁、做了什么（规则见 §4.4）。工单流转不重复记——它有自己的 `ticket_log` |

### 已有辅助能力与可选实验

**AI 问数与 SQL 安全网关（可选实验，保留范围待讨论）**：自然语言 → 白名单 Schema 注入 → 生成 SQL → 安全网关 → 只读执行 → 数据与结论。已有只读账号、SQL 白名单、租户条件注入、查询超时和行数上限；SQL 查询超时不等于模型费用预算控制。接口与安全边界保留，后续是否继续投入见 §1.2。

**统计报表导出（Excel）** —— **已完成**。四张工作表对应统计看板的四块内容（概况 / 报修量趋势 / 分布统计 / 师傅工作量），
取数复用看板的四个 Service 方法，所以导出与页面**不可能出现两个数**；契约与"失败时不留半截文件"的规则见 `docs/03` §5.4.1。
**导的是报表不是工单明细**：明细属于工单模块（筛选条件、列、几万行的内存问题都是另一摊事），
用于验证月度维修统计的统一口径。

**协同处理**（**已完成**，见 §4.5：加协作者 + 拆单）、**登录事件入审计**（**已完成**，见 §4.4：登录成功去重记、失败全记）、**目标机压测**（本机口径已验，见 `docs/08` §6）。

**派单评分模型**（**已完成**，阶段 3 · ADR-019）：后勤打开派单弹窗时，本租户启用中的师傅按「技能（擅长该类别或属于类别对应的工种）/ 满意度（历史平均评分）/ 负载（进行中单数）/ 距离（负责该楼栋 > 同区 > 跨区）/ 值班（今天明确在班 > 没排班记录 > 明确请假）」五项加权排序，**每项得分与一句话理由都显示出来**。
边界：**只排序、不自动派单**（与"明确不做"一致）；**没维护技能或没有评价记中性分**，不让新师傅永久垫底；距离是**楼栋归属的代理**，不是真实里程（项目没有坐标，也不为此引地图）。

**维修知识库 + 师傅排查建议**（**已完成**，决策见 ADR-018；评测见 `docs/07` §6）：后勤在管理端维护本学校的「现象 → 处理步骤」条目；师傅在工单详情里可以要一份排查建议，建议**必须带引用来源**（引用只能来自本次检索命中的条目，服务端核对），检索零命中时就如实说"知识库里没有"。
边界：**只给建议、不改任何数据**；**学生看不到**（这是维修工的工具）；知识库是**每所学校自己的**（与工单同样的租户隔离）。本功能保留为历史实验；系统化 RAG 演进暂缓，演示条目和生成内容未经专业维修审核，引用核对只能证明来源 ID 在检索结果中。

### 明确不做

失物招领、活动报名、**微信授权登录、全自动派单**（只做候选排序 + 人工确认：什么时候派给谁，是调度员的判断，系统只保证“派得到、被派的人看得到”）。

> **通知现状**：站内通知为默认通道；短信、邮件、企业微信、微信订阅消息等站外通道尚未实际接入业务投递，不能替代离线提醒。后续优先评估邮件适配器，选型和时限见 §1.2；不再因“技术含量”排除通知渠道。
> **登录同理**，用**账号密码**（学号 / 工号）而不是微信授权登录，保证 H5 与小程序两端一致。

> **为什么要写"不做"**：把"不做"明确写出来，是在说明取舍标准——宁可把一条主线做深，也不铺五条平铺的 CRUD。以后想加功能时，先对照这一节判断它是否属于这条主线。

### 4.1 四类非主线动作：驳回 / 撤销 / 验收不通过 / 转派

主线是"提交 → 派单 → 接单 → 处理 → 验收 → 关闭"，但现实中一定会出现"这单不该我做""我报错了""修得不行""这个人现在没空"。这四类动作必须写清规则，否则验收时最容易吵——它们各自牵动三方的可见范围、通知与超时计时。

> 四者最容易被混掉，一句话分清：**驳回＝这单不该我做**（退回调度池）· **转派＝换个人做**（单还在流转，只是换了人）· **打回＝还是你做但没做好**（师傅不变）· **撤销＝学生自己不修了**。

**驳回（`80 已驳回`）**

| 项 | 规则 |
|---|---|
| 谁能驳 | 维修工：只能驳**派给自己的**单（20 待接单 / 30 处理中）；后勤：可以驳 20 / 30 / 40 任意阶段 |
| 驳回必须写原因 | 原因进 `ticket_log`，并随通知一起发给相关方 |
| 驳回后 | `worker_id` **清空**（这单不再属于任何师傅）、该单的超时节点取消 |
| 驳回之后 | 后勤可以重新派单（`80 → 20`），**不限制派给谁**——包括刚驳回它的那位师傅。因为"留下驳回过这件事的痕迹"比"拉黑某个人"更有用：谁在第几节点驳回过、什么原因，`ticket_log` 里查得到，由调度员判断 |
| 为什么不直接回到待派单（10） | 回到 80 多留一条"被驳回过"的痕迹，且全程可追溯（`docs/02` §5） |

**撤销（`70 已撤单`）**

| 项 | 规则 |
|---|---|
| 谁能撤 | 只能是提交这单的学生本人 |
| 当前什么时候能撤 | 当前实现允许从 `10 / 20 / 30 / 35 / 45 / 80` 撤销到 70（见 §4.7）；旧文案“仅待派单可撤”已过期 |
| 当前关联动作 | 取消超时登记；已派单时通知相关维修工，不通知撤单学生本人 |
| 待决定 | 是否限制派单后直接撤销、改为取消申请或人工处理，见 §1.2；驳回不等于取消申请审批，当前没有该审批流程 |

**验收不通过（`40 → 30`，打回重做）**

学生验收时看到的是**实物结果**：修好了就是修好了，没修好也不该被逼着"打低分接受"。

| 项 | 规则 |
|---|---|
| 谁能做 | 只能是提交这单的学生本人 |
| 什么时候能 | 工单处于 40 待验收（验收通过走 `/evaluate`，不通过走 `/rework`，两条路都在这个状态上分叉） |
| 必须写理由 | 理由进 `ticket_log`（工单时间线上可见），并随通知发给维修工——不写理由等于让师傅猜 |
| 之后怎么走 | 工单回到 **30 处理中**，`worker_id` **保留**：还是这位师傅返工 |
| 与"驳回"的区别 | 驳回是"**这单不该我做**"，会清空派单、退回调度池；验收不通过是"**还是你做，但没做好**"，师傅不变。这也是状态机上必须多一条 `40 → 30` 的原因——借用驳回会让这一单丢失"谁在做"的信息 |
| 重新计时 | 打回时取消原节点并重新登记"未处理升级"（基准仍是 `dispatch_time`，口径不变：从派到完工整体超期） |
| 能来几次 | 不限次数（每次都有记录）。**处理时长按最后一次完工算**（`finish_time` / `handle_minutes` 会被第二次完工覆盖），因为统计口径关心的是"最终花了多久" |
| 与评价的关系 | 不写 `ticket_evaluation`：那张表只在验收通过时写。满意度统计的是"通过验收的单"。**低分与打回是两件事**：低分＝修完了但质量一般；打回＝没修好，重来 |

**转派（`20 / 30 → 20`，换个人做）**

现实里最常见的一种调度：**师傅临时有事、请假、或者这单本来就该别人去**。它既不该走"驳回"（这单没毛病，不需要退回调度池再重新派），也不该让学生重新报修。

| 项 | 规则 |
|---|---|
| 谁能做 | 后勤（权限码 `ticket:transfer`） |
| 什么时候能 | 20 待接单（还没接）或 30 处理中（接了但没完工） |
| 必须写理由 | 理由进 `ticket_log`，**并随通知发给原师傅**——他的活突然没了，得知道为什么（"临时有事"和"你做得不行"是两回事） |
| 怎么换 | `worker_id` 换成新师傅，状态回到 **20 待接单**（新师傅也要走"接单"这一步，不能替他接） |
| **计时从头开始** | `dispatch_time` 重置为现在。超时口径是"从派到完工"，不能让新师傅背前一个人的延迟：转派后"24h 未接单"重新起算 |
| **上一轮的接单/到场时间清掉** | `accept_time` / `arrive_time` 置空。响应时长的口径是"到场 − 派单"，留着旧的值会算出负数或虚高的数（谁来过、来过几次在 `ticket_log` 里，不丢） |
| 不能转给同一个人 | 否则等于把计时器清零——那是一条绕过"24h 未接单提醒"的路 |
| 跨楼栋也能转 | 与派单同一条规则：属于紧急抽调，服务端放行 + 留痕 + 界面上确认（§4.2） |
| 通知谁 | **原师傅**（工单已转出：转给谁、为什么）+ **新师傅**（新的待接单）。**不通知学生**：与学生有关的状态没变，他看到的还是"处理中/待接单"（与"派单只通知师傅"同一个口径） |
| ~~为什么不做"多人协同"~~ | **已实现（2026-09-28，见 §4.5）**。当初卡住的两个问题都有了答案：协作者是一张关联表 + 数据权限加第三层；"谁完工算完工"靠条件更新（CAS，先完成者算数，第二个人被状态机挡下）。当初列 P1 的理由是**先做主线**，不是规则想不清 |

### 4.2 维修工的任务视图与可见范围

维修工的可见范围是**三层叠加**，不是三选一：

1. **我负责的楼栋**（`worker_building`，主要范围）——这栋楼里所有工单他都看得到，含别人负责的、含终态（便于现场沟通时知道"这栋楼在修什么"）；
2. **派给我的单**——即使不在他负责的楼栋（后勤临时抽调，见下），他也必须看得到**并且能走完整维修流程**（接单 / 到场 / 完工）；
3. **我参与协作的单**（`ticket_collaborator`，§4.5）——后勤拉他一起做的单，同样是"看得到 + 走得完流程"（到场 / 完工），
   只是他不能接单与驳回（处置权在主责）。

> **为什么必须叠加第 2、3 层**：可见范围过去只按楼栋给，于是"跨楼栋派单"会造成一张**没有人能操作**的单——派单成功、师傅却看不到，只能等 24 小时未接单提醒才发现。可见范围与操作权必须一致。协作单是同一个坑的另一半：人被拉进来了却看不到，活照样没人干。

维修工端首页给**两个视图**：

| 视图 | 内容 | 用途 |
|---|---|---|
| **我的任务**（默认） | 派给我的单 **+ 我参与协作的单**（后者带「协作」标记），默认给出**进行中**（待接单 / 处理中 / 待验收） | 回答"我现在该干什么" |
| **本楼栋** | 我负责楼栋里的全部工单（含终态、含别人负责的） | 回答"这栋楼在修什么" |

> **协作单为什么进「我的任务」而不是单独一个 tab**：被拉去搭手的活也是"我现在该干的活"，
> 分成第三个 tab 的后果是"维修工得记得切过去看"——而漏看一张协作单的代价是**没人去修**，
> **漏看**比**列表被多一条活冲乱**严重得多。用「协作」标记区分这两类来源就够了。

**排序规则（两个视图都用）**：紧急度高的置顶（特急 → 紧急 → 普通）；同一紧急度内，**先来的排在前面**（先提交 / 先派单的先做），避免早报修的单被一直推到后面。

**紧急度的作用**（原先只在需求里出现一个字段，没定义行为，这里补齐）：

- 影响维修工任务列表的**排序**（置顶规则，见上）；
- 作为统计看板的一个**分布维度**；
- **不影响**超时阈值（阈值是全校统一的可配项，不按紧急度分档）。

以上是当前实现，不代表具备应急处置能力。“特急”标签不能保证及时响应；漏电、火情等涉及人身安全的情况应联系学校既有值班或应急渠道。分级提醒、值班人员通知和人工升级属于 §1.2 的后续建议，尚未实现，AI 分诊也不承担应急决策。

**跨楼栋派单 = 紧急任务（强制派单）**

后勤可以把单派给不负责该楼栋的师傅，这属于**紧急抽调**，规则是：

- 服务端**允许**，但要在派单时明确告知（前端确认框："该师傅不负责 X 号楼，确认作为紧急任务强制派单？"），并在 `ticket_log` 里留下"跨楼栋强制派单"的痕迹；
- 被派的人按上面第 2 层可见范围，**看得到、走得完流程**；
- 不设"只有紧急单才能跨楼栋"的硬性校验：紧急度是调度员的判断，系统只保证越界这件事**被记录、被看到**，而不是替调度员决定。

### 4.3 通知的接收人（"相关方"具体是谁）

| 动作 | 接收人 | 文案 |
|---|---|---|
| 派单 | 维修工 | 新工单待接单：已派给你，请及时接单 |
| 接单 | 学生 | 维修工已接单，维修工会尽快到场 |
| 到场 | 学生 | 当前实现通知“维修工已到场处理”；实际仅为维修工声明到场，通知用语列入后续同步范围 |
| 完工上报 | 学生 | 维修已完成，请验收评价 |
| 验收评价 | 维修工 | 工单已验收 |
| 驳回 | 学生 **+ 当时的维修工** | 工单被驳回：原因 |
| 转派 | 原维修工（转出）+ 新维修工（待接单） | 工单已转出：转给谁、为什么；新工单待接单 |
| **加协作者**（§4.5） | **被加的维修工** + **主责** | 你是这单的协作人：位置与要求；已请 xxx 一起处理 |
| **移除协作者**（§4.5） | **被移除的维修工** | 你已不是这单的协作人 |
| **拆单**（§4.5） | **学生** + **原主责**（若已派单） | 你的报修已拆成两张单（新单号）；你负责的工单已拆出 WX…（新单号） |
| 协作者完工 | **学生**（与主责完工同一条）+ **主责**（仅当完工的不是他本人） | 维修已完成，请验收评价；你负责的工单已由 xxx 完工 |
| 验收不通过 | 维修工 | 验收不通过：原因（请重新处理） |
| 撤销 | 已派单时通知相关维修工；不通知撤单学生本人 | 工单已撤销 |
| 超时未接单提醒 | 后勤（本租户管理员） | 24h 未接单提醒 |
| 处理超时升级 | 后勤（本租户管理员） | 48h 未处理升级 |
| 验收超时自动关闭 | 学生 | 验收后超时未关闭，工单已自动关闭 |

> 驳回之所以要发给"当时的维修工"：他刚被派了这单又被后勤驳回，不通知他，他会一直以为这单还在自己手上（`worker_id` 已经被清空了）。

**当前验收评价**：`/evaluate` 要求 1–5 分，评价内容可选；当前没有独立的“只验收不打分”接口。评分后从 40 进入 50，再登记超时关闭；长期停在 40 不会因此自动关闭。验收与评价是否拆开见 §1.2，未评价不能被解释为默认满意。

> 那"修得不满意"怎么办：**不用打分，直接走「验收不通过」打回重做**（见 §4.1）。低分与打回是两件事——**低分＝修完了但质量一般，打回＝没修好、重来**，所以两条路都要有。

### 4.4 操作审计日志

**为什么要有**：工单流转有自己的台账（`ticket_log`），但**账号与基础数据的改动一点痕迹都没有**——改一个学生的姓名、停用一位师傅、把某栋楼改成停用、重置谁的口令，事后只能靠人回忆。学校真用起来之后，这类问题一定会出现："这个账号谁停用的""上个月是不是有人改过报修码"。审计日志就是回答这些问题的唯一凭据。

**记什么**（写操作，按类别）：

| 类别 | 动作 |
|---|---|
| 维修工账号 | 新增 · 修改（含启停）· 设置负责楼栋 · 重置口令 |
| 学生账号 | 新增 · 修改（含启停）· 重置口令 · 批量导入 |
| 本人自助 | 改自己的登录口令 |
| 楼栋 / 类别 / 报修码 | 新增 · 修改 · 停用（删除） |
| 平台运营 | 开通学校 · 修改学校 · 启停学校 · 新增学校管理员 · 重置其口令 · **搬迁学校数据 · 切到独立库** |
| **登录事件** | 登录成功 · 登录失败（口令错误 / 账号不存在）· 账号已停用 |

**每条记这六样**：谁（操作人 id + **当时的姓名快照**）、什么时候、对谁（目标类型 + id + **名称快照**）、做了什么（动作码 + 一句人话摘要）、来源 IP、租户。

> **为什么要存姓名快照**：账号改名、楼栋被删之后，审计记录光看 id 什么也读不出来。审计表是**只读的历史**，不能跟着主数据一起变。

**明确不记**（边界要写出来，否则"为什么查不到 XX"会被当成 bug）：

| 不记 | 理由 |
|---|---|
| 读操作（列表 / 详情 / 看板 / 问数） | 记了会把审计表冲成访问日志，真正要查的"谁改了东西"反而淹掉 |
| **工单流转** | `ticket_log` 比审计表更细（from/to 状态 + 动作 + 操作人），重复记两份等于两份可能不一致的真相。想知道工单的轨迹去工单的时间线 |
| **口令明文**（含新口令） | 只记"重置了谁的口令"，绝不记口令本身（AGENTS §5.9）。登录事件同理：只记"谁在哪次登录失败了"，不记他试的是什么口令 |
| **手机号等敏感字段的原值** | 摘要里只说"手机号已更新"，不回显新旧值——审计表也是表，落进去就收不回来了 |
| 登录**成功**的重复登录 | 同一账号 + 同一天 + **同一来源 IP** 只记一条：H5 每次冷启动都要登录，全记会让这张表以登录为主（一所学校约 4000 条/天、一年上百万行），"谁改了东西"的主查询就被淹了。**换 IP 会另记一条**——那正是"账号被盗"最该看见的信号。失败**不去重**（失败本来就是稀有事件，每次都要看得见） |
| 租户不存在 / 已停用的登录尝试 | 租户都不存在，这条记录没有"谁的表"能放（审计是按租户查的）。这类探测留在服务器的 WARN 日志里 |
| 被限流拦下的登录（`10004`） | 它是失败的延续：同一次爆破会连续触发限流，逐条记只会刷屏；每次**失败**都已经记了，看失败的次数就够 |

**登录事件是"独立的一类"**（当初列 P1 时就是这么写的），所以它有两条与其它记录不同的规矩：

1. **默认不出现在列表里**：管理端「操作日志」页默认只回答"谁改了东西"——这是这个页面的主查询。
   要看登录事件就勾「含登录事件」，或直接按动作筛（`LOGIN_SUCCESS` / `LOGIN_FAILED` / `LOGIN_DISABLED`）。
   不加这条，登录记录会占掉列表的绝大多数。
2. **审计写失败不阻断登录**：其它写操作的规矩是"审计失败 → 业务失败"（宁可操作失败，也不要改了东西却查不到谁改的）。
   但登录**没有改任何业务数据**，而它一失败就是全校都登不进去——**包括唯一能来修表的管理员**。
   所以这里破例：审计写失败只记 ERROR 日志（`AuditServiceImpl` 里那两个登录方法因此**绝不抛异常**，
   与其它方法相反，这个差异在类注释里也写了一遍）。

**失败的原因写清，但接口响应不区分**：审计的 detail 里写"账号不存在"还是"口令错误"，而登录接口对两者
返回同一个错误码（`30001`——"不向尝试者透露账号是否存在"的口径没有变）。看审计的人是**本租户的后勤管理**，
他本来就看得见账号列表，所以这里不构成新的泄露；而"有人在试一个不存在的账号"对排查很有用。

**谁能看**：后勤管理（权限码 `audit:list`），**只看本租户**。平台运营的操作也会记进表里（`tenant_id = 0`），但这一期没有给平台账号做查询界面——平台侧排障仍然靠服务器日志，这一点是已知边界。

**改不改得**：**只读**。审计表没有 `update_time`、没有逻辑删除——能改的记录不是审计记录。**本期不做自动清理**：一所学校一天几十条写操作，一年也就几万行，MySQL 毫无压力；真要归档时按 `create_time` 定期导出即可。

### 4.5 协同处理：加协作者与拆单

主线是"一个人一单"，但现实里有两类例外：**一件活需要两个人一起干**（大件、要扶梯子、要断电配合），
和**一张单里其实是两件事**（"灯坏了 + 水龙头漏水"）。前者用**协作者**（加法：加人），
后者用**拆单**（除法：拆活）。两者都在解决"活与人手不匹配"，但规则完全不同，不要混着理解。

#### 加协作者（多人同做一单）

| 项 | 规则 |
|---|---|
| 谁能加 / 移 | 后勤（权限码 `ticket:dispatch`——**加协作者和派单是同一类判断**："谁参与这单"，所以不新造权限码） |
| 什么时候能 | 20 待接单 / 30 处理中。10 还没有主责、40 之后活已经干完，都没有"搭把手"的余地 |
| 加谁 | 本租户、启用中的维修工。**主责本人不能被加成协作者**（他就是主责）。跨楼栋也能加——与派单同一条规则，不加限制 |
| 加几个 | 最多 **3 个**（连同主责最多 4 人在一单上）。再多就不叫"搭把手"了——那种情况该看是不是该拆单 |
| 协作者能做什么 | **能到场打卡、能完工上报**；**不能接单、不能驳回、不能转派**——处置权仍归主责与调度。到场与完工走的是与主责**同一套**校验和幂等，不另开一条路径 |
| **完工怎么算** | **任一参与者都能点完工，谁先点谁算数**。第二个人再点会被状态机挡下（`40` 不允许再完工）——这就是"重复完工怎么办"的答案：不靠约定，靠条件更新（CAS）。"是谁完成的"记在 `ticket_log.operator_id` 里，**不新增字段** |
| **统计归因** | **看板仍按主责归因**（师傅工作量、按时完成率都看 `worker_id`）：主责是这单的责任人，调度与考核对着他。改归因要动看板 SQL 与 `docs/03` 的口径表，本期不动——**这条边界写在明处，免得日后被当成算错** |
| 超时口径 | **不变**：`dispatch_time` 不因加人而重置，阈值也不分档。"加个人来帮忙"不是重新派单——计时从头开始是**转派**才有的语义（§4.1） |
| 可见性 | 协作者对这张单**可见**（否则又会造出"派了却看不到、干不了"的单，与 §4.2 第 2 层同一个教训）：数据权限拦截器给维修工的范围加第三层——`我负责楼栋 OR 派给我的 OR 我协作的` |
| 怎么收尾 | 后勤可以移除协作者；移除后随之不可见。留痕在 `ticket_log`，不是无声无息 |
| 通知谁 | **被加/被移的那个人**（他是当事人）+ **主责**（谁进了这单，他该知道）。协作者完工时，**学生**收到的通知与主责完工完全一样（学生不需要知道干活的是几个人），**主责**另收一条"已由 xxx 完工" |

> **为什么协作者不能驳回**：驳回的语义是"这单不该我做"（§4.1）——那是对**派单**的判断，
> 属于主责与调度。被拉来搭手的人若觉得不该做，正常做法是跟主责说一声，而不是把单退回调度池。

#### 拆单（一张单里其实是两件事）

| 项 | 规则 |
|---|---|
| 谁能拆 | 后勤（同样 `ticket:dispatch`） |
| 什么时候能 | 原单 10 待派单 / 20 待接单 / 30 处理中。40 之后活已经干完，"拆"没有意义 |
| 拆出什么 | **一张新的待派单工单**：继承原单的**楼栋 / 房间 / 学生 / 现场图片**；**描述另填**（拆出来那件事得自己说清楚）；类别与紧急度**默认继承、可改**（"灯坏了"与"水龙头漏水"本来就不是一类）；状态 10 待派单 |
| 原单怎么办 | **一个字都不动**：它继续修它那部分，主责与计时都不变 |
| 关系怎么记 | 新单的 `parent_ticket_id` 指向原单。**只拆一层**：拆出来的单不能再拆（否则会变成一棵谁都说不清的树） |
| 派谁去修 | **不在拆单里指定**——"派给谁"是独立的一个动作（派单）。塞进拆单会让时间线上"拆"和"派"缠在一起，也是"不做自动派单"的同一条理由 |
| 通知谁 | **学生**（他报的一单变成了两张，得知道）+ **原主责**（若已派了人：他的活少了一半） |
| 为什么不顺手做"合单" | 本期不做。拆是"把混在一起的事分开"，合是"把两件事并成一单做"——合单的规则（谁当主责、两张单的时间与评价算谁的）比拆复杂得多，不在 P1 |

> **拆单与加协作者的分界**：一件事需要人手 → 加协作者；一张单里装了多件事 → 拆单。
> 分不清的时候问一句："这些是不是同一个故障？"不是同一个故障，就该拆。

**明确不做**（写出来，免得日后被当成漏做）：合单 · 三层以上的拆分 · 协作者之间的分工记录（谁修了哪一部分）·
协作者自己退出（只能由后勤移除）· 拆分历史工单。

### 4.6 报修位置：扫码与手动选择两条通道

**位置从哪来**有两种，最后落到同一张工单表、同一套到场核验：

| 通道 | 谁用 | 位置怎么确定 |
|---|---|---|
| 扫码 / 手输 6 位码 | 宿舍内最常见 | 码 →（楼栋 + 房间），楼栋房间由**服务端**从码里取，前端不传 |
| 手动选位置（楼栋 → 位置） | **公共区域**（走廊 / 大厅 / 公共卫生间）、门口贴纸磨损 | 从"有码的位置清单"里选，提交 `buildingId + room` |

**为什么必须有第二条**：公共区域不可能"一间房一码"，而要求人为了报修去满楼找码是不现实的。
但**每个可选位置都必须有一张报修码**——师傅到场要扫同一张码核验（`arrive` 比对码与工单位置），
所以公共区域也有自己的"区域码"：**一个区域一张**，贴在楼层电梯口 / 大厅入口这类必经之处。
这条不变量让两条入口共用同一套到场核验，不需要为公共区域写特判。

**为什么不在服务端硬拦"只能报自己的宿舍"**：报修人是 **发现者（Reporter）**，不一定是住户——
串门发现漏水、走廊灯坏了、实验室设备坏了都是真实场景。归属问题用"记报修人 + 后勤按位置派单"解决，
不用限制制造新的死角。真要收紧，正确做法是先给位置加归属（宿舍 ↔ 学生）再按规则判断——
而当前 `sys_user` 里没有宿舍字段，做这件事要先补数据模型，属于独立需求。

**位置清单的来源就是报修码**（`GET /api/locations` 返回"本租户启用楼栋下、有码的位置"）：
不另建位置表，避免出现"选了位置却发不出码 / 到场验不了"的缝。

### 4.7 扩展状态：待料 / 无法维修 / 已合并

主线之外的三种"卡住"与"收敛"，解决的是真实调度里最常被口头处理掉的三件事：师傅等材料、师傅修不了、同一处被报了两次。状态码插在 10 的间隔里（35 / 45 / 75），主线编号不变。

**35 待料**（师傅在处理中发现缺材料）

- **谁能标记**：这单的主责或协作者（30 → 35），理由必填，进 `ticket_log`；学生收到"维修暂停（待料）"。
- **谁能恢复**：同一个师傅（35 → 30，材料到了）；后勤也可以恢复（避免师傅忘了点）。
- **超时口径不变**：待料**不暂停 SLA**。计时仍是"从派到完工"，处理超时照样升级给后勤——
  后勤正是能催料/调人的人；如果暂停计时，待料就成了绕过超时的口子。
- 待料期间学生仍可撤单、后勤仍可合并；不能直接转成"无法维修"（要么恢复后重新判断，要么先恢复）。

**45 无法维修**（师傅判定修不了）

- **谁能标记**：主责或协作者（30 → 45），理由必填；进入 45 时**撤掉处理超时节点**并**通知本租户全部后勤**。
- **45 在等后勤拍板**，师傅不能再自己改状态。后勤有三种处置：
  - **重新派单**（45 → 20）：必须换人；上一轮的接单/到场时间清空，计时从头开始（同转派口径）。
    派回原师傅不允许——那等于把 `dispatch_time` 重置，是一条绕过超时的路。
  - **恢复处理**（45 → 30）：让原师傅继续修。处理超时按**原派单时间**重新登记，已经超期就立即升级。
  - **关闭**（45 → 60）：走外部维修/换设备等线下处置。
- 学生可撤单（45 → 70）；后勤也可把它合并进别的单（45 → 75）。

**75 已合并**（重复报修）

- **谁能合并**：后勤。把当前单并进目标单：当前单 → 75，记 `merged_into_id`、清空维修工、撤掉全部超时节点；
  **目标单不动**。
- **可合并的来源**：10/20/30/35/40/45/80（终态 50/60/70/75 不行）；目标不能是自己、已撤单或已合并。
- 被合并单的学生收到带**目标工单号**的通知；目标单的学生不会被通知（合并是收敛，不是新事件）。
- 目标单不在当前用户可见范围时，详情里的 `mergedIntoNo` 为空——不泄露别的学生的单据。

**撤销与关闭的范围也扩大了**

- 学生撤单：10/20/30/35/45/80 → 70。派单后撤单会**通知当前师傅**并撤销超时节点；10/80 没有师傅，通知自动跳过。
- 后勤关闭：45/50/80 → 60。关闭时撤销超时节点并通知学生。

**这一轮没有做的**（明确留白，避免被当成漏实现）

- 10 待派单、80 已驳回的**超时提醒**（例如"驳回后 24h 没人重新派单"）：需要新的超时节点与口径，
  与 35/45/75 没有依赖关系，单独一轮做。
- 待料的**暂停计时**：需要记录暂停区间（新列/新表），当前选择"不暂停"，理由见上。
- 合并的**反向入口**（从目标单看到合并进来的单）：当前只记 `merged_into_id`，查询方按它反查即可。

### 4.8 设备台账与派单辅助（阶段 3）

主线之外的"资产"与"调度辅助"。两者都不改变工单状态机，只给调度员更多依据。

**设备台账（asset）**

- 学校维护可维修的设备：设备编号（**租户内唯一**，同时作为二维码内容）、名称、类别（复用报修类别）、
  楼栋/房间、状态（1 在用 / 2 维修中 / 3 停用报废）、采购日期、保修期、供应商、备注。
- 管理端 CRUD；编号重复返回 10001；**只允许删除从未被工单引用的设备**，被引用的只能停用/报废
  （与楼栋同一条理由：逻辑删除后历史引用会变成空白）。
- 学生报修时**可选**关联设备（不强制，老入口不受影响）；工单详情展示设备编号/名称；
  设备详情按 `ticket.asset_id` 聚合维修历史。
- 二维码不单独存字段：内容就是设备编号，前端用同一套二维码组件渲染/扫码。

**工种 / 分组 / 排班**

- 工种：在现有 `worker_skill`（擅长类别）之外增加"工种"分组（如水电工、木工、空调工），
  一个维修工可属多个组；派单候选按"工单类别 → 工种"做过滤/加分。
- 排班：`worker_shift`（日期 + 班次 + 值班状态），派单候选默认只看"当天在班"的人；
  调度员可以手动勾选"显示不在班"。
- **派单仍然只做候选排序 + 人工确认**（延续 ADR-019）：技能 / 满意度 / 负载 / 距离 / 值班五项加权，
  输出候选列表，调度员点"派单"才生效。**不做全自动派单**——把调度责任交给系统，与
  "派给谁由调度员判断"的既有约定冲突，也失去了出事时的可解释性。

## 5. 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | 提交报修 P99 < 500ms；工单列表 P99 < 300ms；统计看板 < 800ms |
| 压测基准 | 测试环境以 **100 请求/秒**为设定负载，持续 1 分钟，成功率目标 ≥ 99.9%；请求数不等于新建工单数。历史实测速率、延迟和未达标路径统一见 `docs/08-压测报告.md`，本轮未复跑 |
| 安全 | SQL 注入防护；越权防护（RBAC + 数据权限双层）；AI 生成的 SQL 必须过安全网关；报修码随机生成、防枚举（**已实现**：接收报修码的接口按登录用户限流，超限 `10004`，见 ADR-009）；手机号、密码等敏感字段不入日志 |
| 可用性 | 单机部署，允许短暂不可用；关键路径有降级策略（见下） |
| 可维护性 | 统一返回体、全局异常、traceId 链路、Knife4j 文档、单元测试（状态机 / 幂等 / 数据权限） |
| 多租户公平性 | **租户账号配额**：`max_students` / `max_workers`（0 = 不限），建号与批量导入时校验，超限 `30004`。防"一个学校批量导入把库撑坏"，口径与取舍见 ADR-020 |
| 缓存 | 只缓存**读得多、变得少**的两类：鉴权结果（TTL 30 分钟）与启用中的类别（按租户，TTL 5 分钟）。**Redis 故障时降级为不回缓存**，业务照常（缓存是加速器，不是正确性的依赖） |
| 可观测性 | `/actuator/prometheus` 文本端点（**仅容器内 / 本机可达**，nginx 只反代 health）+ 两个业务指标：工单事件、AI 调用次数。标签只放低基数维度（动作、租户、用途、结果） |

**压测目标的依据与边界**：100 QPS 是自主设定的工程基准，用于观察索引、连接池、事务和混合请求下的表现，没有真实学校工单量或峰值流量证据。历史测试在本机模拟资源限制下完成，不能等同于 4C4G 云主机实测，也不能证明当前提交或 full 部署达到同样容量；创建工单还涉及 Outbox 等写路径，不能简化为固定两条 INSERT。上线容量需在明确版本、拓扑、数据量和负载分布后重新验证，写压测只对隔离测试库执行。

**降级策略**：

| 依赖不可用 | 降级行为 |
|---|---|
| Redis（延迟队列 / 限流计数） | 超时提醒 / 升级暂停，由每分钟一次的兜底扫描补漏；**报修码限流放行**（计数不可用时选择放行，宁可漏挡也不阻断扫码报修）；工单主流程不受影响 |
| AI 模型（DeepSeek） | 问数接口返回 `40004`，前端提示改用统计看板 |
| MinIO | 图片上传返回 `50003`；**文字描述仍可提交**（描述必填 ≤500 字、图片可选 ≤9 张，图片可后补） |

## 7. 设计问答：这份文档能回答哪些问题

> 下面每一条都是**结论性的回答**；展开与追问应对见第 8 节。

- [x] **你为什么要做这个项目？**

  我基于个人观察和自主设计，使用 AI 工具辅助实现了一个高校后勤维修协同平台原型，重点验证工单状态流转、多租户隔离、可靠事件通知和受控 Agent。场景假设是学校已有报修入口，但维修协同和统计仍可能存在断点；目前尚未开展正式访谈、接入真实学校或验证商业需求，演示数据均为虚构或自行生成。

- [x] **为什么设计成三方角色，而不是"管理员 + 用户"？**

  因为三方的**诉求和数据可见范围完全不同**：学生只关心自己那一单；维修工只关心派给自己的单、以及自己负责楼栋的工单（**两层叠加，不是二选一**，规则见 §4.2）；后勤要全局调度和统计。做成"管理员 + 用户"，管理员既要派单又要维修，职责混淆，权限也收敛不到一处。三方分角色后，数据可见范围天然产生差异——**这才是这个项目业务复杂度的来源，也是我数据权限设计的依据**。

- [x] **短信 / 邮件通知要不要做？**

  当前默认站内通知，尚无真实站外业务投递。已预留通道接口、投递记录、退避重试和死信状态，可在确认邮件账号类型、授权和配额后接入适配器。渠道选择依据是接收人能否及时收到、成本和运维能力，而不是 API 调用的“技术含量”。监控告警的邮件配置和业务工单邮件是不同链路，不能混称已接入。

- [x] **你的数据权限是怎么设计的？**

  分三层说。**依据**：`worker_building` 关联表记录每个维修工负责哪些楼栋；学生用自己的 `student_id`；后勤不限制。**实现**：MyBatis 拦截器解析 SQL 的 AST，注入**两层**条件——**先按租户隔离**（`tenant_id = 当前登录者的租户`，后勤也不例外），**再按角色隔离**（学生 `student_id = 当前用户`、维修工 `building_id in (负责楼栋)`、后勤不再追加）。两层条件在同一个拦截器里，顺序即语义（见 ADR-008）。**为什么**：如果每条 SQL 手写 where，问题不是麻烦，是它会漏——漏一次就是一次越权漏洞，而且 code review 时肉眼很难发现；收敛到框架层后，权限逻辑只写一次，新增接口零成本获得保护，从"靠自觉"变成"默认安全"。

- [x] **AI 生成的 SQL 怎么保证不越权？**

  原则是**不信任模型输出**，安全不能写在 Prompt 里，因为 Prompt 约束不了模型行为。所以我做了一道独立的 SQL 安全网关，四层闸门：① 只读账号连接，防改数据、删表；② SQL 白名单只允许 `SELECT`，禁 DDL/DML/多语句，防结构破坏和多语句注入；③ **强制租户范围**，防越权读——这一层是只读账号做不到的；④ 超时熔断（>3s）+ 返回行数上限（>1000 行），防慢查询拖垮数据库。这套网关不依赖模型，可以单独写测试。

  > 第 ③ 层的实现要说明白：**不走 MyBatis 拦截器**。那个拦截器只覆盖 `ticket` / `notification` 两张表，而 AI 能查白名单里的任何一张，靠它 `SELECT * FROM building` 就会读到别家的楼栋。所以是网关自己在 SQL 的 AST 上给每张表注入 `tenant_id`（ADR-003「落地时的修正」）。

## 8. 展开说明（追问与展开）

### Q1 展开：痛点要具体到"能被验证"

描述时要同时交代需求来源、待验证假设与已实现能力，不能因为场景听起来合理就把它写成调研结论：

> 我假设学校已有报修入口，但受理信息补全、维修协同和统计口径可能仍有改进空间，因此设计了维修业务域原型。多租户用于验证学校间配置与数据隔离，不代表已签约多所学校，也没有完成企业微信 / OA 报修对接。下一步需通过访谈和流程验证判断哪些需求值得保留。

### Q2 展开：角色划分要扣到数据权限上

⚠️ 不要用「通用场景」「维修工有多个」当理由——那不是理由，说明还没想清楚。

| 角色 | 关心什么 | 数据可见范围 |
|---|---|---|
| 学生 | 我这一单什么时候来修 | 只有自己提交的工单 |
| 维修工 | 今天要处理哪些单、在哪、什么毛病 | **派给自己的单 + 自己负责楼栋的工单**（两层叠加；默认视图只给「我的任务」，见 §4.2） |
| 后勤管理 | 全局调度是否均衡、谁超时了 | 全部（本租户） |

> 因为三方的**诉求和数据可见范围完全不同**：学生只关心自己那单，维修工只关心派给自己的单和自己负责的楼栋，后勤要全局。做成"管理员 + 用户"，管理员既要派单又要维修，职责混淆，权限也收敛不到一处。三方分角色后，数据可见范围天然产生差异——**这才是这个项目业务复杂度的来源，也是我数据权限设计的依据**。

关键：把"角色划分"直接接到"数据权限"上，一个问题带出下一个技术点。

### Q3 展开：通知通道的取舍

| 方案 | 做不做 | 理由 |
|---|---|---|
| 短信 | 尚未接入 | 需评估账号资质、模板、费用与接收人覆盖范围，当前暂缓 |
| 邮件 / Outlook | 后续优先评估 | 先确认个人 / 组织账号和授权方式，再决定适配方案；已有 Outbox 是事务发件箱模式，不是 Outlook 邮件服务 |
| 企业微信 | 只有占位实现 | `WeComChannel` 默认关闭，打开也会明确失败，不可宣称已送达 |
| 微信订阅消息 | 尚未接入 | 依赖小程序身份、授权和平台规则，当前 H5 演示暂缓 |
| **站内通知** | 已有实现 | 跨端可查看未读、已读和工单关联记录；用户离线时不保证及时获知 |

**登录同理**：用账号密码（学号 / 工号），不接微信授权登录——`wx.login` 只有小程序有，H5 没有，登录方式必须两端一致。
**统一认证（阶段 7 · ADR-022）是账号密码之外的第二个入口**：对接学校自己的 IdP（CAS / OAuth2），
不是第三方社交登录；账号仍由学校维护，认证通过不会自动建号。

**站内通知怎么做**：一张 `notification` 表（接收人 / 类型 / 标题 / 内容 / 关联工单 / 是否已读 / 时间），工单状态变更时插一条，前端**轮询**拉取未读数。

**为什么轮询而不是 WebSocket**：当前演示环境未要求实时推送，轮询的实现和排障成本较低；WebSocket 需要处理心跳、断线重连和多实例广播。没有真实学校的消息量依据，不据此推导生产负载。

> **取舍说明**：先保证站内信可靠记录，再依据离线触达需求接入可选站外通道；外部失败不应阻断站内信和工单主流程。API 能调用不等于通知能可靠送达，需核对授权、重试、去重、退信和死信处置。
>
> 把"不做什么、为什么不做"写清楚，比多做一个功能更能说明取舍标准。

### Q4 展开：数据权限的三层追问

⚠️「数据可见度范围隔离」只是结论。真正要能说清的是三层：**依据是什么、怎么实现、为什么这么做**。三层缺一，就只是背了个概念。

| 层 | 内容 |
|---|---|
| ① 依据 | `worker_building` 表记录维修工负责的楼栋；学生用 `student_id`；后勤不限 |
| ② 实现 | MyBatis 拦截器解析 SQL AST，**先按租户、再按角色**自动注入条件（ADR-008） |
| ③ 为什么 | 手写 where 的问题不是麻烦，**是它会漏**；漏一次就是越权漏洞，review 时很难发现。收敛到框架层后，权限只写一遍，新增接口默认安全 |

补充：多租户隔离（`tenant_id`）走同一层拦截器，并且在数据权限条件之前注入——**先按租户隔离，再按角色隔离**。

### Q5 展开：只读账号防不住越权

⚠️ **这里有个常见概念错误：只读账号防的是"改数据"，防不了"看别人的数据"。** 越权是**读**的问题，只读账号对此完全无效。

| 层 | 做什么 | 防住什么 |
|---|---|---|
| 1 | 只读账号连接 | 改数据 / 删表 |
| 2 | SQL 白名单（只允许 `SELECT`，禁 DDL / DML / 多语句） | 结构破坏、多语句注入 |
| 3 | **强制租户范围**（网关在 AST 上给每张表注入 `tenant_id`，不是走 MyBatis 拦截器） | **越权读** ← 只读账号做不到，靠这层 |
| 4 | 超时熔断（>3s）+ 返回行数上限（>1000 行） | 慢查询拖垮数据库 |

> **一句话总结**：我的原则是**不信任模型输出**。安全不能写在 Prompt 里，因为 Prompt 约束不了模型行为。所以我做了一道独立的 SQL 安全网关，四层校验，而且这套网关不依赖模型，可以单独写测试。

**第 3 层是最关键的一层**——它说明 AI 在这里是被当成工程问题处理的，而不是调个 API。
