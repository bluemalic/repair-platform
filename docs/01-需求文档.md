# 01 · 需求文档（精简 PRD）

> 拷贝到 `docs/01-需求文档.md`，按提示填写。
> **不要写成流水账。** 面试官只关心三件事：为什么做、给谁做、必做的是什么。

---

## 1. 背景与痛点

**要解决的问题**：高校后勤维修的响应流程不透明、效率低。

具体表现（把这三条写实，它们是你"为什么做这个"的答案）：

1. 学生报修靠电话或微信群，说不清位置和问题，图片也传不明白
2. 后勤靠纸笔或 Excel 登记，派单靠打电话，工单进度无人可知
3. 月底统计全靠手工汇总，无法回答"哪个楼报修最多""哪个师傅效率最低"

**为什么要做成 SaaS**：这个痛点不是某一所学校独有的。后勤维修是通用场景，做成多租户后，每个学校/校区独立配置，互不干扰。

---

## 2. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| 学生 | 宿舍水电坏了、门锁坏了 | 快速报修、知道进度、能评价 |
| 维修工 | 每天接单上门 | 清楚今天要干什么、在哪、什么毛病 |
| 后勤管理 | 调度全校维修资源 | 派单合理、进度可控、数据可查 |
| 系统（AI 数据助手） | 后勤管理问数 | 用一句话拿到统计结论，不用学 SQL |

**端形态**：学生端与维修工端是**同一个 uni-app 工程**（先编译 H5，备案后可编译小程序），登录后按角色路由区分；后勤管理端是独立的 Vue 3 PC 后台。

## 3. 用户故事

> 格式：**作为 <角色>，我希望 <做什么>，以便 <获得什么价值>**

### 学生端
- 作为学生，我希望扫码就能提交报修并上传照片，以便不用打电话描述
- 作为学生，我希望**扫宿舍门口的报修码就能自动带出楼栋和房间**，以便不用手填位置
- 作为学生，我希望随时看到工单进度，以便知道师傅什么时候来
- 作为学生，我希望完工后能评价，以便反馈服务质量

### 维修工端
- 作为维修工，我希望看到派给我的工单列表，以便安排上门顺序
- 作为维修工，我希望上传处理结果和现场照片，以便留档
- 作为维修工，我希望只看到我负责的楼栋，以便不被无关工单干扰
- 作为维修工，我希望**到场扫报修码完成打卡**，以便系统准确记录到场时间（响应时长的真实依据）

### 后勤管理端
- 作为后勤管理，我希望按类别或楼栋自动/手动派单，以便调度均衡
- 作为后勤管理，我希望看到超时工单并升级提醒，以便压住响应时长
- 作为后勤管理，我希望看到统计看板，以便考核与决策
- 作为后勤管理，我希望能直接问"上月 3 号楼报修最多的是什么"，以便不学 SQL 也能拿数据

## 4. 功能清单

### 必做（P0）

| 模块 | 功能点 |
|---|---|
| 三方账号与权限 | 三种角色登录、RBAC 菜单/按钮权限、数据可见范围隔离 |
| 工单全流程 | 提交（图片/位置/类别/紧急度）→ 派单 → 接单 → 处理中 → 上传结果 → 验收评价 → 关闭 |
| 工单状态机 | 8 状态 + 合法跃迁校验，禁止跳状态 |
| 超时提醒与升级 | 24h 未接单提醒、48h 未处理升级 |
| **站内通知** | 工单状态变更时向相关方推送站内消息；未读数、已读标记，前端轮询拉取 |
| 统计看板 | 报修量趋势、类别分布、楼栋分布、平均响应/处理时长、超时率、满意度、师傅工作量 |
| AI 数据助手 | 自然语言 → SQL → 结果 + 图表 + 结论 |
| SQL 安全网关 | 只读账号、白名单、禁 DDL/DML、超时熔断、行数上限 |

### 建议做（P1）

工单转派与协同处理、操作审计日志、Excel 导出、压测报告。

### 明确不做（**写出来，这是加分项**）

失物招领、活动报名、师傅排班、**短信 / 邮件通知、微信授权登录、微信订阅消息**。

> **注意：通知不是不做，是用站内通知代替**短信 / 邮件 / 订阅消息——零成本且跨端通用。
> 登录同理，用**账号密码**（学号 / 工号）而不是微信授权登录，保证 H5 与小程序两端一致。

> **为什么要写"不做"**：面试官看到"明确不做"会认为你有取舍意识，而不是什么都往项目里塞。这也是你回答"为什么不做更多功能"的现成答案——**一条做深的主线远胜五条平铺的 CRUD**。

## 8. 面试参考答法（你的答案偏短，这里补强）

### Q1 为什么做这个项目

方向对，但"效率低"太笼统。**痛点要具体**：

> 学生报修靠微信群，说不清位置和故障、图片也传不明白；后勤靠纸笔或 Excel 登记、打电话派单，工单进度没人知道；月底统计全靠手工汇总，回答不了"哪个楼报修最多、哪个师傅效率最低"。
> 我做的是把这条链路线上化的 SaaS 工单平台。做成多租户是因为这个痛点不是某一所学校独有，租户隔离后每校独立配置，可以复制。

### Q2 为什么是三方角色，而不是"管理员 + 用户"

⚠️ 你答的是「通用场景 + 维修工有多个」——**答偏了**，而且"维修工有几个"根本不是理由。

> 因为三方的**诉求和数据可见范围完全不同**：学生只关心自己那单，维修工只关心派给自己的楼栋，后勤要全局。
> 做成"管理员 + 用户"，管理员既要派单又要维修，职责混淆，权限也收敛不到一处。
> 三方分角色后，数据可见范围天然产生差异——**这才是这个项目业务复杂度的来源，也是我数据权限设计的依据**。

关键：把"角色划分"直接接到"数据权限"上，一个问题带出下一个技术点。

### Q3 短信 / 邮件通知要不要做？

**都不做，但做站内通知。**

| 方案 | 做不做 | 理由 |
|---|---|---|
| 短信 | ❌ | 要钱、要企业资质、模板要报备审核，个人很难走通 |
| 邮件 | ❌ | 就是个 SMTP 调用，**零技术含量，面试不值钱** |
| **站内通知** | ✅ | 零成本，有技术点：未读数、已读标记、推送方式选型 |
| 微信订阅消息 | ⚪ 可选 | 学生端是小程序，订阅消息免费且无需资质，是最自然的通道；但增加工作量 |

**站内通知怎么做**：一张 `notification` 表（接收人 / 类型 / 标题 / 内容 / 关联工单 / 是否已读 / 时间），工单状态变更时插一条，前端**轮询**拉取。

> **面试话术**：我明确没做短信和邮件——短信有成本和资质门槛，个人做不划算；邮件是纯 API 调用，没有技术价值。我改做了站内通知，零成本，而且"为什么用轮询而不是 WebSocket"我能说清理由：单机部署、消息量级小，轮询的实现和排障成本都更低。

**「我明确不做 X，因为……」比「我做了 X」更得分**——它显示你会在有限时间里做取舍。

### Q4 数据权限怎么设计

⚠️「数据可见度范围隔离」只是结论。面试官会立刻追问三层：**依据是什么、怎么实现、为什么这么做**。三层缺一，就会被判定为"背概念"。

> **① 依据**：`worker_building` 关联表记录每个维修工负责哪些楼栋；学生用自己的 `student_id`；后勤不限制。
> **② 实现**：MyBatis 拦截器解析 SQL 的 AST，按当前角色自动追加条件——学生加 `student_id = 当前用户`，维修工加 `building_id in (负责楼栋)`。
> **③ 为什么**：如果每个 SQL 手写 where，问题不是麻烦，**是它会漏**——漏一次就是一次越权漏洞，而且 code review 时肉眼很难发现。收敛到框架层后，权限逻辑只写一次，新增接口零成本获得保护，**从"靠自觉"变成"默认安全"**。

### Q5 AI 生成的 SQL 怎么不越权

⚠️ **这里有个概念错误：只读账号防的是"改数据"，防不了"看别人的数据"。** 越权是**读**的问题，只读账号对此完全无效。

正确是四层闸门：

| 层 | 做什么 | 防住什么 |
|---|---|---|
| 1 | 只读账号连接 | 改数据 / 删表 |
| 2 | SQL 白名单（只允许 `SELECT`，禁 DDL / DML / 多语句） | 结构破坏、多语句注入 |
| 3 | **强制走数据权限拦截器** | **越权读** ← 只读账号做不到，靠这层 |
| 4 | 超时熔断（>3s）+ 返回行数上限（>1000 行） | 慢查询拖垮数据库 |

> **一句话总结**：我的原则是**不信任模型输出**。安全不能写在 Prompt 里，因为 Prompt 约束不了模型行为。所以我做了一道独立的 SQL 安全网关，四层校验，而且这套网关不依赖模型，可以单独写测试。

**第 3 层是这个项目最能打的一句话**——它证明你在用工程思维处理 AI，而不是调 API。
