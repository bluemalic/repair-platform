# 01 · 需求文档（精简 PRD）

> 高校后勤报修 SaaS 平台的需求说明。全文只回答三件事：**为什么做、给谁做、必做的是什么**。

---

## 1. 背景与痛点

**要解决的问题**：高校后勤维修的流程不透明、响应慢、数据统计难。

具体表现：

1. **报修说不清**：学生靠电话或微信群报修，说不清故障位置和现象，图片也不方便归档；维修工到了现场才发现带错工具，或者人不在宿舍，白跑一趟。
2. **派单与进度不可见**：后勤靠纸笔或 Excel 登记、靠打电话派单；工单在谁手上、处理到哪一步，学生、后勤、师傅三方的信息是断开的，谁都不知道还要等多久。
3. **数据沉不下来**：月底统计靠手工汇总，回答不了"哪个楼报修最多""哪个师傅效率最低""超时率是多少"，考核和资源配置没有依据。

**为什么做成 SaaS**：这三个痛点不是某一所学校独有的，后勤维修是通用场景。做成多租户后，每个学校/校区独立配置自己的楼栋、报修类别、维修工与报修码，数据互不干扰，一套系统可以复制到多所学校。（**角色与权限码是平台级的种子数据**，由平台统一维护，租户不自行配置——见 `docs/04` ADR-012。）

---

## 2. 角色定义

| 角色 | 场景 | 核心诉求 |
|---|---|---|
| 学生 | 宿舍水电坏了、门锁坏了 | 快速报修、知道进度、能评价 |
| 维修工 | 每天接单上门 | 清楚今天要干什么、在哪、什么毛病 |
| 后勤管理 | 调度全校维修资源 | 派单合理、进度可控、数据可查 |
| 平台运营 | 给新学校开号、停用不再使用的学校 | 开一所学校就能用，不用碰数据库 |
| 系统（AI 数据助手） | 后勤管理问数 | 用一句话拿到统计结论，不用学 SQL |

**端形态**：学生端与维修工端是**同一个 uni-app 工程**（先编译 H5，备案后可编译小程序），登录后按角色路由区分；后勤管理端是独立的 Vue 3 PC 后台，**平台运营页也在这个后台里**（同一个工程、同一个登录页，只是菜单不同）。

## 3. 用户故事

> 格式：**作为 <角色>，我希望 <做什么>，以便 <获得什么价值>**

### 学生端
- 作为学生，我希望扫码就能提交报修并上传照片，以便不用打电话描述
- 作为学生，我希望**扫宿舍门口的报修码就能自动带出楼栋和房间**，以便不用手填位置
- 作为学生，我希望随时看到工单进度，以便知道师傅什么时候来
- 作为学生，我希望**在还没派单之前能撤销自己报的单**，以便报错了能收回
- 作为学生，我希望完工后能评价，以便反馈服务质量

### 维修工端
- 作为维修工，我希望看到派给我的工单列表，以便安排上门顺序
- 作为维修工，我希望上传处理结果和现场照片，以便留档
- 作为维修工，我希望只看到我负责的楼栋，以便不被无关工单干扰
- 作为维修工，我希望**碰上不归我处理的单能驳回并写明原因**，以便后勤改派，而不是让我空等
- 作为维修工，我希望**后勤临时抽调给我的紧急单（不在我负责楼栋）也能看到、也能走维修流程**，以便应急时不用先改配置
- 作为维修工，我希望**到场扫报修码完成打卡**，以便系统准确记录到场时间（响应时长的真实依据）

### 后勤管理端
- 作为后勤管理，我希望按类别或楼栋自动/手动派单，以便调度均衡
- 作为后勤管理，我希望看到超时工单并升级提醒，以便压住响应时长
- 作为后勤管理，我希望看到统计看板，以便考核与决策
- 作为后勤管理，我希望能直接问"上月 3 号楼报修最多的是什么"，以便不学 SQL 也能拿数据

## 4. 功能清单

### 必做（P0）

| 模块 | 功能点 |
|---|---|
| 账号与权限 | 三种角色账号密码登录（学号 / 工号）、RBAC 菜单与按钮权限、数据可见范围隔离 |
| 租户开通 | 平台运营开通学校（建租户 + 首个后勤管理员）、启停学校、给学校加管理员 / 重置其口令 |
| 工单全流程 | 提交（图片 / 位置 / 类别 / 紧急度）→ 派单 → 接单 → 处理中 → 上传结果 → 验收评价 → 关闭；三条分支：**驳回**（20/30/40，师傅或后勤）· **撤销**（学生，仅待派单）· **验收不通过**（40 → 30，打回重做）。规则见 §4.1 |
| 工单状态机 | 8 状态 + 合法跃迁校验，禁止跳状态；每次流转写 `ticket_log` 可追溯 |
| 报修码 | 房间门口张贴的位置码：学生扫码带出楼栋与房间，维修工扫码到场打卡；**两端共用同一个查询接口** |
| 文件与图片 | 现场图片、维修后图片上传（MinIO），类型与大小校验，返回可访问 URL |
| 超时提醒与升级 | 24h 未接单提醒调度方、48h 未处理升级（两者**基准都是 `dispatch_time`**，即「从派到完工」整体超期）；另有验收超时（已完成但长期未关闭）自动关闭 |
| **站内通知** | 工单状态变更时向相关方推送站内消息；**接收人按动作定，见 §4.3** |
| 统计看板 | 报修量趋势、类别分布、楼栋分布、平均响应 / 处理时长、超时率、满意度、师傅工作量 |
| AI 数据助手 | 自然语言 → **Schema 注入**（白名单表的表名 / 列名 / 注释全量进提示词；表少时不做向量检索）→ 生成 SQL → 执行 → 结果 + 图表 + 结论 |
| SQL 安全网关 | 只读账号、白名单、禁 DDL/DML、**强制租户范围**（网关在 AST 上注入，见 §7）、超时熔断、行数上限 |

### 建议做（P1）

工单转派与协同处理、操作审计日志、Excel 导出、压测报告。

### 明确不做

失物招领、活动报名、师傅排班、**短信 / 邮件通知、微信授权登录、微信订阅消息**、**自动派单**（只做手动派单：什么时候派给谁，是调度员的判断，系统只保证"派得到、被派的人看得到"）。

> **通知不是不做，是用站内通知代替**短信 / 邮件 / 订阅消息——零成本且跨端通用。
> **登录同理**，用**账号密码**（学号 / 工号）而不是微信授权登录，保证 H5 与小程序两端一致。

> **为什么要写"不做"**：把"不做"明确写出来，是在说明取舍标准——宁可把一条主线做深，也不铺五条平铺的 CRUD。以后想加功能时，先对照这一节判断它是否属于这条主线。

### 4.1 三条分支流转：驳回 / 撤销 / 验收不通过

主线是"提交 → 派单 → 接单 → 处理 → 验收 → 关闭"，但现实中一定会出现"这单不该我做""我报错了""修得不行"。这三条分支必须写清规则，否则验收时最容易吵——它们各自牵动三方的可见范围、通知与超时计时。

**驳回（`80 已驳回`）**

| 项 | 规则 |
|---|---|
| 谁能驳 | 维修工：只能驳**派给自己的**单（20 待接单 / 30 处理中）；后勤：可以驳 20 / 30 / 40 任意阶段 |
| 驳回必须写原因 | 原因进 `ticket_log`，并随通知一起发给相关方 |
| 驳回后 | `worker_id` **清空**（这单不再属于任何师傅）、该单的超时节点取消 |
| 驳回之后 | 后勤可以重新派单（`80 → 20`），**不限制派给谁**——包括刚驳回它的那位师傅。因为"留下驳回过这件事的痕迹"比"拉黑某个人"更有用：谁在第几节点驳回过、什么原因，`ticket_log` 里查得到，由调度员判断 |
| 为什么不直接回到待派单（10） | 回到 80 多留一条"被驳回过"的痕迹，且全程可追溯（`docs/02` §5） |

**撤销（`70 已撤单`）**

| 项 | 规则 |
|---|---|
| 谁能撤 | 只能是提交这单的学生本人 |
| 什么时候能撤 | **仅"待派单"阶段**（`10 → 70`）。一旦派单出去，学生自己撤不了——师傅可能已经在路上了，撤单要经后勤驳回 |
| 为什么这样定 | 派单之后撤单，等于让一次已经发生的调度凭空消失；让后勤介入（驳回 → 重新派/不派）比放开撤单更可控 |

**验收不通过（`40 → 30`，打回重做）**

学生验收时看到的是**实物结果**：修好了就是修好了，没修好也不该被逼着"打低分接受"。

| 项 | 规则 |
|---|---|
| 谁能做 | 只能是提交这单的学生本人 |
| 什么时候能 | 工单处于 40 待验收（验收通过走 `/evaluate`，不通过走 `/rework`，两条路都在这个状态上分叉） |
| 必须写理由 | 理由进 `ticket_log`（工单时间线上可见），并随通知发给维修工——不写理由等于让师傅猜 |
| 之后怎么走 | 工单回到 **30 处理中**，`worker_id` **保留**：还是这位师傅返工 |
| 与"驳回"的区别 | 驳回是"**这单不该我做**"，会清空派单、退回调度池；验收不通过是"**还是你做，但没做好**"，师傅不变。这也是状态机上必须多一条 `40 → 30` 的原因——借用驳回会让这一单丢失"谁在做"的信息 |
| 重新计时 | 打回时取消原节点并重新登记"未处理升级"（基准仍是 `dispatch_time`，口径不变：从派到完工整体超期） |
| 能来几次 | 不限次数（每次都有记录）。**处理时长按最后一次完工算**（`finish_time` / `handle_minutes` 会被第二次完工覆盖），因为统计口径关心的是"最终花了多久" |
| 与评价的关系 | 不写 `ticket_evaluation`：那张表只在验收通过时写。满意度统计的是"通过验收的单"。**低分与打回是两件事**：低分＝修完了但质量一般；打回＝没修好，重来 |

### 4.2 维修工的任务视图与可见范围

维修工的可见范围是**两层叠加**，不是二选一：

1. **我负责的楼栋**（`worker_building`，主要范围）——这栋楼里所有工单他都看得到，含别人负责的、含终态（便于现场沟通时知道"这栋楼在修什么"）；
2. **派给我的单**——即使不在他负责的楼栋（后勤临时抽调，见下），他也必须看得到**并且能走完整维修流程**（接单 / 到场 / 完工）。

> **为什么必须叠加第 2 层**：可见范围过去只按楼栋给，于是"跨楼栋派单"会造成一张**没有人能操作**的单——派单成功、师傅却看不到，只能等 24 小时未接单提醒才发现。可见范围与操作权必须一致。

维修工端首页给**两个视图**：

| 视图 | 内容 | 用途 |
|---|---|---|
| **我的任务**（默认） | 派给我的单，默认给出**进行中**（待接单 / 处理中 / 待验收） | 回答"我现在该干什么" |
| **本楼栋** | 我负责楼栋里的全部工单（含终态、含别人负责的） | 回答"这栋楼在修什么" |

**排序规则（两个视图都用）**：紧急度高的置顶（特急 → 紧急 → 普通）；同一紧急度内，**先来的排在前面**（先提交 / 先派单的先做），避免早报修的单被一直推到后面。

**紧急度的作用**（原先只在需求里出现一个字段，没定义行为，这里补齐）：

- 影响维修工任务列表的**排序**（置顶规则，见上）；
- 作为统计看板的一个**分布维度**；
- **不影响**超时阈值（阈值是全校统一的可配项，不按紧急度分档）。

**跨楼栋派单 = 紧急任务（强制派单）**

后勤可以把单派给不负责该楼栋的师傅，这属于**紧急抽调**，规则是：

- 服务端**允许**，但要在派单时明确告知（前端确认框："该师傅不负责 X 号楼，确认作为紧急任务强制派单？"），并在 `ticket_log` 里留下"跨楼栋强制派单"的痕迹；
- 被派的人按上面第 2 层可见范围，**看得到、走得完流程**；
- 不设"只有紧急单才能跨楼栋"的硬性校验：紧急度是调度员的判断，系统只保证越界这件事**被记录、被看到**，而不是替调度员决定。

### 4.3 通知的接收人（"相关方"具体是谁）

| 动作 | 接收人 | 文案 |
|---|---|---|
| 派单 | 维修工 | 新工单待接单：已派给你，请及时接单 |
| 接单 | 学生 | 维修工已接单，维修工会尽快到场 |
| 到场 | 学生 | 维修工已到场处理 |
| 完工上报 | 学生 | 维修已完成，请验收评价 |
| 验收评价 | 维修工 | 工单已验收 |
| 驳回 | 学生 **+ 当时的维修工** | 工单被驳回：原因 |
| 验收不通过 | 维修工 | 验收不通过：原因（请重新处理） |
| 撤销 | ——（学生自己撤的，不通知自己） | —— |
| 超时未接单提醒 | 后勤（本租户管理员） | 24h 未接单提醒 |
| 处理超时升级 | 后勤（本租户管理员） | 48h 未处理升级 |
| 验收超时自动关闭 | 学生 | 验收后超时未关闭，工单已自动关闭 |

> 驳回之所以要发给"当时的维修工"：他刚被派了这单又被后勤驳回，不通知他，他会一直以为这单还在自己手上（`worker_id` 已经被清空了）。

**验收评价是否强制**：**必须打分**（1–5 分），评价内容可选。没有"只验收不打分"的路径——满意度是看板的核心指标，允许空分会让它出现无法解释的缺口。

> 那"修得不满意"怎么办：**不用打分，直接走「验收不通过」打回重做**（见 §4.1）。低分与打回是两件事——**低分＝修完了但质量一般，打回＝没修好、重来**，所以两条路都要有。

## 5. 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | 提交报修 P99 < 500ms；工单列表 P99 < 300ms；统计看板 < 800ms |
| 并发 | 峰值 **100 QPS**（约 6000 单/分钟），持续 1 分钟成功率 ≥ 99.9%，M5 压测验证 |
| 安全 | SQL 注入防护；越权防护（RBAC + 数据权限双层）；AI 生成的 SQL 必须过安全网关；报修码随机生成、防枚举（**已实现**：接收报修码的接口按登录用户限流，超限 `10004`，见 ADR-009）；手机号、密码等敏感字段不入日志 |
| 可用性 | 单机部署，允许短暂不可用；关键路径有降级策略（见下） |
| 可维护性 | 统一返回体、全局异常、traceId 链路、Knife4j 文档、单元测试（状态机 / 幂等 / 数据权限） |

**为什么并发目标定 100 QPS**：一所 2 万人规模的学校，日工单量在数百量级，峰值集中在小时间（开学季、暴雨后）。100 QPS 相对真实流量有约 10 倍余量，是一个"够用且能被压测验证"的目标。单机部署（**当前演示机是 2C2G**，MySQL 同机）时，创建工单只有「工单主表 + 流转日志」两条 insert，配合合理的连接池和索引是可达的；**压测在目标规格的机器上跑**，不达标时先调连接池大小和事务范围，而不是加机器——这个规模下后者才是过度设计。

**降级策略**：

| 依赖不可用 | 降级行为 |
|---|---|
| Redis（延迟队列 / 限流计数） | 超时提醒 / 升级暂停，由每分钟一次的兜底扫描补漏；**报修码限流放行**（计数不可用时选择放行，宁可漏挡也不阻断扫码报修）；工单主流程不受影响 |
| AI 模型（DeepSeek） | 问数接口返回 `40004`，前端提示改用统计看板 |
| MinIO | 图片上传返回 `50003`；**文字描述仍可提交**（描述必填 ≤500 字、图片可选 ≤9 张，图片可后补） |

## 6. 里程碑

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| M1 | 工程骨架 + 三方账号与权限 | 三种角色登录后看到的菜单和数据不同 |
| M2 | 工单全流程 + 状态机 | 一个工单能从提交走到关闭，非法跃迁被拒 |
| M3 | 超时升级 + 统计看板 | 超时工单自动升级；看板有数 |
| M4 | AI 数据助手 + SQL 安全网关 | 能问"上月各楼栋报修量"并出图；越权查询被拦 |
| M5 | 部署上线 + CI/CD | 公网可访问，push 自动部署 |

## 7. 设计问答：这份文档能回答哪些问题

> 下面每一条都是**结论性的回答**；展开与追问应对见第 8 节。

- [x] **你为什么要做这个项目？**

  高校后勤报修的链路有三个断点：学生报修靠微信群，说不清位置和故障、图片传不明白；后勤靠纸笔或 Excel 登记、打电话派单，工单进度没人知道；月底统计靠手工汇总，回答不了"哪个楼报修最多、哪个师傅效率最低"。我把这条链路线上化成了一个工单 SaaS 平台。做成多租户是因为这个痛点不是某一所学校独有的，租户隔离后每所学校可以独立配置，方案可以复制。

- [x] **为什么设计成三方角色，而不是"管理员 + 用户"？**

  因为三方的**诉求和数据可见范围完全不同**：学生只关心自己那一单；维修工只关心派给自己的单、以及自己负责楼栋的工单（**两层叠加，不是二选一**，规则见 §4.2）；后勤要全局调度和统计。做成"管理员 + 用户"，管理员既要派单又要维修，职责混淆，权限也收敛不到一处。三方分角色后，数据可见范围天然产生差异——**这才是这个项目业务复杂度的来源，也是我数据权限设计的依据**。

- [x] **短信 / 邮件通知要不要做？**

  都不做，改做站内通知。短信要钱、要企业资质、模板要报备审核，个人很难走通；邮件本质就是一个 SMTP 调用，没有技术含量。站内通知零成本、跨端通用，而且有真实技术点：未读数、已读标记、推送方式选型。微信订阅消息只有小程序有，H5 用不了，会破坏跨端一致性，所以这一期也不做。

- [x] **你的数据权限是怎么设计的？**

  分三层说。**依据**：`worker_building` 关联表记录每个维修工负责哪些楼栋；学生用自己的 `student_id`；后勤不限制。**实现**：MyBatis 拦截器解析 SQL 的 AST，注入**两层**条件——**先按租户隔离**（`tenant_id = 当前登录者的租户`，后勤也不例外），**再按角色隔离**（学生 `student_id = 当前用户`、维修工 `building_id in (负责楼栋)`、后勤不再追加）。两层条件在同一个拦截器里，顺序即语义（见 ADR-008）。**为什么**：如果每条 SQL 手写 where，问题不是麻烦，是它会漏——漏一次就是一次越权漏洞，而且 code review 时肉眼很难发现；收敛到框架层后，权限逻辑只写一次，新增接口零成本获得保护，从"靠自觉"变成"默认安全"。

- [x] **AI 生成的 SQL 怎么保证不越权？**

  原则是**不信任模型输出**，安全不能写在 Prompt 里，因为 Prompt 约束不了模型行为。所以我做了一道独立的 SQL 安全网关，四层闸门：① 只读账号连接，防改数据、删表；② SQL 白名单只允许 `SELECT`，禁 DDL/DML/多语句，防结构破坏和多语句注入；③ **强制租户范围**，防越权读——这一层是只读账号做不到的；④ 超时熔断（>3s）+ 返回行数上限（>1000 行），防慢查询拖垮数据库。这套网关不依赖模型，可以单独写测试。

  > 第 ③ 层的实现要说明白：**不走 MyBatis 拦截器**。那个拦截器只覆盖 `ticket` / `notification` 两张表，而 AI 能查白名单里的任何一张，靠它 `SELECT * FROM building` 就会读到别家的楼栋。所以是网关自己在 SQL 的 AST 上给每张表注入 `tenant_id`（ADR-003「落地时的修正」）。

## 8. 展开说明（追问与展开）

### Q1 展开：痛点要具体到"能被验证"

"效率低"太笼统，无法判断是否真的理解了业务。把三条痛点说到"能想象出场景"的程度：

> 学生报修靠微信群，说不清位置和故障、图片也传不明白；后勤靠纸笔或 Excel 登记、打电话派单，工单进度没人知道；月底统计全靠手工汇总，回答不了"哪个楼报修最多、哪个师傅效率最低"。我做的是把这条链路线上化的 SaaS 工单平台。做成多租户，是因为这个痛点不是某一所学校独有，租户隔离后每校独立配置，可以复制。

### Q2 展开：角色划分要扣到数据权限上

⚠️ 不要用「通用场景」「维修工有多个」当理由——那不是理由，说明还没想清楚。

| 角色 | 关心什么 | 数据可见范围 |
|---|---|---|
| 学生 | 我这一单什么时候来修 | 只有自己提交的工单 |
| 维修工 | 今天要处理哪些单、在哪、什么毛病 | **派给自己的单 + 自己负责楼栋的工单**（两层叠加；默认视图只给「我的任务」，见 §4.2） |
| 后勤管理 | 全局调度是否均衡、谁超时了 | 全部（本租户） |

> 因为三方的**诉求和数据可见范围完全不同**：学生只关心自己那单，维修工只关心派给自己的单和自己负责的楼栋，后勤要全局。做成"管理员 + 用户"，管理员既要派单又要维修，职责混淆，权限也收敛不到一处。三方分角色后，数据可见范围天然产生差异——**这才是这个项目业务复杂度的来源，也是我数据权限设计的依据**。

关键：把"角色划分"直接接到"数据权限"上，一个问题带出下一个技术点。

### Q3 展开：通知通道的取舍

| 方案 | 做不做 | 理由 |
|---|---|---|
| 短信 | ❌ | 要钱、要企业资质、模板要报备审核，个人很难走通 |
| 邮件 | ❌ | 就是个 SMTP 调用，**没有技术含量** |
| 微信订阅消息 | ❌ | 只有小程序有，H5 没有，会破坏跨端一致性（将来上小程序可再加） |
| **站内通知** | ✅ | 零成本、跨端通用，有技术点：未读数、已读标记、推送方式选型 |

**登录同理**：用账号密码（学号 / 工号），不接微信授权登录——`wx.login` 只有小程序有，H5 没有，登录方式必须两端一致。

**站内通知怎么做**：一张 `notification` 表（接收人 / 类型 / 标题 / 内容 / 关联工单 / 是否已读 / 时间），工单状态变更时插一条，前端**轮询**拉取未读数。

**为什么轮询而不是 WebSocket**：单机部署、消息量级小（一个学校每分钟几条），轮询的实现和排障成本都更低；WebSocket 要额外处理心跳、断线重连、多实例广播，收益和成本不匹配。

> **取舍说明**：明确不做短信和邮件——短信有成本和资质门槛，个人做不划算；邮件是纯 API 调用，没有技术价值。改做站内通知，零成本，而且"为什么用轮询而不是 WebSocket"有明确理由。
>
> 把"不做什么、为什么不做"写清楚，比多做一个功能更能说明取舍标准。

### Q4 展开：数据权限的三层追问

⚠️「数据可见度范围隔离」只是结论。真正要能说清的是三层：**依据是什么、怎么实现、为什么这么做**。三层缺一，就只是背了个概念。

| 层 | 内容 |
|---|---|
| ① 依据 | `worker_building` 表记录维修工负责的楼栋；学生用 `student_id`；后勤不限 |
| ② 实现 | MyBatis 拦截器解析 SQL AST，**先按租户、再按角色**自动注入条件（ADR-008） |
| ③ 为什么 | 手写 where 的问题不是麻烦，**是它会漏**；漏一次就是越权漏洞，review 时很难发现。收敛到框架层后，权限只写一遍，新增接口默认安全 |

补充：多租户隔离（`tenant_id`）走同一层拦截器，并且在数据权限条件之前注入——**先按租户隔离，再按角色隔离**。

### Q5 展开：只读账号防不住越权

⚠️ **这里有个常见概念错误：只读账号防的是"改数据"，防不了"看别人的数据"。** 越权是**读**的问题，只读账号对此完全无效。

| 层 | 做什么 | 防住什么 |
|---|---|---|
| 1 | 只读账号连接 | 改数据 / 删表 |
| 2 | SQL 白名单（只允许 `SELECT`，禁 DDL / DML / 多语句） | 结构破坏、多语句注入 |
| 3 | **强制租户范围**（网关在 AST 上给每张表注入 `tenant_id`，不是走 MyBatis 拦截器） | **越权读** ← 只读账号做不到，靠这层 |
| 4 | 超时熔断（>3s）+ 返回行数上限（>1000 行） | 慢查询拖垮数据库 |

> **一句话总结**：我的原则是**不信任模型输出**。安全不能写在 Prompt 里，因为 Prompt 约束不了模型行为。所以我做了一道独立的 SQL 安全网关，四层校验，而且这套网关不依赖模型，可以单独写测试。

**第 3 层是最关键的一层**——它说明 AI 在这里是被当成工程问题处理的，而不是调个 API。
