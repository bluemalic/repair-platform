# 05 · 部署文档

> 对应《上手步骤》阶段 7。服务器上要做什么、怎么发布、出问题怎么查。

---

## 1. 部署架构

单机 Docker Compose，所有服务跑在同一台机器上：

```
                        Nginx (:8080 对外)
   ┌──────────────┬──────────────┬──────────────┬──────────────┐
   /              /h5/           /api/          /files/
管理端静态文件    学生端 H5     Spring Boot app   工单图片
                               :8080(容器内)         │
                                    │               │
              ┌─────────────────────┼───────────────┘
            MySQL 8              Redis 7           MinIO
          (仅内网 3306)        (仅内网 6379)      (仅内网 9000)
```

**只暴露 Nginx 的 8080**。MySQL、Redis、MinIO 都只绑 `127.0.0.1`，公网访问不到。

**图片为什么要走 `/files/`**：MinIO 不对公网开放，浏览器拿不到 `http://IP:9000/...`。应用按 `MINIO_PUBLIC_BASE_URL` 拼出图片 URL（`{该值}/{bucket}/{对象键}`），把它设成 `http://<域名或IP>:8080/files`，由 nginx 反代进容器网络。这样对外只有一个入口，不必把 S3 端口开出去——**这是"图片上传成功但打不开"最常见的原因**，`MINIO_PUBLIC_BASE_URL` 填了容器内网地址（`http://minio:9000`）就会出现这个症状。

## 2. 服务器初始化清单（一次性）

- [ ] 更新系统，时区设为 `Asia/Shanghai`
- [ ] 创建非 root 用户，配置 SSH 密钥登录，**禁用密码登录**
- [ ] 防火墙只放行：`22`、`8080`（以及备案前的临时调试端口）
- [ ] 安装 Docker 与 Docker Compose
- [ ] **加 2G swap**（2C2G 的机器必做，见 §2.2）
- [ ] **先腾资源**：同一台机器上已有的项目进它自己的目录 `docker compose down` 停掉
- [ ] 建目录：`/opt/app/repair`，下面放 `docker-compose.yml`、`nginx/`、`.env`、`data/`、`logs/`

### 2.1 为什么必须"先腾资源"

不是省内存那么客气——**端口是硬冲突，不停根本起不来**。以我们这台机器上原有的 `life-diary` 为例：

| 端口 | 旧项目占用 | 本项目要用 | 结果 |
|---|---|---|---|
| 8080 | 它的 web 前端 | nginx 对外入口 | 冲突 |
| 6379 | 它的 Redis | 我们的 Redis | 冲突（它绑的是 `0.0.0.0`，我们的 `127.0.0.1` 也绑不上） |
| 9000 / 9001 | 它的 MinIO | 我们的 MinIO | 冲突 |
| 3306 | 它的 MySQL | —— | 不冲突（我们用 13306） |

停掉之后**不要复用它的 MySQL / Redis**。共用实例会在版本、权限、端口、字符集上互相牵制，而且出问题时很难判断是谁改的。

> ⚠️ 顺带检查旧项目的端口暴露：如果它的 MySQL / Redis / MinIO 是 `0.0.0.0` 绑定且云防火墙放行了，那它们**在公网上是可直接连的**。无密码的 Redis 暴露在公网，扫描器几分钟内就会找上门。本项目这三个都只绑 `127.0.0.1`，公网只能看到 nginx 的 8080。

### 2.2 小内存机型（2 核 2G）

四个容器的内存上限默认加起来约 2.2G，再加系统本身，**2G 的机器不调必然 OOM**——而且症状很隐蔽：`docker compose ps` 只显示 MySQL「退出了」，看不出是内存不够（`docker inspect` 里的 `OOMKilled` 才是证据）。

**第一步，加 swap**（内存尖峰时靠换页活下来，而不是被直接杀掉）：

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab   # 开机自动挂载
free -h                                                       # Swap 那行应显示 2.0Gi
```

**第二步，在服务器的 `.env` 里启用"小内存机型"那一段**（`.env.example` 末尾，取消注释即可）：

```
MYSQL_MEM_LIMIT=512M
MYSQL_BUFFER_POOL=128M
MYSQL_PERFORMANCE_SCHEMA=OFF     # 诊断用的库，能省 100-200MB
REDIS_MEM_LIMIT=256M
REDIS_MAXMEMORY=128mb
MINIO_MEM_LIMIT=256M
APP_MEM_LIMIT=512M
JAVA_MAX_RAM_PERCENTAGE=55       # 512M × 55% ≈ 280M 堆，其余留给元空间与线程栈
```

**为什么 JVM 那条要单独调**：容器内存上限里，堆只占一部分，元空间、线程栈、直接内存加起来能到 200MB 以上。默认按上限的 70% 给堆，会出现"堆没满、容器先被 OOM killer 杀掉"这种最难查的重启。戴个安全帽的做法是**同时**限制容器上限和堆比例，让两者之间留出余量。

调完用 `docker stats --no-stream` 看实际占用，再决定要不要升级套餐。

> **压测**：这套 2C2G 口径下的性能目标与实测结论在 `docs/08-压测报告.md`（提交 / 列表 / 看板 / 混合四个场景）。
> 上线后想复跑一遍，生成器在本地跑、目标指向服务器即可——注意提交场景会真建工单（`docs/08` §6 有四条注意事项）。

## 3. 环境变量（`.env`）

服务器上的 `.env` **单独手动创建，不要走 Git**：

```bash
scp .env 用户名@服务器IP:/opt/app/repair/.env    # 或用编辑器直接建
```

内容参照 `.env.example`，但**密码必须换成强密码**（本地开发用的弱密码不能上生产）：

| 变量 | 说明 |
|---|---|
| `MYSQL_ROOT_PASSWORD` | 换强密码 |
| `REDIS_PASSWORD` | 换强密码 |
| `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` | 密码**至少 8 位**，否则容器反复重启 |
| `MINIO_PUBLIC_BASE_URL` | **服务器上必须改**：`http://<域名或IP>:8080/files`。填错的表现是"图片上传成功但打不开"，见 §1 |
| `NGINX_PORT` | 默认 8080；要在 80 端口直接对外就改成 80 |
| 内存上限那一组 | 2C2G 的机器照 §2.2 取消注释 |
| `AI_MODEL_API_KEY` | DeepSeek 的 Key |
| `AI_DB_USERNAME` / `AI_DB_PASSWORD` | AI 的**只读数据库账号**（ADR-003 第 1 层）。**由应用启动时自动创建并授权**，不用手工建；只授白名单那几张表的 SELECT，所以问数改不了数据、也读不到别的表。两个要么都填要么都不填 |
| `REPAIR_AI_RATE_LIMIT_MAX_REQUESTS` | **问数与 Agent 接口**（受理 / 分诊 / 维修建议）每分钟上限，默认 10。**它是花钱接口的成本上限**，三类接口共用这一档（花的都是模型的钱）。演示站**保持默认 10**（2026-10-17 定）：Agent 一轮对话就是 1~3 次请求，调到 3 会让演示到一半被 `10004` 打断；成本的硬上界交给 `REPAIR_AGENT_MAX_STEPS`（一轮最多问几次模型）与账号余额。要更保守就自己调小 |
| `REPAIR_AGENT_MAX_STEPS` | 受理 / 分诊 Agent 一轮最多问模型几次，默认 6。**另一道成本上限**；调小不影响正确性（信息没补齐会正常追问），只是更早收尾 |
| `REPAIR_DISPATCH_WEIGHT_SKILL` / `_SATISFACTION` / `_LOAD` / `_DISTANCE` | 派单评分的四项权重，默认 0.4 / 0.3 / 0.2 / 0.1（按和归一化）；`REPAIR_DISPATCH_LOAD_CAP`：负载封顶单数，默认 5（ADR-019） |
| `REPAIR_PLATFORM_BOOTSTRAP_USERNAME` / `REPAIR_PLATFORM_BOOTSTRAP_PASSWORD` | 平台运营账号的引导（可选，见 §4.3）。**两个都留空 = 不引导**，这是常态；只填一个会启动报错 |

> **运维端点**：应用暴露 `health / info / metrics / prometheus`，但 **nginx 只反代 `/actuator/health`**——
> `/actuator/prometheus` 只在容器网络与本机可达（指标文本会暴露内部结构，不对外；ADR-020）。
> 在服务器上看一眼：`curl -s http://127.0.0.1:8080/actuator/prometheus | grep repair_`（在 app 容器的网络命名空间里执行）。
>
> **业务指标的标签已收敛**：`repair.ticket.events{event,tenant}` 与 `repair.ai.calls{kind,result}`；
> 不要往标签里加工单号 / 用户 ID（高基数会撑爆时序库）。
>
> **域名还没备案时**，`MINIO_PUBLIC_BASE_URL` 先填 `http://<服务器IP>:8080/files`；备案下来换域名时**记得一起改这里**——图片 URL 是直接存进工单表的，改晚了老工单里的图还是旧地址。

> ⚠️ **MinIO 的镜像源换过两次，两次都是 MinIO 自己收紧分发**（Docker Hub 的 `minio/minio` → `quay.io/minio/minio` → 现在两个都拉不到，2026-09-25 起 quay.io 要认证、Docker Hub 上仓库已不存在）。
> 现在用的是 **Bitnami 的 legacy 镜像**（同一个 MinIO 二进制），标签钉死在 `2025.7.23-debian-12-r5`。
> 用法与官方镜像有两处不同，改 `docker-compose.yml` 时别踩：数据目录要用 `MINIO_DATA_DIR` 指定（默认不是挂载的那个目录），以及容器要 `user: root`（挂载目录属于 root）。
> **已经在跑的部署不用动**：容器用的是本地缓存里的旧镜像，照常运行；但如果哪天 `docker compose pull` 或重建容器，minio 这一步会失败——**换镜像前先备份一份**：
>
> ```bash
> docker save quay.io/minio/minio:latest | gzip > /opt/backup/minio-image.tar.gz   # 起不来时能回滚
> ```
>
> 换过去之后确认数据还在：`docker compose logs minio` 无异常 + 工单里的图片还能打开（数据在 `./data/minio` 挂载卷里，换镜像不影响它，前提是 `MINIO_DATA_DIR` 配对）。

> **新增配置只需要写进 `.env`**，不必再改 `docker-compose.yml`：app 服务用了 `env_file: .env`，整个文件都会传进容器（显式写的 `environment` 优先级更高，所以容器网络内的地址不会被 `.env` 覆盖）。
> 这条是踩过才补的——之前把演示模式的配置写进 `.env` 却没在 `environment` 里逐条列出，结果是"配置写了、应用读不到"，演示模式一直不生效，日志里连一行都没有。

## 4. 首次部署

> 下面的命令是 Bash 写法（服务器上是 Linux）。如果你在 **Windows 本地**构建后上传，PowerShell 5.x 不支持 `&&`——把 `&&` 换成 `;` 即可，例如 `cd web-admin; npm run build; cd ..`。

> ⚠️ **不要在生产库执行 `docs/dev-seed.sql`。** 那个脚本里的演示账号（`admin` / `worker01` / `20260001`，口令写在 README 里）只用于本地开发和演示。它**没有**挂在 MySQL 的 `docker-entrypoint-initdb.d` 上，所以生产库不会自动获得这些账号；只要你不在服务器上手动执行它，就不需要"上线时记得删"。

### 4.1 代码与产物怎么上去

**后端镜像在服务器上构建**（`docker compose up -d --build`），所以服务器需要源码；**前端产物在本地构建**后传上去——服务器上不装 Node，这也是 AGENTS §3.1 那条"后端构建不依赖前端"的落地方式。

```bash
# 1. 服务器：拉源码（私有仓库先配 deploy key）
git clone <仓库地址> /opt/app/repair
cd /opt/app/repair && cp .env.example .env && vi .env    # 按 §3 填，2C2G 记得取消注释小内存那段

# 2. 本地：构建前端产物（两个工程各自独立，产物路径不一样）
cd web-admin && npm run build && cd ..                   # 产物 dist/
cd miniapp-h5 && npm run build:h5 && cd ..               # 产物 dist/build/h5/（uni-app 约定）

# 3. 本地：把前端产物传上去（几 MB，很快）
scp -r web-admin/dist 用户名@IP:/opt/app/repair/web-admin/
scp -r miniapp-h5/dist/build/h5 用户名@IP:/opt/app/repair/miniapp-h5/dist/build/h5

# 4. 服务器：构建并启动
cd /opt/app/repair
docker compose up -d --build

# 5. 验证
docker compose ps                                   # 全部 running，mysql 是 healthy
docker logs repair-app | tail -50                   # 应用启动日志
curl -f http://localhost:8080/actuator/health       # 应返回 {"status":"UP"}
```

> **构建前先确认 `.env` 里有 `MAVEN_MIRROR`**（`.env.example` 里已给出阿里云地址）。**国内不填这个几乎必然构建失败**——实测不填时 `docker build` 会挂在一行看不出原因的报错上（`SSL peer shut down incorrectly` → `PluginResolutionException`），填上之后同一份 Dockerfile 构建成功。CI 在境外跑时不必填。
>
> **首次构建会慢**（Maven 要在容器里下依赖，这台机器是 2 核 2G）。**先把 §2.2 的 swap 加上**再构建，否则构建过程本身就可能把容器挤爆。构建产物有 Docker 层缓存，之后的重新部署不会重下依赖。
>
> 如果实在受不了这个速度，另一条路是在本地构建镜像后传上去：`docker save repair-app:latest | gzip > app.tar.gz` → `scp` → 服务器上 `gunzip -c app.tar.gz | docker load` → `docker compose up -d --no-build`。代价是每次要传约 90MB。

### 4.2 更新发布

```bash
cd /opt/app/repair
git pull
docker compose up -d --build app      # 只重建应用；前端产物按 4.1 的方式重新传
```

> ⚠️ **演示站重新构建前端时，必须带上 `VITE_DEMO_ACCOUNTS`**（命令见 §4.4）。它是**构建时**注入的，
> 而前端没有运行时配置——漏了它，登录页底部那行账号提示就没了，现象是"演示站能打开、但访客不知道该拿什么登录"，
> 而代码和构建都是成功的，从报错里看不出任何线索。**踩过一次**：一次普通的前端重建把这个提示弄丢过，
> 直到有人打开演示站才发现。判断方法：`grep -rl "演示账号" web-admin/dist/` —— 没有输出就是漏了。

配好镜像仓库后改走 §6 的 CI/CD，服务器就不必再构建了。

### 4.3 建第一个管理员账号（**空库必须做，否则登不进去**）

迁移脚本只建表结构和基础数据（租户 / 角色 / 权限点 / 楼栋 / 类别 / 报修码），**一个账号都不建**；账号在 `dev-seed.sql` 里，而那个脚本按设计不进生产库。所以部署完打开页面会停在登录页——**没有账号可以登**。

**推荐路径：先引导一个平台运营账号，再用它开学校 / 给学校加管理员。** 在服务器的 `.env` 里加两行，然后重启应用：

```
REPAIR_PLATFORM_BOOTSTRAP_USERNAME=platform
REPAIR_PLATFORM_BOOTSTRAP_PASSWORD=改成你自己的口令
```

```bash
docker compose up -d app          # 或 docker compose restart app
docker compose logs app | grep "平台运营账号"
```

看到「已引导创建平台运营账号 …（首次登录必须改密）」就成了。然后在管理端登录页点「平台运营登录」（学校编码固定是 `platform`），**首次登录会被强制改口令**；改完就能：

- **开通一所学校**：「租户管理 → 开通学校」，一次填完学校名称 / 编码和它的第一个后勤管理员
- **给种子租户 `gdou` 加一个管理员**（想直接用手册里的那所学校时走这条）：「租户管理 → 管理员 → 新增」

> **引导只建不改**：账号已存在就什么都不做——否则每次重启都会把改过的口令打回 `.env` 里的值，"首次登录必须改密"也白做。
> 所以**忘记平台口令时的恢复路径是"删掉这个账号 + 重启"**，不是改环境变量：
>
> ```sql
> -- 在服务器上：docker exec -it repair-mysql mysql -uroot -p repair
> DELETE FROM sys_user_role WHERE user_id IN (SELECT id FROM sys_user WHERE tenant_id = 0);
> DELETE FROM sys_user      WHERE tenant_id = 0;
> ```
>
> 重启后引导会把它按 `.env` 里的口令重建（**平台账号只能这样建**：没有任何接口能造出它）。
> 另外两个变量要么都填、要么都不填，只填一个会启动报错——静默跳过的话现象是"平台账号登不上"，要绕一圈才查到是配置没填全。

**最后手段：手工插库。** 平台账号自己也进不去、又不想删账号时（或者只想要一个后勤管理员、不需要平台账号），还是可以手写 SQL。先自己生成密码的 BCrypt 哈希——**别用网上现成的哈希生成器**，强度或前缀对不上就登不进去，而且报的是"用户名或密码错误"，看不出真正原因：

```bash
# 在本地执行（需要 JDK 17，且 Maven 依赖已下载过）
cat > /tmp/Hash.java <<'EOF'
import org.springframework.security.crypto.bcrypt.BCrypt;

public class Hash {
    public static void main(String[] args) {
        // 强度 10，与项目里 BCryptPasswordEncoder 的默认值一致
        System.out.println(BCrypt.hashpw(args[0], BCrypt.gensalt(10)));
    }
}
EOF
java -cp "$(ls ~/.m2/repository/org/springframework/security/spring-security-crypto/*/spring-security-crypto-*.jar | tail -1)" \
  /tmp/Hash.java '换成你自己的密码'
```

拿到 `$2a$10$...` 之后，在服务器上执行：

```bash
docker exec -it repair-mysql mysql -uroot -p repair
```

```sql
-- 后勤管理员（user_type=3，role_id=3）。id 显式给：雪花 ID 是应用生成的，手工插库时自己定一个
INSERT INTO sys_user (id, tenant_id, username, password, real_name, phone, user_type, status)
VALUES (1, 1, 'admin', '粘贴刚生成的哈希', '后勤管理员', NULL, 3, 1);

-- 角色关联也必须插：只有用户没有角色，登录后权限码为空，每个接口都会 403
INSERT INTO sys_user_role (id, user_id, role_id) VALUES (1, 1, 3);
```

```sql
-- 平台运营账号（user_type=4，role_id=4，**tenant_id 固定为 0**）。这三处错一个的现象都是"用户名或密码错误"
INSERT INTO sys_user (id, tenant_id, username, password, real_name, phone, user_type, status)
VALUES (2, 0, 'platform', '粘贴刚生成的哈希', '平台管理员', NULL, 4, 1);
INSERT INTO sys_user_role (id, user_id, role_id) VALUES (2, 2, 4);
```

登录时「学校编码」填 `gdou`（迁移脚本种子里的租户，`tenant.code`），账号 `admin`；平台账号的学校编码固定填 `platform`。

> **为什么 id 手写 1、2 而不让数据库自增**：本项目主键是雪花 ID、由应用生成，没有自增。手工插的这几行只要不与应用生成的 ID 撞上就行，1、2、3 这种小数字天然安全。
>
> **后续账号都走管理端建，不用再手写 SQL**：维修工在「基础数据 → 维修工管理」，学生在「基础数据 → 学生管理」（支持粘贴学号名单批量导入），后勤管理员由平台运营在「租户管理」里加。
> 学生账号的初始口令是统一的，**首次登录会被强制要求改密**——这条在服务端也拦着（未改密时只放行 `/api/auth/**`），不只是前端的跳转引导。
> 平台运营建出来的管理员同样带这个标记。

### 4.4 演示部署（可选）：让站点每天自动恢复原样

**要解决的问题**：演示站是公开的，口令就写在登录页上，任何人进去都能改数据。放任几天，楼栋会被删、工单列表会被垃圾数据塞满，HR 或面试官点开看到的是一片狼藉。靠人记得去重置是不可靠的，所以做成自动的。

在服务器的 `.env` 里加：

```
REPAIR_DEMO_ENABLED=true
REPAIR_DEMO_PASSWORD=<演示口令，启用时必填>
REPAIR_DEMO_RESET_CRON=0 0 4 * * *
```

**重置会做这几件事**（只动 `REPAIR_DEMO_TENANT_ID` 指定的租户，默认 1）：

| 动作 | 说明 |
|---|---|
| 清空工单 / 流转日志 / 评价 / 通知 | **物理删除**，不是逻辑删除——每天逻辑删一遍会让表一天比一天大，旧行还占着 `uk_ticket_no` |
| 重建 5 个演示账号 | admin（后勤）、worker01 / worker02（维修工）、20260001 / 20260002（学生），并**把口令改回配置里的值** |
| 重建 12 条示例工单 | 覆盖 8 种状态，已结束的往前铺到一周，让统计看板的趋势图有起伏 |
| 补建被删掉的**类别** | 只补不删：已有的不动，缺的按名字建回来 |
| 楼栋 | **只在「该租户一栋楼都没有」时**才建演示楼栋，已有的一律复用。曾经是「按名字补建」，结果访客每改一次楼栋名就多出一栋同名的（详见 `docs/07` §5.6） |
| 清空对象存储里该租户的图片 | 工单都重建了，旧图没有引用方，留着纯占磁盘 |

**触发时机有两个**：每天凌晨（可配），以及**应用启动时**。后者有两个用处——刚开启演示模式时不用等到凌晨才有数据；演示站被玩坏了 `docker compose restart app` 就能恢复。

> ⚠️ **生产部署不要打开这个开关**：它会删掉该租户的全部工单。默认是关的，且关着时定时任务这个 Bean 根本不会被装配。

**登录页的账号提示也是配套的**，但它是**构建时**注入的（前端没有运行时配置）。构建演示版前端时加一个环境变量：

```bash
cd web-admin && VITE_DEMO_ACCOUNTS="演示账号：admin，口令 Repair@2026" npm run build && cd ..
cd miniapp-h5 && VITE_DEMO_ACCOUNTS="演示账号：worker01 / 20260001，口令 Repair@2026" npm run build:h5 && cd ..
```

不注入就没有那一行提示——**两种部署共用同一份代码**，不靠改代码区分。

> 实测确认：`VITE_*` 走 shell 环境变量在 Vite 与 uni-app 两边都能注入；不设变量时产物里搜不到提示文字。

**演示站上的平台运营账号：故意不写进登录页提示。** 登录页上写出来的账号等于公开的账号，而平台运营账号能开通学校——访客随手开几十所垃圾学校，而**每天的重置只清理 `REPAIR_DEMO_TENANT_ID` 那一个租户**（默认 1），多出来的租户会一直留在库里。
想让人看到"多租户"这一面，正确做法是**你自己登录平台账号现场演示**（或在面试时说明），而不是把那个入口挂到登录页上。
真要挂上去，得先让演示重置把"非种子租户"也一起清掉——那是一件独立的事，别只加一行 `VITE_DEMO_ACCOUNTS` 就以为安全了。

**顺手把上传也收紧**：图片上传走的是 `@RateLimit`（按登录用户计，默认 60 次/分钟），演示站上把它调小即可，不用改代码：

```
REPAIR_RATE_LIMIT_MAX_REQUESTS=10
```

配合每天清理对象存储，磁盘被刷爆的风险就基本封住了。

### 4.5 AI 问数上线清单（M4）

AI 是**唯一会花钱**的功能，所以按这份清单逐条过，不要"先上去看看"。

1. **`.env` 里填三组变量，缺一组就是"用不了"**：

   | 变量 | 漏了它的表现 |
   |---|---|
   | `AI_MODEL_API_KEY` | 问数回 `40004`（日志里是"未启用"） |
   | `AI_DB_USERNAME` / `AI_DB_PASSWORD` | 同上，日志会说清是只读账号没配；**两个要么都填要么都不填**，只填一个启动就报错 |
   | `REPAIR_AI_RATE_LIMIT_MAX_REQUESTS` | 默认 10 次/分钟。演示站**保持默认**（理由见 §3 的环境变量表：Agent 一轮对话 1~3 次请求，调太小会打断演示） |

2. **重建 app 容器**（只读账号由应用启动时自动创建并授权，不用手工建）：

   ```bash
   sudo docker compose up -d --no-deps --build app
   sudo docker logs repair-app | grep 只读数据库账号
   # 预期：只读数据库账号已就绪 username=repair_ai database=repair 授权表数=7
   ```

3. **验一条真问数**（先拿一个后勤管理员的 token，再问一次）：

   ```bash
   TOKEN=$(curl -s -X POST http://127.0.0.1:8080/api/auth/login \
     -H "Content-Type: application/json" \
     -d '{"tenantCode":"<学校编码>","username":"<管理员账号>","password":"<口令>"}' \
     | grep -o '"tokenValue":"[^"]*"' | cut -d'"' -f4)
   curl -s -X POST http://127.0.0.1:8080/api/ai/query \
     -H "Content-Type: application/json" -H "Authorization: Bearer $TOKEN" \
     -d '{"question":"各楼栋各有多少工单"}' | head -c 400
   # 预期：code=0，data.sql 里能看到 tenant_id = <本租户> 与 deleted = 0
   ```

4. **验流式**（它走 nginx 上单独一个 location，`proxy_buffering off` 已经配好；
   **少了那一行，SSE 会退化成"等十几秒一次性返回"**，功能不算坏，但界面上的分阶段提示就没了）：

   ```bash
   curl -N -s "http://127.0.0.1:8080/api/ai/query/stream?question=%E5%90%84%E6%A5%BC%E6%A0%8B%E7%9A%84%E6%8A%A5%E4%BF%AE%E9%87%8F" \
     -H "Authorization: Bearer <token>"
   # 预期：先 event:sql，再 event:data，最后 event:done —— 三条**分几次**到达，不是一口气全来
   ```

   也可以直接用页面：管理端 → AI 问数 → 点一个示例问题，应当看到"正在理解问题 → 正在取数 → 正在总结"
   依次出现，SQL 折叠块在 1~2 秒内就能展开。

5. **出问题先看错误码**（`docs/03` §3 有完整触发场景）：

   | 现象 | 大概率原因 |
   |---|---|
   | `40004` | Key 没配 / 只读账号没配 / 模型接口不通（日志里有一行 WARN 说清是哪种） |
   | `40002` | 安全网关拦下了模型生成的 SQL——**这是防线在工作**，文案会说清是哪一条 |
   | `40003` | 单条 SQL 超过 3 秒（阈值 `REPAIR_AI_QUERY_TIMEOUT_MS` 可调） |
   | `40001` | 问题没能变成可执行的查询（换个说法再问） |
   | 页面一直转圈、最后"连接中断" | nginx 那个 location 的 `proxy_buffering` 没关，或 `proxy_read_timeout` 小于 120s |

6. **准确率不是"感觉还行"**：改动 AI 模块（换模型、改提示词、加规则）之后重跑一遍 20 问评测集
   （`docs/07`，手动、要花钱），把新数字写回那张表。

### ⚠️ 四个必须知道的坑

**手工写 SQL 插中文时，务必带上字符集参数。** 这个容器里 `mysql` **命令行客户端**的默认 `character_set_client` 是 **latin1**（实测），中文会被逐字节当成 latin1 再转存，每个中文变成两个乱码字符（`1号楼` 存成 `1å\x8f·æ¼`）——**而且不报错、看起来像成功了**。所以任何手工 SQL 都要带参数：

```bash
sudo docker exec -i repair-mysql mysql --default-character-set=utf8mb4 -uroot -p"$MP" repair -e "…"
```

> 建表与基础数据已经不走这条路了（改由 Flyway 走 JDBC 执行，字符集由连接串保证，**这个坑从路径上消失**）。但"手工插一条中文记录"仍然要用上面的写法。

**手工执行 SQL 时，别用 shell 去读 `.env` 里的口令。** `MYSQL_ROOT_PASSWORD` 写在 `.env` 里，但 `grep | cut` 读出来的值**不一定等于 compose 实际传给容器的值**——compose 解析 `.env` 时会处理引号、把 `#` 之后当注释，而原样读取会把引号/注释一起当成口令。**实测踩过**：用 `grep` 读出来的口令连不上（`Access denied`），而应用连得好好的，因为它拿的是 compose 解析后的值。现象很有误导性——看起来像"密码记错了"，其实错在读法。

所以要么让**容器用它自己的环境变量**（不管值里有什么字符都对）：

```bash
sudo docker exec -i repair-mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" --default-character-set=utf8mb4 repair -e "…"'
```

要么直接 `docker exec -it repair-mysql mysql -uroot -p` 交互式输入——但**别把 `.env` 里的引号也输进去**（引号是 `.env` 的语法，不是口令的一部分）。

**建表和迁移失败会让应用起不来（这是有意的）。** 迁移在应用启动时执行，失败就启动失败、日志里有明确报错——这比"打一行 ERROR 继续跑、容器照样显示 healthy"好得多，后者会留下"库是坏的但服务是绿的"这种最难查的状态。所以**每次部署后仍要验一次表和数据**，不能只看健康状态。

**`docker compose down -v` 删不掉 bind mount 的数据。** 我们的数据落在 `./data/` 目录，是宿主机目录挂载。要重建库必须手动删：

```bash
docker compose down && rm -rf data/mysql && docker compose up -d mysql
```

> **本地 Windows（PowerShell）注意**：PowerShell 5.x 不支持 `&&`，`rm -rf` 也不是它的参数写法。等价命令是：
>
> ```powershell
> docker compose down; Remove-Item -Recurse -Force data\mysql; docker compose up -d mysql
> ```
>
> （PowerShell 7+ 支持 `&&`，但 `Remove-Item -Recurse -Force` 仍要替掉 `rm -rf`。）

## 5. 数据库迁移（Flyway）

表结构不靠手工 ALTER，也不靠"首次启动执行一次建表脚本"——它由 **Flyway 迁移脚本**管理，应用启动时自动执行。执行真相在 `src/main/resources/db/migration/`：

| 脚本 | 内容 |
|---|---|
| `V1__baseline.sql` | 建表（14 张表）。**基线**：把一个空库建成现在这个样子 |
| `V2__*.sql`、`V3__*.sql` … | 之后每次表结构变更各加一个，**只增不改** |
| `R__seed.sql` | 基础数据（租户 / 角色 / 权限点 / 楼栋 / 类别 / 报修码）。可重复迁移：**脚本内容一变就重跑**，所以内部必须幂等 |

改表结构的正确姿势：**加一个 V 号脚本 + 改 `docs/02-数据库设计.md`**（见 AGENTS §6）；新增权限码只改 `R__seed.sql`。为什么这么选见 ADR-010。

### 5.1 空库（全新部署、CI）——不用做任何事

启动时 Flyway 会建表、再跑一遍种子：

```
All configured schemas are empty; baseline operation skipped.
Migrating schema `repair` to version "1 - baseline"
Migrating schema `repair` with repeatable migration "seed"
Successfully applied 2 migrations to schema `repair`, now at version v1
```

### 5.2 已有的库（首次接管）——**先核对，再启动**

`baseline-on-migrate` 会把"有表但没有迁移历史"的库直接标记成"V1 已应用"，**它不会去检查那些表是不是真的和 V1 一致**。所以首次接管前必须核对一次，否则结构差异会被静默跳过、等到某个 V 脚本执行时才以奇怪的方式失败。

```bash
cd /opt/app/repair
MP=$(grep '^MYSQL_ROOT_PASSWORD=' .env | cut -d= -f2- | tr -d '
')
sudo docker exec -i repair-mysql mysql --default-character-set=utf8mb4 -uroot -p"$MP" repair -e "
SELECT table_name, column_name, column_type, is_nullable, column_default
FROM information_schema.columns WHERE table_schema = 'repair'
ORDER BY table_name, ordinal_position;"
```

把输出与 `V1__baseline.sql` 逐表对比（表数、每张表的列名与类型）。**一致** → 直接部署；**不一致** → 先把差异补齐再部署，不要靠调 `baseline-version` 绕过去（那只会把差异掩盖到更晚才爆）。

核对通过后，新版本首次启动会看到：

```
Schema history table `repair`.`flyway_schema_history` does not exist yet
Creating Schema History table `repair`.`flyway_schema_history` with baseline ...
Successfully baselined schema with version: 1
Migrating schema `repair` with repeatable migration "seed"
```

之后每次部署只执行"没跑过的 V 脚本"，比如只加了一列就是一行 `Migrating ... to version "2 - ..."`。

### 5.3 迁移失败了怎么办

**MySQL 下迁移失败会留下一条 `success = 0` 的记录，之后每次启动都会报"检测到失败的迁移"而拒绝启动。** 恢复步骤：

```bash
# 1) 先看日志里失败的语句，把改动手工补齐或回退
# 2) 删掉失败记录（这是 flyway repair 的手工等价操作）
sudo docker exec -i repair-mysql mysql --default-character-set=utf8mb4 -uroot -p"$MP" repair -e "
DELETE FROM flyway_schema_history WHERE success = 0;
SELECT installed_rank, version, description, success FROM flyway_schema_history;"
# 3) 重新启动应用，它会再跑一次那个脚本
```

> **迁移脚本一经执行就不能再改**——改了校验和会被判定为不一致。要改只能新增一个脚本，这条约束在协作时必须说清楚，否则新人很容易直接去改 V1。

### 5.4 每个学校一个库（阶段 6 · ADR-021）

**开通一所学校 = 建一个 database**（`repair_<学校编码>`，如 `repair_gdou`）：它自己的账号、角色、
业务表、审计都在里面。平台库 `repair` 只剩学校名录（`tenant`，**只有这里有**）与平台账号，
外加过渡期里还没搬家的存量租户的数据。库名规则与命名冲突的处理见 `TenantSchemas`。

| 什么时候跑迁移 | 用哪一套脚本 | 说明 |
|---|---|---|
| 应用启动（平台库） | `db/migration`（V…） | 与以前一样，§5.1~§5.2 的说明继续适用 |
| **开通学校时** | `db/tenant`（T…） | 建库 + 建表 + 灌平台种子（角色 / 权限），幂等，可重跑 |
| **每次应用启动** | `db/tenant`（T…） | 对每个已有租户库跑一遍：补上没跑过的版本脚本；**可重复脚本内容变了就重跑**，所以平台新增权限码会在下次启动时同步到所有学校。某个学校的库坏了只记 ERROR、**不影响其它学校也不阻断启动**——那所学校自己的请求会响亮地报错 |

**连接预算（2C2G 单机要算这笔账）**：平台库主池 12 条；每个租户池 **3 条**（懒建、`min-idle = 0`、
空闲 10 分钟归还）；AI 只读池每库 2 条。10 所学校稳态约 `12 + 10×3 + 10×2 = 62` 条连接，
MySQL 默认 `max_connections = 151`，留有余量。参数在 `repair.tenancy.*`（默认值写在
`TenancyProperties` 上，可用环境变量 `REPAIR_TENANCY_POOL_SIZE` 等覆盖）。

**逐租户运维**（这正是做这个改造的目的）：

```bash
# 这所学校的数据在哪、有多大
sudo docker exec -i repair-mysql mysql -uroot -p"$MP" -e "
SELECT id, code, db_schema FROM repair.tenant WHERE db_schema IS NOT NULL;
SELECT table_schema, ROUND(SUM(data_length + index_length) / 1024 / 1024, 1) AS mb
FROM information_schema.tables WHERE table_schema LIKE 'repair\_%' GROUP BY table_schema;"

# 单独备份 / 导出 / 迁走一所学校（不碰别人）
sudo docker exec -i repair-mysql mysqldump -uroot -p"$MP" --single-transaction repair_gdou | gzip > gdou.sql.gz
```

**把一所学校搬到它自己的库（搬迁工具，阶段 6 第 2 步）**

```bash
# 平台 token（浏览器里登录平台账号，F12 拿 Authorization 里的那段即可）
T="Bearer <平台 token>"; ID=<租户ID>

# ① 看现状：数据在哪、目标库建好没、逐表是否一致（一致性的比对是 O(行数)，两个库各扫一遍）
curl -s -H "Authorization: $T" http://127.0.0.1:8080/api/platform/tenants/$ID/database

# ② 搬家（可在学校正常使用时做；幂等，跑几次都行）
curl -s -X POST -H "Authorization: $T" http://127.0.0.1:8080/api/platform/tenants/$ID/database/copy

# ③ 挑个没人用的时刻切换（几秒钟；期间该校请求会被拒并提示稍后重试）
curl -s -X POST -H "Authorization: $T" http://127.0.0.1:8080/api/platform/tenants/$ID/database/switch
```

**操作要点（都是这套设计里刻意留下的边界，不是操作失误的余地）**：

- **②③ 之间不要隔太久**：切换前会再校验一次，源库在这段时间里又被写过就会拒绝切换，重跑 ② 即可；
- **源库那份保留**（ADR-021：确认无误再归档）。所以回退 = 把 `tenant.db_schema` 改回 `NULL` 并重启应用
  （目录缓存按租户存着，重启最省事），代价是**丢掉切换之后写进新库的数据**——回退窗口到学校真正开始使用为止；
- 要重做一次搬迁（比如目标库结构是旧的）：把 `db_schema` 改回 `NULL`，再 ② ③ 各来一次；
- 搬迁只读源库、只写目标库，**并发跑同一所学校的多次搬家没有互斥保护**（单人运维场景，不做额外的锁）。

**当前边界（第 1 步与第 2 步做到的与没做到的，写清楚免得被当成故障）**：

1. **存量租户照旧**：`db_schema` 为空的学校（含演示学校 gdou）行为与改动前完全一致，数据仍在平台库。
   搬迁工具（上面那三步）已就绪；**还没做的是"把 gdou 切过去"**——因为第 3 步的定时任务改造没做完（见第 2 条）。
2. **定时任务还没覆盖独立库**：超时自动升级与兜底扫描目前只扫平台库，所以**新开通的学校**
   暂时没有"超时自动升级 / 自动关闭"。开通成功时日志里会打一行 WARN 指明这件事（第 3 步覆盖）。
3. **每租户一个数据库账号**（第二道防线）没做：现在所有库都用应用账号，隔离靠"路由 + `tenant_id`"，
   靠的是**报错**而不是权限不足——推迟的理由（凭据保管与轮换）见 ADR-021 的落地修正。
4. `CREATE DATABASE` 要求应用账号有建库权限：**当前部署的应用账号是 root，满足**；
   将来换成受限账号时要显式授予建库权限，并把范围限定在 `repair\_%`。

### 6.1 工作流干什么（四个 job、两条独立的链）

| job | 做什么 | 依赖 |
|:---|:---|:---|
| `verify` | 跑 `mvn -B clean package`（**含 JaCoCo 覆盖率门槛**） | —— |
| `deploy-app` | 下载 CI 打好的 jar → scp 上传（约 60-80MB）→ 服务器用 `Dockerfile.deploy` **组装**镜像（只 COPY，几秒）→ 重启 → 健康检查，**失败自动回滚** | verify |
| `frontend` | 构建管理端与 H5 产物（注入 `VITE_DEMO_ACCOUNTS`）并打包 | —— |
| `deploy-frontend` | 上传产物 → 解包到 nginx 挂载目录 → **断言"演示账号"提示在两个产物里** | frontend |
| `deploy-frontend` | 上传产物 → 解包到 nginx 挂载目录 → **断言"演示账号"提示在产物里** | frontend |

**后端与前端分成两条链是刻意的**（AGENTS §3.1 第 4 条的延续）：前端构建失败不该拦住后端发布，
反过来也一样。两条链唯一的共同前提是 SSH 通。

几个设计点，都是"出错时才知道重要"的地方：

- **`verify` 在最前面**：这是"自动测试 + 自动上线"里的前半句。测试红、或覆盖率掉到门槛以下，
  就上不了线——而不是先上线再发现。
- **拉取前先记回滚点**：`docker compose pull` 会把 `latest` 覆盖成新版，等健康检查失败时已经
  没有可回退的目标了。所以部署脚本第一步就把"当前正在跑的镜像"标成 `:previous`；失败时把它
  复位并重启（服务器本地就有，不涉及拉取，秒级）。
- **推两个标签**：`latest` 给 compose 用，`<sha>` 给回滚用。只推 `latest` 的话"回滚"就只剩
  重新构建一条路，那在故障时是最慢的。
- **前端产物用 grep 当验收**：`grep -rq "演示账号" web-admin/dist/` —— 这是唯一一处
  "构建成功、页面也能打开、但站点就是不对"的失败模式，光看退出码发现不了。

---

**触发方式**：推 `main` **自动部署**，也可以在 Actions 页面手动触发（CD → Run workflow）。

- **纯文档改动不触发**：`paths-ignore` 列了 `docs/**`、`**.md`、`LICENSE`、两个 dockerignore、
  `.env.example` 与另外三个 workflow——部署会重启 app 容器（几秒访问中断），而文档不影响运行
- **故意不排除 `deploy.yml` 自己**：改了流水线就顺带跑一次，正好验证它没被改坏
- 有 `concurrency` 串行（`cancel-in-progress: false`）：连着两次合并会让两个部署交叉执行（都在改同一份
  源码、重启同一个容器），串行最稳；不用 `true` 是因为"中断一次改到一半的部署"比"多等几分钟"危险
- **改代码的合并会真的重启容器**——这是"推 main 就上线"的固有代价，不是缺陷

### 6.2 三件前置（① ③ 已完成；② 仓库已建，只差把 2 个凭据填进 Secret）
#### ① 给 `ubuntu` 装一把部署公钥 —— **已完成**

> **当初的判断是错的，复盘留在这里**：文档曾写"SSH 挂着腾讯云的「安全登录」，自动化进不去，
> 要先去控制台关掉那道保护"。实测下来这条站不住，**那个开关从头到尾不需要动**：
>
> - 那串微信二维码是 **SSH 的 banner**（腾讯云给自己打的广告位），**不影响认证**，公钥照样能用
> - 真正的失败原因是两个，都与开关无关：**用了 `root`**（Ubuntu 镜像的默认登录名是 `ubuntu`，
>   控制台「VNC 登录」卡片上就写着）、以及**还没装公钥**
> - 我当时的测试带了 `BatchMode=yes`（本意是不让它卡在密码提示上），于是"无公钥 + 不许提示密码"
>   合起来表现为 `Permission denied (publickey,password,keyboard-interactive)`，**看起来像被拦住了**
>
> **可迁移的教训**：看到"连不上"，先分清是**认证被拒**还是**根本没提供凭据**。
> 前者要改服务器，后者改自己就行——我把后者误判成了前者，白绕了两轮。

装的时候走的是控制台的**「执行命令」**（TAT，无需 SSH 就能在实例上执行），一条命令装好：

```bash
mkdir -p /home/ubuntu/.ssh
echo '<CI 用的公钥>' >> /home/ubuntu/.ssh/authorized_keys
sort -u /home/ubuntu/.ssh/authorized_keys -o /home/ubuntu/.ssh/authorized_keys
chmod 700 /home/ubuntu/.ssh && chmod 600 /home/ubuntu/.ssh/authorized_keys
chown -R ubuntu:ubuntu /home/ubuntu/.ssh
```

`sort -u` 是为了幂等——重复粘同一把公钥不会让 `authorized_keys` 越堆越长。

装完在**本机**验一次（这一步不能省：本地不通的通道配到 CI 里只会变成一个挂住不动的 job）：

```bash
ssh -i <私钥路径> -o BatchMode=yes -o ConnectTimeout=10 ubuntu@119.91.47.63 'echo SSH_OK; whoami'
# 期望输出：SSH_OK 与 ubuntu
```

顺手在服务器上确认过（这些是后面的前提）：`PubkeyAuthentication` 走 OpenSSH 默认值（开）、
`PermitRootLogin yes`、`PasswordAuthentication yes`、Docker 29.6 + Compose v5.3、
以及 `/opt/app/repair` 属主是 `ubuntu` 且**可写**——最后一条不成立的话，部署会在写产物那一步失败，
而报错看着像"上传失败"，很容易误判成网络问题。

#### ② 镜像仓库 —— **建好了，但实测后放弃这条路**

TCR 个人版的命名空间 `bluemalic-repair` 与访问凭证都建好了，四个 `REGISTRY_*` Secret 也配了，
流水线里的 `docker login` **是成功的**——放弃与凭据无关，是网络方向的问题（§6.3）。

顺带留一条经验：**TCR 个人版的命名空间建在"默认共享实例"上，名字在所有腾讯云账号之间全局唯一**。
`repair` 这种通用词早被注册了，得带辨识度（这里用的是 `bluemalic-repair`）。
要真正隔离的私有仓库得上企业版（付费）。

#### ③ 服务器 `.env` 的 `IMAGE_NAME` —— **已改为由流水线自己维护，不需要手工改**

原先这里写的是"手动把 `.env` 里的 `IMAGE_NAME` 改成仓库路径"。推敲之后改成**由部署脚本管那一行**，
因为手动改存在一个**会挂站点的顺序陷阱**：

> 一旦 `.env` 里的 `IMAGE_NAME` 指向仓库，compose 就认为 app 服务变了。此时如果镜像还没拉到本地，
> 任何一次 `docker compose up -d` 都会**先删掉旧容器、再卡在"镜像拉不到"上**——中间那段就是站点空窗。
> 而"先拉镜像、再改 `.env`"这个顺序，靠人记迟早会记反。

所以脚本里的顺序是固定的：**记回滚点 → 按完整镜像路径 `docker pull` → 幂等改 `.env` 那一行 → `up -d`**。
改 `.env` 用 `sed -i` 只动这一行（文件里还有数据库口令等，CI 不碰别的），没有这一行时追加；
改完把那行回显到 CI 日志，便于事后核对。这也顺带解开了首次启用的"先有鸡还是先有蛋"：
按完整路径拉不需要 `.env` 已经正确。

仍然需要人工确认的是**小内存机型的取值**（`MYSQL_MEM_LIMIT` / `APP_MEM_LIMIT` / `REDIS_MAXMEMORY`，
见 §2.2）——起容器本身也要占内存，这几个值不对会在部署之后以 `OOMKilled` 的形式暴露出来，
而 `docker compose ps` 只显示"退出了"，看不出是内存不够。

### 6.3 为什么后端不在 CI 里构建镜像 —— **跨境推镜像实测 0.3 Mbps**

> 这是本次唯一一处"按计划做完、被实测推翻"的决策。数据留在这里，**免得将来有人又想改回去**。

原设计是 CI 构建镜像 → 推 TCR → 服务器拉取。第一次真跑，卡在"构建并推送镜像"这一步
**51 分钟没完**；取消之后从日志里拿到证据：

```
#22 pushing layer 2dc9e195c9e2 114.97MB / 141.61MB 3129.0s
#22 pushing layer 4c599f782540  58.46MB /  90.48MB 3126.8s
```

一层 141MB 推了 52 分钟才到 115MB，算下来约 **0.3 Mbps**；这两层共 232MB 还要再跑一个多小时。

**关键是方向性——慢的是"往境内推"，不是"从境内拉"：**

| 方向 | 实测 | 依据 |
|:---|:---|:---|
| 服务器**拉**镜像 | **约 11 Mbps** | `docker pull eclipse-temurin:17-jre-jammy`（约 230MB）耗时 2 分 49 秒 |
| GitHub runner **往境内推** | **约 0.3 Mbps** | 上面那两行 buildx 日志，差 30 多倍 |

所以正确的做法是让**大流量的那一段留在境内**：

| 环节 | 跨境流量 | 走哪条路 |
|:---|:---|:---|
| 源码包（排除 `data` / `logs` / `.env` / `node_modules` / `dist`） | 几 MB | CI → 服务器 scp |
| 前端产物 | 几 MB | CI → 服务器 scp |
| 构建镜像 | **0** | **服务器本地** `docker compose build`：依赖走 `.env` 里的 `MAVEN_MIRROR`（境内源）、复用 Docker 层缓存 |

代价是服务器要跑一次 Maven——这正是你们一直手工在做的事，只是现在自动化了。
`pom.xml` 不变时依赖不会重新下载（层缓存命中）。

**一个要留意的细节**：服务器拉基础镜像（`maven:3.9-eclipse-temurin-17` / `eclipse-temurin:17-jre-jammy`）
走的是它的 Docker Hub 镜像站 `docker.m.daocloud.io`，而那个镜像站的 **referrers 接口会 502**
（OCI 查 SBOM / 签名用的接口，实测过：层全部 Pull complete 之后命令仍以非零退出）。
变通办法很简单：**基础镜像先在服务器上 `docker pull` 一次**，之后构建就只是层缓存命中，
不依赖那个接口。真正升级基础镜像时才需要再手动拉一次。

### 6.4 后端的交付方式：三轮迭代，两次被实测推翻

这块设计前后换了三次。**每次都是"按计划做完、真跑一次、被数据推翻"**，证据按顺序留在这里，
免得将来有人凭直觉改回去：

| 轮次 | 做法 | 实测结果 | 结论 |
|:---|:---|:---|:---|
| 一 | CI 构建镜像 → 推 TCR → 服务器拉 | 跨境推 **0.3 Mbps**：一层 141MB 推 52 分钟只到 115MB | ✗ 弃 |
| 二 | 传源码 → 服务器 `docker compose build` | 服务器缺 `maven` 基础镜像（500MB），而镜像站拉大镜像**间歇性 502**，两次都失败；且 2C2G 跑 Maven 有 OOM 风险 | ✗ 弃 |
| 三（当前） | CI 里 `mvn` 打好的 jar（`verify` 本来就要跑）→ scp（约 60-80MB）→ 服务器用 `Dockerfile.deploy` **只做 COPY** | —— | ✓ 用 |

第三轮的好处：不依赖那个反复 502 的基础镜像、不在 2C2G 上跑 Maven、部署从几分钟变成几秒。
**代价是多了一个 `Dockerfile.deploy`**——它的运行阶段必须与 `Dockerfile` 保持一致，两边都写了提示。
将来若 CI 换成**境内**的 runner，可以切回第一轮：那是服务器最省事的做法。

顺带记三个在这几轮里踩到的坑，都属于"看起来无关、实际会打断部署"的类型：

1. **`tar -czf x.tar.gz ... .` 把归档写进被归档的目录**：tar 读到自己正在长大，报
   `file changed as we read it` 并以 1 退出（部署因此失败）。归档要写在目录之外，或加 `--exclude`。
2. **`if: failure()` 的回滚步骤对"任何上游失败"都成立**：如果失败发生在部署之前，它找不到回滚点，
3. **清源码树时连带删掉了 bind mount 的父目录**：`web-admin` / `miniapp-h5` 里有挂给 nginx 的
   `dist` 目录，整体删目录会让容器握着失效的 inode（现象是**全站 403**）；更麻烦的是
   **容器一旦重启，Docker 会以 root 身份重建不存在的挂载源**，之后部署用户再也写不进去，
   恢复要靠一个临时容器去 `chown`。结论：**清源码只清 `src`**（唯一会被编译的目录），
   前端产物**只清内容、不删目录**。两次事故（10-15 与 10-16）都是同一个道理的两面。

   却报出一个像模像样的错误，把日志搅浑。正确姿势是把"没有回滚点"当成**无事可做**（`exit 0`），
   因为那不是回滚失败，而是容器根本没被动过。

### 7.1 Redis 淘汰策略：既是防线，也是探针

`docker-compose.yml` 里写死了 `--maxmemory-policy volatile-lru`，**不要改回 `allkeys-lru`**
（理由与验证方式见 `docs/04` ADR-016）。它顺带兼职一个内存探针：

```bash
docker exec repair-redis redis-cli -a <密码> CONFIG GET maxmemory-policy    # 期望 volatile-lru
docker exec repair-redis redis-cli -a <密码> INFO stats | grep evicted_keys  # 非 0 = 内存已经不够
docker exec repair-redis redis-cli -a <密码> INFO memory | grep used_memory_human
docker exec repair-redis redis-cli -a <密码> DBSIZE
```

**症状：用户"莫名其妙被登出"。** 原因：内存压到上限后，会话键（有 TTL）被淘汰。
修法：`evicted_keys` 是不是非 0 → 是就升机器规格或调大 `REDIS_MAXMEMORY`（同时按 §2.2 调
容器内存上限）。**不要靠"把策略改回 `allkeys-lru`"来治**——那会让超时队列（唯一没有 TTL 的键）
变成可淘汰对象，症状变成"一批工单再也不会超时提醒 / 自动关闭，而且全程没有报错"，比登出难查得多。

### 7.2 容器镜像对齐（**已于 2026-10-16 完成**）

> 这一节以前是「⚠️ 别裸跑 `docker compose up -d`」，因为当时**声明态与运行态不一致**：
> compose 写的是 `redis:7-alpine` 与 Bitnami minio，实际跑的是 `redis-stack-server:7.2`（750MB）
> 与 `quay.io/minio`。现在两边已对齐，那个隐患（裸跑 compose 会试图切换容器、而 minio 新镜像
> 本地没有 → 拉不到就起不来 → **工单图片全挂**）随之消失。

对齐过程与两个值得记下来的发现：

| 步 | 动作 | 验收 |
|:---|:---|:---|
| 1 | 先确认新镜像拿得到 | `redis:7-alpine` 本地已有；`bitnamilegacy/minio:2025.7.23-debian-12-r5` **本地没有，要单独拉**（拉成功） |
| 2 | 换 minio（`up -d --no-deps minio`） | **换之前先记一张真实图片的 URL**：换完同一张图仍 200、新上传也 200 → 数据与桶策略都没问题 |
| 3 | 换 redis（`up -d --no-deps redis`） | 站点 200、登录成功、`CONFIG GET maxmemory-policy` = **volatile-lru** ✓（ADR-016 的保护在生产生效，`maxmemory` 为小机型取值 128MB） |

**发现一：换 redis 镜像会重置整个数据集，不只是清掉会话。** 换完之后 AOF 是**新建**的
（base 文件只有 88 字节），旧键空间没有带过来——两个镜像的 AOF 目录属主与运行用户不同，
新容器的持久化目录被重新创建了。

- **为什么可以接受**：业务数据在 MySQL（未受影响）；超时队列丢了有**每分钟兜底扫库**接管
  （ADR-001 的那道防线就是为这类情况准备的）；限流计数与登录去重键本来就是短命的；会话被清是预期内的。
- **但要知道**：换的那一瞬间排在 ZSet 里的超时任务会丢，**别在有大量在途工单的时候换**。
- **换完必须验业务**：站点接口 + 登录 + `GET /api/student/tickets`（确认数据完好），
  而不是只看"容器起来了"。

**发现二：验收要挑能证明端到端的手段。** minio 那次用的是"换之前先取一张真实图片的 URL，换完再取一次"，
而不是"容器起来了"——只有前者能同时证明数据、桶策略、nginx 反代这条链路是通的。

> 附：旧镜像还留在本地（`redis-stack-server` 750MB + `quay.io/minio` 241MB）作为回退选项。
> 观察几天没问题后可以 `docker rmi` 清掉，约省 1GB。

## 9. 访问方式（备案相关）

| 方式 | 说明 |
|---|---|
| **IP + 端口** | `http://服务器IP:8080`。**未备案也能用**——备案管的是"域名指向境内服务器"，直接用 IP + 非 80 端口不涉及。适合备案审核期间先上线 |
| 域名 + HTTPS | 需 ICP 备案。备案通过后配 Nginx + Let's Encrypt 证书 |

**为什么最终要上 HTTPS**（这条以前写错过，特此改掉）：不只是"小程序才要求"——

- **H5 的摄像头扫码只在 HTTPS 或 localhost 下可用**（浏览器的 `getUserMedia` 限制）。公网 IP 不算 localhost，所以在 `http://IP:8080` 上点"扫二维码"只会看到"请用手输"的提示，功能是好的但展示不出来
- 登录密码在 HTTP 下是明文过网的
- 浏览器会给 HTTP 站点标"不安全"

**顺序建议**：先用 IP 上线（一天都不用等），同时提交备案；备案通过后再改 `MINIO_PUBLIC_BASE_URL` 加域名、配证书，切过去。切换时**别漏了 `MINIO_PUBLIC_BASE_URL`**（见 §3）。
