# 05 · 部署文档

> 对应《上手步骤》阶段 7。服务器上要做什么、怎么发布、出问题怎么查。

---

## 1. 部署架构

单机 Docker Compose，所有服务跑在同一台机器上：

```
                        Nginx (:8080 对外)
   ┌──────────────┬──────────────┬──────────────┬──────────────┐
   /              /h5/           /api/          /files/
管理端静态文件    学生端 H5     Spring Boot app   工单图片
                               :8080(容器内)         │
                                    │               │
              ┌─────────────────────┼───────────────┘
            MySQL 8              Redis 7           MinIO
          (仅内网 3306)        (仅内网 6379)      (仅内网 9000)
```

**只暴露 Nginx 的 8080**。MySQL、Redis、MinIO 都只绑 `127.0.0.1`，公网访问不到。

**图片为什么要走 `/files/`**：MinIO 不对公网开放，浏览器拿不到 `http://IP:9000/...`。应用按 `MINIO_PUBLIC_BASE_URL` 拼出图片 URL（`{该值}/{bucket}/{对象键}`），把它设成 `http://<域名或IP>:8080/files`，由 nginx 反代进容器网络。这样对外只有一个入口，不必把 S3 端口开出去——**这是"图片上传成功但打不开"最常见的原因**，`MINIO_PUBLIC_BASE_URL` 填了容器内网地址（`http://minio:9000`）就会出现这个症状。

## 2. 服务器初始化清单（一次性）

- [ ] 更新系统，时区设为 `Asia/Shanghai`
- [ ] 创建非 root 用户，配置 SSH 密钥登录，**禁用密码登录**
- [ ] 防火墙只放行：`22`、`8080`（以及备案前的临时调试端口）
- [ ] 安装 Docker 与 Docker Compose
- [ ] **加 2G swap**（2C2G 的机器必做，见 §2.2）
- [ ] **先腾资源**：同一台机器上已有的项目进它自己的目录 `docker compose down` 停掉
- [ ] 建目录：`/opt/app/repair`，下面放 `docker-compose.yml`、`nginx/`、`.env`、`data/`、`logs/`

### 2.1 为什么必须"先腾资源"

不是省内存那么客气——**端口是硬冲突，不停根本起不来**。以我们这台机器上原有的 `life-diary` 为例：

| 端口 | 旧项目占用 | 本项目要用 | 结果 |
|---|---|---|---|
| 8080 | 它的 web 前端 | nginx 对外入口 | 冲突 |
| 6379 | 它的 Redis | 我们的 Redis | 冲突（它绑的是 `0.0.0.0`，我们的 `127.0.0.1` 也绑不上） |
| 9000 / 9001 | 它的 MinIO | 我们的 MinIO | 冲突 |
| 3306 | 它的 MySQL | —— | 不冲突（我们用 13306） |

停掉之后**不要复用它的 MySQL / Redis**。共用实例会在版本、权限、端口、字符集上互相牵制，而且出问题时很难判断是谁改的。

> ⚠️ 顺带检查旧项目的端口暴露：如果它的 MySQL / Redis / MinIO 是 `0.0.0.0` 绑定且云防火墙放行了，那它们**在公网上是可直接连的**。无密码的 Redis 暴露在公网，扫描器几分钟内就会找上门。本项目这三个都只绑 `127.0.0.1`，公网只能看到 nginx 的 8080。

### 2.2 小内存机型（2 核 2G）

四个容器的内存上限默认加起来约 2.2G，再加系统本身，**2G 的机器不调必然 OOM**——而且症状很隐蔽：`docker compose ps` 只显示 MySQL「退出了」，看不出是内存不够（`docker inspect` 里的 `OOMKilled` 才是证据）。

**第一步，加 swap**（内存尖峰时靠换页活下来，而不是被直接杀掉）：

```bash
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab   # 开机自动挂载
free -h                                                       # Swap 那行应显示 2.0Gi
```

**第二步，在服务器的 `.env` 里启用"小内存机型"那一段**（`.env.example` 末尾，取消注释即可）：

```
MYSQL_MEM_LIMIT=512M
MYSQL_BUFFER_POOL=128M
MYSQL_PERFORMANCE_SCHEMA=OFF     # 诊断用的库，能省 100-200MB
REDIS_MEM_LIMIT=256M
REDIS_MAXMEMORY=128mb
MINIO_MEM_LIMIT=256M
APP_MEM_LIMIT=512M
JAVA_MAX_RAM_PERCENTAGE=55       # 512M × 55% ≈ 280M 堆，其余留给元空间与线程栈
```

**为什么 JVM 那条要单独调**：容器内存上限里，堆只占一部分，元空间、线程栈、直接内存加起来能到 200MB 以上。默认按上限的 70% 给堆，会出现"堆没满、容器先被 OOM killer 杀掉"这种最难查的重启。戴个安全帽的做法是**同时**限制容器上限和堆比例，让两者之间留出余量。

调完用 `docker stats --no-stream` 看实际占用，再决定要不要升级套餐。

## 3. 环境变量（`.env`）

服务器上的 `.env` **单独手动创建，不要走 Git**：

```bash
scp .env 用户名@服务器IP:/opt/app/repair/.env    # 或用编辑器直接建
```

内容参照 `.env.example`，但**密码必须换成强密码**（本地开发用的弱密码不能上生产）：

| 变量 | 说明 |
|---|---|
| `MYSQL_ROOT_PASSWORD` | 换强密码 |
| `REDIS_PASSWORD` | 换强密码 |
| `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` | 密码**至少 8 位**，否则容器反复重启 |
| `MINIO_PUBLIC_BASE_URL` | **服务器上必须改**：`http://<域名或IP>:8080/files`。填错的表现是"图片上传成功但打不开"，见 §1 |
| `NGINX_PORT` | 默认 8080；要在 80 端口直接对外就改成 80 |
| 内存上限那一组 | 2C2G 的机器照 §2.2 取消注释 |
| `AI_MODEL_API_KEY` | DeepSeek 的 Key |

> **域名还没备案时**，`MINIO_PUBLIC_BASE_URL` 先填 `http://<服务器IP>:8080/files`；备案下来换域名时**记得一起改这里**——图片 URL 是直接存进工单表的，改晚了老工单里的图还是旧地址。

> **新增配置只需要写进 `.env`**，不必再改 `docker-compose.yml`：app 服务用了 `env_file: .env`，整个文件都会传进容器（显式写的 `environment` 优先级更高，所以容器网络内的地址不会被 `.env` 覆盖）。
> 这条是踩过才补的——之前把演示模式的配置写进 `.env` 却没在 `environment` 里逐条列出，结果是"配置写了、应用读不到"，演示模式一直不生效，日志里连一行都没有。

## 4. 首次部署

> 下面的命令是 Bash 写法（服务器上是 Linux）。如果你在 **Windows 本地**构建后上传，PowerShell 5.x 不支持 `&&`——把 `&&` 换成 `;` 即可，例如 `cd web-admin; npm run build; cd ..`。

> ⚠️ **不要在生产库执行 `docs/dev-seed.sql`。** 那个脚本里的演示账号（`admin` / `worker01` / `20260001`，口令写在 README 里）只用于本地开发和演示。它**没有**挂在 MySQL 的 `docker-entrypoint-initdb.d` 上，所以生产库不会自动获得这些账号；只要你不在服务器上手动执行它，就不需要"上线时记得删"。

### 4.1 代码与产物怎么上去

**后端镜像在服务器上构建**（`docker compose up -d --build`），所以服务器需要源码；**前端产物在本地构建**后传上去——服务器上不装 Node，这也是 AGENTS §3.1 那条"后端构建不依赖前端"的落地方式。

```bash
# 1. 服务器：拉源码（私有仓库先配 deploy key）
git clone <仓库地址> /opt/app/repair
cd /opt/app/repair && cp .env.example .env && vi .env    # 按 §3 填，2C2G 记得取消注释小内存那段

# 2. 本地：构建前端产物（两个工程各自独立，产物路径不一样）
cd web-admin && npm run build && cd ..                   # 产物 dist/
cd miniapp-h5 && npm run build:h5 && cd ..               # 产物 dist/build/h5/（uni-app 约定）

# 3. 本地：把前端产物传上去（几 MB，很快）
scp -r web-admin/dist 用户名@IP:/opt/app/repair/web-admin/
scp -r miniapp-h5/dist/build/h5 用户名@IP:/opt/app/repair/miniapp-h5/dist/build/h5

# 4. 服务器：构建并启动
cd /opt/app/repair
docker compose up -d --build

# 5. 验证
docker compose ps                                   # 全部 running，mysql 是 healthy
docker logs repair-app | tail -50                   # 应用启动日志
curl -f http://localhost:8080/actuator/health       # 应返回 {"status":"UP"}
```

> **构建前先确认 `.env` 里有 `MAVEN_MIRROR`**（`.env.example` 里已给出阿里云地址）。**国内不填这个几乎必然构建失败**——实测不填时 `docker build` 会挂在一行看不出原因的报错上（`SSL peer shut down incorrectly` → `PluginResolutionException`），填上之后同一份 Dockerfile 构建成功。CI 在境外跑时不必填。
>
> **首次构建会慢**（Maven 要在容器里下依赖，这台机器是 2 核 2G）。**先把 §2.2 的 swap 加上**再构建，否则构建过程本身就可能把容器挤爆。构建产物有 Docker 层缓存，之后的重新部署不会重下依赖。
>
> 如果实在受不了这个速度，另一条路是在本地构建镜像后传上去：`docker save repair-app:latest | gzip > app.tar.gz` → `scp` → 服务器上 `gunzip -c app.tar.gz | docker load` → `docker compose up -d --no-build`。代价是每次要传约 90MB。

### 4.2 更新发布

```bash
cd /opt/app/repair
git pull
docker compose up -d --build app      # 只重建应用；前端产物按 4.1 的方式重新传
```

配好镜像仓库后改走 §5 的 CI/CD，服务器就不必再构建了。

### 4.3 建第一个后勤管理员账号（**空库必须做，否则登不进去**）

`schema.sql` 只建表结构和基础数据（租户 / 角色 / 权限点 / 楼栋 / 类别 / 报修码），**一个账号都不建**；账号在 `dev-seed.sql` 里，而那个脚本按设计不进生产库。所以部署完打开页面会停在登录页——**没有账号可以登**。

先自己生成密码的 BCrypt 哈希。**别用网上现成的哈希生成器**，强度或前缀对不上就登不进去，而且报的是"用户名或密码错误"，看不出真正原因：

```bash
# 在本地执行（需要 JDK 17，且 Maven 依赖已下载过）
cat > /tmp/Hash.java <<'EOF'
import org.springframework.security.crypto.bcrypt.BCrypt;

public class Hash {
    public static void main(String[] args) {
        // 强度 10，与项目里 BCryptPasswordEncoder 的默认值一致
        System.out.println(BCrypt.hashpw(args[0], BCrypt.gensalt(10)));
    }
}
EOF
java -cp "$(ls ~/.m2/repository/org/springframework/security/spring-security-crypto/*/spring-security-crypto-*.jar | tail -1)" \
  /tmp/Hash.java '换成你自己的密码'
```

拿到 `$2a$10$...` 之后，在服务器上执行：

```bash
docker exec -it repair-mysql mysql -uroot -p repair
```

```sql
-- 后勤管理员（user_type=3）。id 显式给：雪花 ID 是应用生成的，手工插库时自己定一个
INSERT INTO sys_user (id, tenant_id, username, password, real_name, phone, user_type, status)
VALUES (1, 1, 'admin', '粘贴刚生成的哈希', '后勤管理员', NULL, 3, 1);

-- 角色关联也必须插：只有用户没有角色，登录后权限码为空，每个接口都会 403
INSERT INTO sys_user_role (id, user_id, role_id) VALUES (1, 1, 3);
```

登录时「学校编码」填 `gdou`（`schema.sql` 里的种子租户，`tenant.code`），账号 `admin`。

> **为什么 id 手写 1 而不让数据库自增**：本项目主键是雪花 ID、由应用生成，没有自增。手工插的这几行只要不与应用生成的 ID 撞上就行，1、2、3 这种小数字天然安全。
>
> **后续的维修工账号走管理端接口建**（`POST /api/admin/workers`），不用再手写 SQL；学生账号的管理入口还没做，见 `docs/00` 的待办。

### 4.4 演示部署（可选）：让站点每天自动恢复原样

**要解决的问题**：演示站是公开的，口令就写在登录页上，任何人进去都能改数据。放任几天，楼栋会被删、工单列表会被垃圾数据塞满，HR 或面试官点开看到的是一片狼藉。靠人记得去重置是不可靠的，所以做成自动的。

在服务器的 `.env` 里加：

```
REPAIR_DEMO_ENABLED=true
REPAIR_DEMO_PASSWORD=<演示口令，启用时必填>
REPAIR_DEMO_RESET_CRON=0 0 4 * * *
```

**重置会做这几件事**（只动 `REPAIR_DEMO_TENANT_ID` 指定的租户，默认 1）：

| 动作 | 说明 |
|---|---|
| 清空工单 / 流转日志 / 评价 / 通知 | **物理删除**，不是逻辑删除——每天逻辑删一遍会让表一天比一天大，旧行还占着 `uk_ticket_no` |
| 重建 5 个演示账号 | admin（后勤）、worker01 / worker02（维修工）、20260001 / 20260002（学生），并**把口令改回配置里的值** |
| 重建 12 条示例工单 | 覆盖 8 种状态，已结束的往前铺到一周，让统计看板的趋势图有起伏 |
| 补建被删掉的楼栋 / 类别 | 只补不删：已有的不动，缺的按名字建回来 |
| 清空对象存储里该租户的图片 | 工单都重建了，旧图没有引用方，留着纯占磁盘 |

**触发时机有两个**：每天凌晨（可配），以及**应用启动时**。后者有两个用处——刚开启演示模式时不用等到凌晨才有数据；演示站被玩坏了 `docker compose restart app` 就能恢复。

> ⚠️ **生产部署不要打开这个开关**：它会删掉该租户的全部工单。默认是关的，且关着时定时任务这个 Bean 根本不会被装配。

**登录页的账号提示也是配套的**，但它是**构建时**注入的（前端没有运行时配置）。构建演示版前端时加一个环境变量：

```bash
cd web-admin && VITE_DEMO_ACCOUNTS="演示账号：admin，口令 Repair@2026" npm run build && cd ..
cd miniapp-h5 && VITE_DEMO_ACCOUNTS="演示账号：worker01 / 20260001，口令 Repair@2026" npm run build:h5 && cd ..
```

不注入就没有那一行提示——**两种部署共用同一份代码**，不靠改代码区分。

> 实测确认：`VITE_*` 走 shell 环境变量在 Vite 与 uni-app 两边都能注入；不设变量时产物里搜不到提示文字。

**顺手把上传也收紧**：图片上传走的是 `@RateLimit`（按登录用户计，默认 60 次/分钟），演示站上把它调小即可，不用改代码：

```
REPAIR_RATE_LIMIT_MAX_REQUESTS=10
```

配合每天清理对象存储，磁盘被刷爆的风险就基本封住了。

### ⚠️ 三个必须知道的坑


**建表脚本必须显式指定字符集，否则中文全部写坏。** 这个容器里 `mysql` 客户端的默认 `character_set_client` 是 **latin1**（实测），而 `docs/schema.sql` 是 UTF-8。如果让 entrypoint 直接执行 `.sql` 文件，文件里的中文字节会被逐字节当成 latin1 解释后再转成 UTF-8 存进库——每个中文变成两个乱码字符（`1号楼` 存成 `1å\x8f·æ¥¼`），**而且不报错、看起来像灌成功了**。

所以 compose 里把脚本挂在 `/opt/repair-schema.sql`，由 `docs/initdb/01-load-schema.sh` 用 `--default-character-set=utf8mb4` 导入。那个脚本导入后会顺手打一行楼栋名的 HEX 做校验（`E6B5B7` 开头的 `海` 说明正常）。**手写 SQL 插中文时也要带这个参数**：

```bash
sudo docker exec -i repair-mysql mysql --default-character-set=utf8mb4 -uroot -p"$MP" repair -e "…"
```

**初始化脚本报错会让容器起不来（这是有意的）。** `01-load-schema.sh` 里写了 `set -e`：导入失败时整个 entrypoint 以非零退出、容器起不来、日志里有明确报错。这比 MySQL 默认的行为好——默认只在日志里打一行 ERROR 就继续了，容器照样显示 healthy，于是"库是坏的但服务是绿的"。所以**每次重建库后仍要验一次中文**，不能只看健康状态。

**`docker compose down -v` 删不掉 bind mount 的数据。** 我们的数据落在 `./data/` 目录，是宿主机目录挂载。要重建库必须手动删：

```bash
docker compose down && rm -rf data/mysql && docker compose up -d mysql
```

> **本地 Windows（PowerShell）注意**：PowerShell 5.x 不支持 `&&`，`rm -rf` 也不是它的参数写法。等价命令是：
>
> ```powershell
> docker compose down; Remove-Item -Recurse -Force data\mysql; docker compose up -d mysql
> ```
>
> （PowerShell 7+ 支持 `&&`，但 `Remove-Item -Recurse -Force` 仍要替掉 `rm -rf`。）

## 5. 更新发布（CI/CD）

配好 GitHub Secrets 后，推 `main` 就会自动走 `deploy.yml`：构建镜像 → 推镜像仓库 → SSH 到服务器拉取重启。

需要配置的 Secrets（仓库 `Settings → Secrets and variables → Actions`）：

| Secret | 说明 |
|---|---|
| `REGISTRY_URL` | 镜像仓库地址，如 `registry.cn-shenzhen.aliyuncs.com` |
| `REGISTRY_NAMESPACE` | 命名空间 |
| `REGISTRY_USERNAME` / `REGISTRY_PASSWORD` | 镜像仓库凭据 |
| `SERVER_HOST` | 服务器 IP |
| `SERVER_USER` | SSH 用户（非 root） |
| `SERVER_SSH_KEY` | SSH 私钥 |

手动发布（不走 CI）：

```bash
cd /opt/app/repair
docker compose pull app && docker compose up -d --no-deps app
```

## 6. 常用排查命令

```bash
docker compose ps                              # 服务状态
docker compose logs -f app                     # 实时看应用日志
docker logs repair-mysql | grep -i error       # MySQL 初始化报错
docker stats --no-stream                       # 各容器内存占用（小机器最容易爆这个）
docker exec -it repair-mysql mysql -uroot -p   # 进 MySQL 命令行
docker exec -it repair-redis redis-cli -a <密码>
```

**远程调试**（线上问题不加日志就能断点排查）：

```bash
# 服务器上启动应用时临时加 JVM 参数
-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005
```

本地 IDEA 加一个 **Remote JVM Debug** 配置连过去即可。

> ⚠️ **调试完立刻关闭 5005 端口。** 开放的远程调试端口等同于开放代码执行能力，生产环境绝不能常开。

## 8. 访问方式（备案相关）

| 方式 | 说明 |
|---|---|
| **IP + 端口** | `http://服务器IP:8080`。**未备案也能用**——备案管的是"域名指向境内服务器"，直接用 IP + 非 80 端口不涉及。适合备案审核期间先上线 |
| 域名 + HTTPS | 需 ICP 备案。备案通过后配 Nginx + Let's Encrypt 证书 |

**为什么最终要上 HTTPS**（这条以前写错过，特此改掉）：不只是"小程序才要求"——

- **H5 的摄像头扫码只在 HTTPS 或 localhost 下可用**（浏览器的 `getUserMedia` 限制）。公网 IP 不算 localhost，所以在 `http://IP:8080` 上点"扫二维码"只会看到"请用手输"的提示，功能是好的但展示不出来
- 登录密码在 HTTP 下是明文过网的
- 浏览器会给 HTTP 站点标"不安全"

**顺序建议**：先用 IP 上线（一天都不用等），同时提交备案；备案通过后再改 `MINIO_PUBLIC_BASE_URL` 加域名、配证书，切过去。切换时**别漏了 `MINIO_PUBLIC_BASE_URL`**（见 §3）。
