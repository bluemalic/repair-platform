# 08 · 压测报告（2C2G 口径）

> 这份报告回答一个问题：**`docs/01` §5 那几条性能目标，到底达不达标。**
> 复现命令、口径、样本数都在文里；发现的问题在 §4（缺索引、看板的逐行探测、师傅端「本楼栋」没有时间窗口），
> 它们是这份报告真正的产出。

## 1. 结论（对照 `docs/01` §5）

| 场景 | 目标 | 结果（多轮样本） | 判定 |
|---|---|---|---|
| 提交报修（写） | 100 QPS、P99 < 500ms、成功率 ≥ 99.9% | **99.7 QPS**，P99 **133ms**，成功率 **100%** | ✅ |
| 管理端工单列表（读） | P99 < 300ms | **99.7 ~ 99.8 QPS**，P99 **82 / 88 / 86ms**（三轮），100% | ✅ |
| 统计看板（读） | P99 < 800ms | **89.5 ~ 95.2 QPS**，P99 **507 / 543 / 585ms**（三轮），100% | ⚠️ P99 达标，**速率差 5~10%** |
| 混合（提交 10% / 列表 60% / 看板 30%） | 100 QPS | **99.9 QPS**，P99 **153ms**，100% | ✅ |
| 师傅端「我的任务」（读，§4.4 补测） | P99 < 300ms | **99.8 QPS**，P50 36ms · P99 **51ms**，100% | ✅ |
| 师傅端「本楼栋」（读，§4.4 补测） | P99 < 300ms | **63.8 QPS**，P50 584ms · P99 **760ms**，100% | ❌ **本来就超标**（对照 510/678ms，与本轮改动无关，§4.4） |
| 系统余量（混合） | —— | **约 150 QPS**：150 QPS 时达成 98.2%（P99 468ms）；200 QPS 时只完成 70.7% | 参考 |

一句话：**100 QPS 这个目标达到了**（提交、列表、混合都稳定达成且成功率 100%），看板是唯一吃力的路径——它能给出 500~590ms 的 P99（目标 800ms 以内），但撑不满 100 QPS。**师傅端「本楼栋」是第二条吃力的路径，而且它没有时间窗口**（§4.4）。

## 2. 环境（先看这一节，它决定了怎么读上面的数字）

| 项 | 值 |
|---|---|
| 应用 | 本机 `java -jar`，**`-XX:ActiveProcessorCount=2 -Xmx280m`** —— 与 `docs/05` §2.2 给 2C2G 的口径一致（`APP_MEM_LIMIT=512M` + `JAVA_MAX_RAM_PERCENTAGE=55` ≈ 280M 堆） |
| 数据库 | 本机 Docker MySQL 8（上限 768M、buffer pool 128M）——比 2C2G 部署建议的 512M **宽一些** |
| Redis | 本机 Docker Redis（`maxmemory` 256mb，与 2C2G 建议同档） |
| 数据集 | 独立库 `repair_loadtest`（Flyway 建表 + `docs/dev-seed.sql` 的三个账号），压测结束时 **3.6 万工单 / 3.6 万流转日志**——相当于一所学校一两年的量（跑完即删，不留在本机） |
| 压测机 | 同一台笔记本（Windows + Docker Desktop），**同时跑着 Docker、你自己的 IDEA 实例（8080）和这个压测实例** |

**三条必须一起读的边界**：

1. **本机不是目标机。** 结论要读成"这个量级扛得住"，不要读成"服务器上 P99 精确是 133ms"。真结论要在 `119.91.47.63` 上跑一遍（§6 给了命令）。
2. **测量有噪声。** 同一场景（列表 100 QPS）在不同轮次里出现过 P99 **82ms 与 380ms** 的差别——那不是代码变了，而是这台机器上还有别的负载。所以稳定结论来自**多轮样本**，单轮数字只作参考。
3. **延迟含客户端侧。** 生成器与被测应用在同一台机器上抢 CPU，测出来的延迟里混着"生成器自己调度"的时间。空载基线：`/actuator/health`（不过应用逻辑）P50 **6.1ms**，纯 TCP 连 MySQL 0.5ms、Redis AUTH+PING 1.2ms——**底座很快，所以应用侧那几十毫秒是真实的**。

## 3. 方法

- **工具**：`scripts/loadtest/loadtest.mjs`（Node 自带 fetch，零依赖，仓库里的一个文件）。自己写而不用 k6/JMeter 的理由在脚本头部：要按权重混场景、要复用登录态、而且它是可复跑可 review 的。
- **判成功**：HTTP 200 **且** `body.code === 0`。业务失败（例如 `10004` 限流）也算失败——**压测要把限流打出来**，否则会漏掉"高并发下自己被限流"。
- **速率控制**：按绝对时间切片，每个 tick 发一个请求（不是"起一堆会自己循环的虚拟用户"——我第一版那么写，20 QPS 实际打了 64 QPS）。
- **背压**：在途请求到 `--concurrency` 上限就**跳过这个 tick 并计数**，不排队等待。所以"达成率 < 100%"与"被挤掉的 tick 数"就是服务端饱和的信号，而延迟里不会混进客户端的排队时间。
- **样本**：提交 / 列表 / 看板 / 混合各跑 100 QPS × 60s；列表与看板另跑 **3 轮 30s** 取波动范围；余量探测跑混合 150 / 200 QPS × 30s。
- **补测（§4.4，协同处理之后）**：师傅端两条列表各跑 **2 轮 30s**，并把协作层临时摘掉再跑一遍作为对照——
  同一个会话里的 A/B 比"和历史数字比"可靠得多（§2 第 2 条）。

```bash
# 起被测实例（本机，2 核 / 280M 堆，独立库）
cd F:\code\repair-platform
set -a; . ./.env; set +a
MYSQL_PASSWORD="$MYSQL_ROOT_PASSWORD" MYSQL_DATABASE=repair_loadtest \
MINIO_ACCESS_KEY="$MINIO_ROOT_USER" MINIO_SECRET_KEY="$MINIO_ROOT_PASSWORD" \
/f/jdk17/bin/java -XX:ActiveProcessorCount=2 -Xmx280m \
  -jar target/repair-platform-0.0.1-SNAPSHOT.jar --server.port=8082

# 打流
node scripts/loadtest/loadtest.mjs --base http://127.0.0.1:8082 \
  --scenario submit --qps 100 --duration 60 --concurrency 40
```

## 4. 压测发现的三个问题（真正的产出）

### 4.1 工单列表缺一条索引：每请求排序 1.1 万行

- **现象**：列表 100 QPS 时只完成 77 QPS，P50 487ms、P99 620ms（目标 300ms）。
- **原因**：EXPLAIN 是 `key=idx_tenant_status  rows=11079  Extra=Using filesort`——
  先按租户取出 1.1 万行，**再在内存里排序**才能给出第 1 页那 10 条。
  现有索引都差一列：`idx_tenant_status(tenant_id, status, submit_time)` 中间夹着 `status`，
  而默认列表**不筛状态**，第三列就用不上（索引只在"前导列等值/范围"时才有序）。
- **修法**：`V4__ticket_tenant_time_index.sql` 加 `idx_tenant_deleted_time(tenant_id, deleted, submit_time)`
  ——`deleted` 是等值条件，必须排在范围条件 `submit_time` 之前才能全用上。
- **复测**：EXPLAIN 变成 `type=range  key=idx_tenant_deleted_time  Extra=Using index condition; Backward index scan`（不再 filesort）；
  列表 100 QPS **达成率 100%**，P99 从 620ms 降到 **82~88ms**（三轮样本）。
  混合场景跟着从 77 QPS / P99 654ms 变成 99.9 QPS / P99 153ms。

### 4.2 看板每行探一次 ticket_log：2 万次探测/请求

- **现象**：看板 100 QPS 只完成 64.6 QPS，P50 606ms。
- **原因**：核心指标卡的"超时工单数"写成了 `SUM(CASE WHEN EXISTS (SELECT 1 FROM ticket_log ...))`——
  聚合里套相关子查询，MySQL 只能**逐行探**，每张工单一次索引探测（3.6 万单就是 3.6 万次）；
  而 `ticket_log` 上当时只有 `(ticket_id, create_time)` 索引，只能从工单侧找动作。
- **修法**：**反过来从动作侧找工单**（`V5__ticket_log_action_index.sql` 加 `(action, ticket_id)` +
  把 EXISTS 改写成半连接 `COUNT(DISTINCT l.ticket_id)`）。超时动作在真实数据里是稀有事件
  （正常学校一天几条），于是代价从 O(工单数) 降到 O(超时数)。
  `COUNT(DISTINCT)` 不能省：同一张单可能既接单超时、又处理超时，去重后才与原口径一致
  （`StatisticsTest` 新增一条断言盯着它）。
- **复测**：看板 100 QPS 达成率 89.5~95.2%，P99 **507~585ms**（目标 800ms 以内 ✓）；
  统计数据与改写前完全一致（`StatisticsTest` 六条全绿）。

### 4.3 一次 1.1 秒的 P99 尖峰：没复现，是环境噪声

- **现象**：阶梯里 100 QPS 那一轮出现 P99 1102ms、MAX 1255ms（而 150/200 QPS 的轮次反而只有 288/208ms —— 非单调）。
- **排查**：GC 日志里**没有** > 100ms 的停顿（280M 堆下 206 次 GC 全是短停顿）；`Innodb_log_waits=0`；
  底层 TCP/Redis 往返都在 1ms 量级。按修复后的同一场景连续跑三轮，P99 稳定在 82~88ms，**尖峰没有复现**。
- **结论**：那是测量期间机器上的其他负载（Docker + 另一个应用实例）造成的，不是服务端缺陷。
  **这条写进来是因为它说明了一件事：单轮数字不足以定论，多轮样本才能。**

### 4.4 协同处理后的复测：师傅端两条列表（2026-09-29 补测）

协同处理（`docs/01` §4.5）给维修工的可见范围加了第三层——`我协作的工单`，
它是一条会注入到**师傅端每一个工单查询**里的条件（`docs/03` §5.3）。所以这一轮补测师傅端的两条列表，
并且**把那条条件临时摘掉再跑一遍**作为对照（A = 有协作层，B = 无协作层）。顺带把 `scripts/loadtest/`
补上了这两个场景——之前它只压管理端列表，师傅端那两条一直没被测过。

数据集：独立库 `repair_loadtest`，3.6 万工单（生成器灌），worker01 负责的楼栋里有 1.78 万，
其中 970 张派给了他（保证「我的任务」有数据）。口径与 §2 一致（2 核 / 280M 堆）。

| 场景 | A：有协作层 | B：无协作层（对照） | 差 |
|---|---|---|---|
| 「我的任务」`scope=mine` | P50 **36ms** · P99 **51ms** · 达成 99.8% | P50 30ms · P99 76ms · 达成 99.8% | P50 +6ms（P99 的差被噪声盖住） |
| 「本楼栋」`scope=building` | P50 **584ms** · P99 **760ms** · 达成 **63.8%** | P50 510ms · P99 678ms · 达成 71.2% | P50 **+74ms（+15%）** |

（每格两轮 30s 的样本：A 两轮差在 8ms 内；B 的 P99 两轮差 26ms，所以 P99 的差异要按噪声读。）

**EXPLAIN 说明代价花在哪**（`scope=mine`，3.6 万单）：

- 主表访问路径**逐字没变**：`type=range`、`key=idx_tenant_status`、`rows=972`、`Using filesort`
- 多出来的两步都走索引：`EXISTS(...)` 是 `DEPENDENT SUBQUERY`（`type=eq_ref`、`key=uk_ticket_worker`、
  `rows=1`、`Using index`）；拦截器注入的 `IN (SELECT ...)` 是 `SUBQUERY`（物化一次，`type=ref`、
  `key=idx_worker`、`rows=1`）

**两个结论，一个达标、一个是本来就坏的**：

1. **「我的任务」达标**：P50 36ms、P99 51ms，100 QPS 稳定达成。协作层的代价是 P50 +6ms 量级——
   这条查询本来只有几百行候选（`idx_tenant_status` 上 972 行），子查询是索引点查，乘上去也不明显。
2. **「本楼栋」本来就超标，协作层再让它慢 15%**：对照组（**没有**协作层）已经是 P50 510ms / P99 678ms、
   100 QPS 只能跑到 71%。原因是这条查询**没有任何时间或状态窗口**——它要把该师傅楼栋里的 1.78 万行
   按 `urgency DESC, submit_time` 排序（`Using filesort`），而 `idx_building_time(building_id, submit_time)`
   里没有 `urgency`，排序用不上索引。
   **这不是本次改动引入的**（对照组的数字就是证据），但这次把它量出来了。两条修法都属于产品决策，没放进本 PR：
   - 给这个视图加**默认时间窗口**（例如近 30 天）——它回答的是"这栋楼在修什么"，不是"这两年修过什么"
   - 或者建 `(building_id, urgency, submit_time)` 索引让排序也走索引（代价是再多一条要维护的索引）

> 读这组数字时记住 §2 第 2 条：这台机器上还跑着 Docker 与用户的 IDEA 实例，单轮数字只作参考。
> 上表的结论靠的是**同一次会话里 A/B 两组的对照**，不是绝对值的精度。

## 5. 没验的东西（别把它读成"都验过了"）

- **AI 问数**：每次调用都要花真钱，压测不碰它；它的成本上限由 `REPAIR_AI_RATE_LIMIT_MAX_REQUESTS` 控（ADR-003/013）。
- **文件上传**：会写对象存储，压的是磁盘与带宽，不属于本轮目标（且 MinIO 与 MySQL 抢同一台机器）。
- **并发下的定时任务**：超时调度（ZSet 秒级消费 + 每分钟兜底）在压测期间一直开着，但没有专门放大压它。
- **多实例部署**：本项目单机部署，没有验多实例下的 ZSet 去重与 Session 行为。
- **师傅端列表的绝对值**（§4.4）：那份数据集把 3.6 万单**集中在一栋楼**（都来自同一个报修码），
  比真实学校夸张得多——真实单栋楼的工单量小得多。所以"「本楼栋」P50 510ms"要读成
  **"数据涨上来之后这条视图会出问题"**，而不是"现在每所学校都这么慢"。
- **目标机**：见 §2 第 1 条，服务器上的数字要自己跑一遍才算数。

## 6. 在服务器上怎么跑（这台的数字才是要写进简历/交付文档的）

```bash
# 在**你自己的电脑**上跑生成器，目标指向服务器（生成器不需要装在服务器上）
node scripts/loadtest/loadtest.mjs --base http://119.91.47.63:8080 \
  --scenario mixed --qps 100 --duration 60 --concurrency 40 --yes
```

四条注意：

1. **会真写数据**：提交场景每 60 秒建 6000 张工单。演示站开了演示模式，重启（或凌晨 4 点）会自动清掉；
   如果不是演示环境，别对着生产库跑提交场景（只跑 `--scenario list` / `dash` 是纯读，安全）。
2. `--yes` 是跳过"目标不是本机"的 5 秒确认，不加也会等 5 秒然后开始。
3. 从公网打，延迟里会多出**你自己的上行带宽与网络往返**（广州大概 20~40ms），看 P99 时把这部分算进去。
4. 服务器是 2 核 2G 且**四个容器同机**，跑完记得 `docker stats --no-stream` 看一眼有没有把 MySQL 挤到 OOM
   （`docs/05` §2.2 的 swap 就是为这种尖峰准备的）。
