# 06 · 架构图（Mermaid）

> **这份文档解决什么问题**：读懂系统"长什么样、请求怎么走"。
> `docs/01~05` 是**契约**（规定"必须是什么"），本文件是**视图**（描述"现在实际是什么样"）——
> 图里出现与文字文档不一致的地方，以文字文档为准，并回来改图。
>
> **为什么用 Mermaid**：图是文本，能进 Git、能走 review、能和代码在同一个提交里改；
> 用截图或画图工具存的图，三个月后没人敢动，因为不知道改了哪里。
>
> **图的取舍**：只用 `flowchart` / `sequenceDiagram` / `erDiagram` 三种 GitHub 原生渲染的类型。
> Mermaid 的 `C4Context` 语法在部分渲染器上支持不完整，会出现"本地能看、GitHub 上空白"，
> 所以 C4 的分层用 `flowchart` + `subgraph` 表达，语义等价、渲染稳定。
>
> 每张图的**事实来源**都写在图下面，改代码时按那一行找到对应文档改。

| 图 | 回答的问题 | 事实来源 |
|---|---|---|
| §1 系统上下文图 | 边界在哪、谁在用、依赖了谁 | `docs/01` §角色、`docs/04` ADR-003/005 |

## 1. 系统上下文图（C4 Level 1）

**边界**：框内是本项目自己开发、自己部署的部分；框外是我们依赖但不控制的东西。

```mermaid
flowchart LR
    student(["学生<br/>报修人"])
    worker(["维修工<br/>接单上门"])
    admin(["后勤管理员<br/>派单调度"])
    operator(["平台运营<br/>开通 / 停用学校"])

    subgraph boundary["本系统：高校后勤报修 SaaS 平台"]
        platform["三端应用<br/>管理端 PC（含平台运营页）+ 学生/维修工 H5 + 后端 API"]
        data["本系统持有的数据<br/>工单 · 用户与权限 · 报修码 · 图片对象"]
        platform --- data
    end

    subgraph external["外部依赖（不控制，但故障会影响功能）"]
        camera["设备能力：摄像头<br/>H5 用 getUserMedia + jsqr<br/>小程序用 uni.scanCode"]
        deepseek["DeepSeek API<br/>自然语言问数 · 已接入（M4）"]
        mirror["GitHub Actions + 镜像仓库<br/>构建与部署 · M5 未验证"]
        dns["域名 / HTTPS 证书<br/>备案后可编小程序 · 当前用 IP + 端口"]
    end

    student -->|"扫码报修 · 查进度 · 验收评价"| platform
    worker -->|"接单 · 到场打卡 · 完工上报"| platform
    admin -->|"派单 · 统计看板 · 基础数据维护"| platform
    operator -->|"开通 / 停用学校 · 维护学校管理员"| platform
    student -.->|"扫码（HTTPS 或 localhost 才可用）"| camera
    worker -.->|"扫码（同上）"| camera
    platform -.->|"生成 SQL 与结论文案"| deepseek
    platform -.->|"推送镜像并重启容器"| mirror
    platform -.->|"小程序端要求 HTTPS + 已备案域名"| dns
```

**边界里明确没有什么**（避免"以后要不要加"的反复讨论，理由见 `docs/01` §5 与 `AGENTS.md` §9）：

- **不接微信授权登录、不接微信订阅消息 / 短信 / 邮件**：这些只在某一种端上有，会破坏"一套代码编 H5 也能编小程序"的跨端前提；通知一律走站内通知。
- **不集成学校现有的资产 / 教务系统**：没有对接需求，`tenant` + `tenantCode` 就是多租户的全部抽象。
- **没有面向学生的自助找回口令**：不做短信 / 邮件，所以"忘记口令"的出路是找学校后勤重置（学生 / 维修工），或找平台重置（后勤管理员）。详见 ADR-012。
- **平台运营的可见范围只有"租户 + 租户的管理员"**：`sys_role.tenant_id = 0` 是平台内置角色的位置，平台运营账号（`tenant_id = 0`、`user_type = 4`）通过 `/api/platform/**` 开通 / 停用学校。它**看不到任何学校的业务数据**——这条由 `PlatformScopeInterceptor` 强制（ADR-012），不是"当前没写那些接口"。

**为什么把"设备能力"画在框外**：扫码不是后端接口，是客户端能力。`docs/03` §7.1 明确写了"二维码没有后端接口，内容就是 code 本身，前端用 qrcode 库渲染"——把它画进边界内会让人误以为后端参与了扫码。

### 各容器的职责与关键约束

| 容器 | 技术 | 关键约束（写错会出什么问题） |
|---|---|---|
| `web-admin` | Vue 3 + Vite，产物 `dist/` | 只与后端通过 `/api/**` 通信；不 import 后端源码（`AGENTS.md` §3.1） |
| `miniapp-h5` | uni-app，产物 `dist/build/h5/` | 只用 `uni.*` 与 Vue（`uni.request` / `uni.getStorageSync` / `uni.uploadFile`），不引入 axios、不用 `localStorage`——否则编小程序时全部要重写 |
| `nginx` | nginx 1.27 | 唯一对外入口。图片 URL 由后端拼 `MINIO_PUBLIC_BASE_URL`，浏览器**不直连 MinIO**（9000 只绑 127.0.0.1，直连会打不开） |
| `app` | Spring Boot 3.5 + Java 17 | **无状态**：登录态在 Redis，所以可以多实例；超时调度的多实例去重靠 `ZREM` 返回值（ADR-001） |
| `mysql` | MySQL 8 | 14 张表；**不使用物理外键**，关联由应用层保证（`docs/02` §1） |
| `redis` | redis-stack-server 7.2 | 四种用途见下 |
| `minio` | MinIO（`quay.io` 镜像） | 应用启动**不依赖**它：首次上传才建客户端与桶，挂了只影响上传（返回 `50003`） |

**Redis 的四种用途**（拆开看才知道为什么它挂了不会全站不可用）：

| 用途 | Key | 不可用时的影响 |
|---|---|---|
| 登录态 | Sa-Token 自动管理 | 鉴权直接失败——这是唯一"硬依赖"（未登录回 401 + `10002`，Redis 异常回 500 + `10005`） |
| 延迟队列 | `ticket:timeout:{ACCEPT\|PROCESS\|EVAL}` | 秒级触发失效，由每分钟兜底扫描接管 |
| 限流计数 | 按「用户 + 接口」 | **放行**，不拦业务（ADR-009） |
| 工单号序列 | `ticket:no:seq:{yyyyMMdd}` | 取号失败即提交失败；`uk_ticket_no` 是兜底唯一约束 |

**M4 的位置**：`ai/` 包已落地——四层安全网关、Schema 注入、模型接入（LangChain4j + DeepSeek）、问数编排、`POST /api/ai/query` 与管理端「AI 问数」页都在。**只有流式（`/api/ai/query/stream`）还没做**，图里与流式相关的部分是计划态。

## 4. 核心业务时序图

参与者统一简写：`H5` = 学生/维修工端，`AD` = 管理端，`API` = 后端，
`DB` = MySQL，`R` = Redis，`MIO` = MinIO，`N` = 站内通知。

### 4.1 登录与发令牌

```mermaid
sequenceDiagram
    autonumber
    participant C as 前端（管理端 / H5）
    participant A as AuthController
    participant S as AuthServiceImpl
    participant DB as MySQL
    participant R as Redis

    C->>A: POST /api/auth/login（tenantCode + username + password）
    A->>S: login(dto)
    S->>DB: 按 tenantCode 查 tenant，须为启用状态
    alt 租户不存在或已停用
        S-->>C: 30003 租户不存在或已停用
    end
    S->>DB: 按 tenant_id + username 查 sys_user
    S->>S: BCrypt 校验口令
    Note over S: 账号不存在 / 口令错误回同一个 30001，<br/>账号停用回 30002 且放在口令校验之后<br/>——不向尝试者透露账号是否存在
    S->>R: StpUtil.login(userId)：token 与 Session 写入 Redis
    S->>R: Session 绑定 tenantId（数据权限每个请求都要读，避免每请求查库）
    S-->>C: token + userId / realName / userType
    C->>C: 持久化 token（H5 用 uni.setStorageSync）
    Note over C,S: 后续请求统一带 Authorization: Bearer 格式的 token<br/>登录态存 Redis，所以停用账号要同时踢下线
```

**为什么 token 放 Redis 而不是 JWT**：JWT 签出去就收不回，而"停用维修工"必须立刻生效
（`docs/03` §维修工接口的约定：停用会同时让已登录 token 失效）。代价是每个请求多一次 Redis 读。

### 4.2 一次请求要过的四道护栏

这张图是理解本项目**权限模型**的关键：功能权限在 Web 层，数据权限在 MyBatis 层，两者都在框架层，新增接口默认继承。

```mermaid
sequenceDiagram
    autonumber
    participant C as 前端
    participant F as TraceIdFilter
    participant T as SaInterceptor（order 0）
    participant L as RateLimitInterceptor（order 1）
    participant S as Controller / Service
    participant P as MyBatis 数据权限插件
    participant DB as MySQL

    C->>F: 任意 /api/** 请求
    F->>F: 生成 traceId → 写入 MDC 与响应头
    F->>T: 放行
    T->>T: ① /api/** 除登录接口外必须已登录<br/>② 校验 @SaCheckPermission 权限码
    T->>DB: 回调 StpInterfaceImpl 查权限码<br/>sys_user_role → sys_role_permission → sys_permission
    Note over T: 未登录 → 401 + 10002<br/>权限码不匹配 → 403 + 10003<br/>注意：没有按 /api/admin/** 前缀统一校验角色<br/>漏写注解 = 该接口对所有已登录用户开放
    T->>L: 放行
    L->>L: 只对 @RateLimit 接口计数<br/>键 = 用户 + 接口方法，固定窗口 60 次/分钟
    Note over L: Redis 不可用 → 放行<br/>限流防的是滥用，不是业务正确性
    L->>S: 放行
    S->>P: 执行 SQL
    P->>P: 只改写 ticket 与 notification：<br/>ticket 先注入租户、再按角色追加范围<br/>notification 注入 receiver_id = 我
    Note over P: 无登录态（定时任务）→ 不注入<br/>这是超时兜底能跨租户处理的前提（ADR-008）
    P->>DB: 改写后的 SQL
    DB-->>C: Result{code, message, data, traceId}
```

**这条链路里最容易犯的错**：以为 `/api/admin/**` 前缀本身就是权限。前缀只是路径组织方式，
真正决定能不能调用的是方法上的 `@SaCheckPermission`——所以漏写注解的接口是**对所有已登录用户开放的**。
`docs/03` §4 把这一点写成了明文约定。

### 4.3 提交报修（扫码或手输码 → 落库）

```mermaid
sequenceDiagram
    autonumber
    participant H5 as 学生端
    participant API as 后端
    participant DB as MySQL
    participant R as Redis
    participant MIO as MinIO

    H5->>H5: 扫码（getUserMedia + jsqr）或手输 6 位码
    Note over H5: H5 只在 HTTPS 或 localhost 下能取到摄像头<br/>取不到时必须提示改手输，不能静默失败
    H5->>API: GET /api/tickets/by-code/{code}
    Note over API: @RateLimit：短凭证可枚举，按用户限流<br/>超限 10004；码本身是随机生成的，限流只是抬高成本
    API->>DB: repair_code：本租户 + code + 启用
    alt 码不存在或已停用
        API-->>H5: 20006 报修码无效或已失效
    end
    API-->>H5: buildingId / buildingName / room（前端预填，不解析码）

    opt 有现场照片（最多 3 张）
        H5->>API: POST /api/files/upload（multipart，字段名固定 file）
        API->>API: 按文件头魔数判真实类型（不看后缀与 Content-Type）
        API->>MIO: putObject，对象键 = 租户ID/日期/uuid.扩展名
        API-->>H5: url + objectKey
    end

    H5->>API: POST /api/student/tickets
    API->>DB: 楼栋必须本租户且启用（扫码路径同样要过）
    API->>DB: 类别必须本租户且启用
    API->>R: INCR ticket:no:seq:{yyyyMMdd} 取当日序号
    API->>DB: insert ticket（status = 10 待派单）
    API->>DB: insert ticket_log（SUBMIT，operator = 学生）
    API-->>H5: 工单详情
    Note over API,DB: 提交时不登记任何超时任务<br/>三个超时节点的基准都是派单时刻（需求口径"从派到完工"）<br/>所以停在 10 待派单的工单不会被超时调度碰到
```

**为什么类别、楼栋都要服务端复校**：`requireEnabledBuilding` 的注释里写了两个真实后果——
不校验直接传的 `buildingId`，能造出"后勤看得到、师傅永远看不到"的孤儿工单；
不校验扫码路径，停用楼栋就挡不住扫码报修，"停用"就成了空话。

### 4.4 派单与接单

```mermaid
sequenceDiagram
    autonumber
    participant AD as 管理端
    participant API as 后端
    participant DB as MySQL
    participant N as 站内通知
    participant R as Redis
    participant W as 维修工端

    AD->>API: POST /api/admin/tickets/{id}/dispatch（workerId）
    API->>DB: 校验师傅：同租户 + 类型 = 维修工 + 启用
    Note over API: 跨租户师傅与不存在的师傅返回同一个 10001<br/>不告诉调用方"这个师傅是别家的"
    API->>DB: UPDATE ticket SET status=20, worker_id, dispatch_time<br/>WHERE id=? AND status=10
    alt 受影响行数 = 0（状态已被并发改动）
        API-->>AD: 20002 工单当前状态不允许该操作
    end
    API->>DB: insert ticket_log（DISPATCH 10 → 20）
    API->>N: 通知师傅（TICKET_DISPATCHED）
    API->>R: ZADD ticket:timeout:ACCEPT，score = 现在 + 24h
    API-->>AD: 成功

    W->>API: POST /api/worker/tickets/{id}/accept
    API->>DB: UPDATE SET status=30, accept_time<br/>WHERE id=? AND status=20 AND worker_id=我
    alt 被别人抢先（rows = 0）
        API-->>W: 20003 该工单已被其他人接单
    end
    API->>DB: insert ticket_log（ACCEPT 20 → 30）
    API->>R: ZREM 三个节点的 member（撤掉未接单提醒）<br/>ZADD ticket:timeout:PROCESS，score = 派单时间 + 48h
    API->>N: 通知学生（TICKET_ACCEPTED）
```

**两个不看代码就会理解错的点**：

1. **幂等靠条件更新，不靠"先查再改"**。`WHERE status = 旧状态` 的受影响行数为 0 就是并发冲突的信号。
   这套机制不依赖单实例假设，也没有锁的获取释放成本（`docs/03` §6）。
2. **处理超时的基准是派单时间，不是接单时间**。所以 `registerProcess` 传的是 `ticket.getDispatchTime()`，
   与每分钟兜底扫描的 `dispatch_time < now - 48h` 必须完全一致——两条路径基准不同就会给出不同的到期时刻。

### 4.5 到场打卡与完工上报

```mermaid

    participant N as 站内通知

    W->>API: POST /api/worker/tickets/{id}/arrive（repairCode）
    Note over API: @RateLimit：这也是接收短凭证的接口<br/>漏掉它就等于留了另一条猜码通道
    API->>DB: 查 repair_code（本租户 + 启用）
    alt 码指向的楼栋房间 ≠ 工单的楼栋房间

    end
    API->>DB: UPDATE SET arrive_time, arrive_minutes<br/>WHERE status=30 AND worker_id=我 AND arrive_time IS NULL
    Note over API,DB: 到场不改变状态（30 → 30）<br/>arrive_time 仅空时写入 → 重复打卡不覆盖首次时间<br/>arrive_minutes = 到场 − 派单
    API->>DB: insert ticket_log（ARRIVE）
```

**为什么要再校验一次码**：前端已经比对过一次，但"只靠前端比对等于没有校验"——

### 4.7 超时调度与兜底

```mermaid
sequenceDiagram
    autonumber
    participant T as TimeoutScheduler
    participant TS as TimeoutService
    participant R as Redis ZSet
    participant TI as TicketService
    participant DB as MySQL
    participant N as 站内通知

    loop 每 1 秒，三个节点各一个任务（ACCEPT / PROCESS / EVAL）
        T->>TS: handleDueAccept / handleDueProcess / handleDueEval
        TS->>R: ZRANGEBYSCORE key 0 now
        TS->>R: 逐个 ZREM member
        Note over TS,R: 只有 ZREM 返回 1 的实例才处理这个 member<br/>多实例部署时天然去重，不需要额外的分布式锁
        TS-->>T: 到期工单 id 列表
        T->>TI: autoClose / remindAcceptTimeout / escalateProcessTimeout
        TI->>DB: 查工单：状态是否仍停在预期节点
        TI->>DB: 查 ticket_log：该动作是否已经记录过
        Note over TI,DB: 幂等判据就是 ticket_log<br/>兜底扫描每分钟都会扫到同一批超期工单，不判重会刷屏
        TI->>DB: insert ticket_log（20 → 20 提醒 / 30 → 30 升级）<br/>或条件更新 50 → 60（唯一会改状态的超时动作）
        TI->>N: sendToTenantAdmins：提醒调度方
    end

    loop 每分钟整点兜底
        T->>TS: backstopScanAccept / Process / Eval
        TS->>DB: 扫「该到期却不在 ZSet 里」的工单
        Note over TS,DB: 三条硬约束：带状态过滤（N 不随时间增长）<br/>只取主键 · 单轮 LIMIT 200<br/>无登录态 → 数据权限不注入 → 天然跨租户
        TS-->>T: 走与上面完全相同的处理动作
    end
```

**这张图要记住的一句话**：秒级路径（ZSet）负责"准时"，分钟级路径（兜底扫描）负责"不漏"，
两条路径必须共用同一个到期基准，否则同一个工单会在两个时刻被处理两次、给出矛盾的结果。
基准的定义写在 `TimeoutServiceImpl` 的注释与 `docs/00` §3.4。

**只画不写会漏掉的坑**（都在代码注释里，这里集中一次）：

- 调度任务**不向上抛异常**，降级成一行 WARN 且同类失败只提醒一次——一个任务每秒跑一轮，
  Redis 挂掉时抛异常会按 ERROR 打整段堆栈，一天 20 多万行日志把真正的问题淹掉。
- `@Scheduled` 的线程池显式配成 4（`application.yml`）：Spring 默认池大小是 1，
  四个任务串行执行时，一次慢的兜底扫描会吃掉秒级任务的调度窗口，触发精度退化回分钟级——正是 ADR-001 要消灭的问题。
