# 04 · 架构决策记录（ADR）

> 记录每个技术选择背后的「备选方案 → 取舍 → 后果」。没有这份记录，过几个月连自己都说不清当初为什么这么选。
>
> 用它记录两类事：**① 为什么采用这个方案**；**② 遇到阻碍时暂时妥协了什么、打算怎么还**。
> 只写"最终选了什么"不算 ADR——**"负面后果"这一栏不能省**。

---

## 模板

```markdown
## ADR-00X：<决策标题>

- **状态**：已采纳 / 已废弃 / 待定
- **日期**：2026-XX-XX
- **背景**：我们面临什么问题？约束条件是什么？
- **备选方案**：
  1. 方案 A —— 简述
  2. 方案 B —— 简述
  3. 方案 C —— 简述
- **决定**：选哪个
- **理由**：为什么是它？关键权衡点是什么？
- **后果**：
  - 正面 —— 得到了什么
  - 负面 —— 付出了什么代价，以后可能要还什么债
```

> **"后果"这一栏别省。** 只写优点的 ADR 是自夸，写了代价的才是工程判断。

## ADR-001：用 Redis ZSet 延迟队列替代 Spring Task 定时轮询

- **状态**：已采纳（**已实现**，M3 超时三节点用的就是它）
- **日期**：2026-09-11

**背景**
工单需要超时提醒：24 小时未接单提醒调度方、48 小时未处理自动升级。原教程做法是用 `Spring Task` 每分钟轮询数据库，扫描超时工单。

**备选方案**

1. **Spring Task 定时轮询**：每分钟 `select * from ticket where status in (...) and submit_time < now() - 24h`
2. **Redis ZSet 延迟队列**：把「到期时间戳」作为 score 存入 ZSet，由调度线程每秒 `ZRANGEBYSCORE` 取出到期任务
3. **RabbitMQ 延迟插件 / Kafka 延时消息**：用消息中间件原生延迟能力

**决定**
选方案 2。

**理由**

| 维度 | 定时轮询 | Redis ZSet 延迟队列 |
|---|---|---|
| 触发精度 | 最差 ±60s（轮询间隔） | 秒级 |
| 数据库压力 | 每分钟一次全表范围扫描，随工单量线性增长 | 无无效查询，只查真正到期的 |
| 资源空转 | 大部分轮询没有结果 | 空转成本极低 |
| 实现复杂度 | 最低 | 中等（需处理时间轮/单次扫描上限） |
| 可靠性 | 依赖定时任务，多实例会重复执行 | 需加分布式锁或多实例下保证只消费一次 |

关键权衡：**轮询的"简单"是用数据库压力和触发精度换来的**。工单量小时看不出问题，但这是典型的"上线后随数据量恶化"的设计。

**后果**

- 正面：触发精度从分钟级降到秒级；数据库不再被无效扫描打扰；这个能力被复用到项目一的"优惠券到期"场景
- 负面：
  - 需要额外处理**多实例并发消费**（方案：`ZREM` 返回值判定，只有删除成功的实例才执行，天然去重）
  - Redis 重启需要保证 ZSet 不丢（方案：开 AOF + 兜底定时任务扫一次数据库补漏）
  - 比定时轮询多约 150 行代码

**取舍说明**：最初用的是定时轮询，后来发现两个问题——触发有最多 60 秒误差，而且每分钟都在扫一张越来越大的表。所以改成了 ZSet 延迟队列，用 `ZREM` 的返回值做多实例去重；但 Redis 重启有丢任务的风险，所以保留了一个低频兜底扫描。

## ADR-002：用 MyBatis 拦截器实现数据权限，而不是在每个 SQL 里手写条件

- **状态**：已采纳（**已实现**，M1/M2 落地）
- **日期**：2026-09-11

**背景**
三类角色的数据可见范围不同：学生只能看自己的工单；维修工只能看自己负责楼栋的工单；后勤管理看全部。系统有几十个查询工单的接口。

**备选方案**

1. **每个 SQL 手写 where**：在 Mapper XML 里为每条查询加 `and student_id = #{currentUserId}`
2. **Service 层统一封装**：在业务方法里调用 `setDataScope(query)` 后再执行
3. **MyBatis 拦截器自动注入**：拦截 SQL 解析 AST，根据当前登录角色自动拼上范围条件

**决定**
选方案 3。

**理由**

- 方案 1 的问题不是"麻烦"，而是**会漏**。只要有一个人新加接口时忘了写 where，就是一次越权漏洞，而且 code review 很难发现
- 方案 2 稍微好一些，但仍依赖"每个人都记得调用"
- 方案 3 把安全边界**收敛到框架层**：权限逻辑只写一次，新增接口零成本获得保护，**从"靠自觉"变成"默认安全"**

**后果**

- 正面：越权风险从"每个 SQL 手写 where"收敛到一处；新增业务接口自动受保护
- 负面：
  - SQL 解析有性能开销（方案：用 MyBatis-Plus 的 `TenantLineInnerInterceptor` 或自建 `InnerInterceptor`，只解析一次）
  - 复杂 SQL（多表 join、子查询）条件注入位置需要额外处理，要写测试覆盖
  - 调试时看不到完整的 SQL，需要开 SQL 日志

**取舍说明**：核心考虑是**默认安全**。手写 where 的问题不是麻烦，是它会漏——漏一次就是越权漏洞，而且 review 时肉眼很难发现。

## ADR-003：AI 生成的 SQL 必须经过数据权限拦截器与安全网关

- **状态**：已采纳（**待实现**：M4，尚未接入 AI）
- **日期**：2026-09-11

**背景**
AI 数据助手让模型根据自然语言生成 SQL。但模型是"不可信输入"——它可能生成 `select * from ticket where 1=1`（绕过租户隔离）、可能生成 `drop table`、也可能生成一条全表扫描的慢查询。

**备选方案**

1. **信任模型输出**：直接执行（**很多教程项目就是这么做的**）
2. **只在 Prompt 里约束**：在提示词里写"请只查询当前租户数据""不要生成 DML"
3. **独立的安全网关做代码级校验 + 复用数据权限拦截器**

**决定**
选方案 3。

**理由**

- 方案 1 是安全事故
- 方案 2 是**把安全寄托在模型身上**——同一个 prompt 换一个问题就可能失效，而且不同模型表现不一致，不可验证
- 方案 3 把安全从"模型自觉"变成"代码强制"：**不管模型生成什么，最后都过同一道闸门**

**具体闸门（四层）**

| 层 | 校验 | 拦截后返回 |
|---|---|---|
| 1 | 只读账号连接（数据库权限层面兜底） | —— |
| 2 | SQL 白名单：只允许 `SELECT`，禁 DDL / DML / 多语句 | `40002` |
| 3 | **强制走 MyBatis 数据权限拦截器**（复用 ADR-002 的能力） | `20004` |
| 4 | 超时熔断（>3s 中断）+ 返回行数上限（>1000 行截断） | `40003` |

**后果**

- 正面：模型再"胡说"也不会造成越权或数据损坏；这套网关可以独立测试（不依赖模型）
- 负面：
  - 部分合理但复杂的 SQL 会被误拦（方案：白名单只放行 `SELECT`，其他走人工审核）
  - 需要维护一个只读数据库账号
  - 增加了"生成 → 校验 → 执行"的链路长度，需要记录每一步用于排查

**取舍说明**：原则是**不信任模型输出**。安全不能写在 Prompt 里，因为 Prompt 约束不了模型行为。所以做了一道独立的 SQL 安全网关：只读账号、白名单、强制走数据权限拦截器、超时和行数限制。这套网关不依赖模型，可以单独写测试。

> 🔥 **这一篇是整套设计里最关键的一环**：AI 被当作一个**不可信的外部依赖**在工程上处理，而不是"调个 API"。

## ADR-004：报修码用「位置码 + 映射表」，而不是自解释编码或工单码

- **状态**：已采纳（**已实现**：repair_code 表 + `/api/tickets/by-code/{code}`）
- **日期**：2026-09-11

**背景**

学生报修和维修工到场都需要"扫码"这个入口：学生扫宿舍门口的码要自动带出楼栋和房间，省掉手填；维修工到场扫**同一个码**要验证"他确实到了这间房"，这是响应时长（到场时间 − 派单时间）的真实依据。两端必须共用一个后端接口（`GET /api/tickets/by-code/{code}`），否则将来从 H5 换成小程序就要改后端。

要决定的是：怎么把"码"和"楼栋 + 房间"对应起来。

**备选方案**

1. **位置码 + 映射表**：每房间一个短码，存 `repair_code(code, building_id, room)`，扫码查表定位
2. **自解释编码**：码由楼栋号 + 房间号 + 校验位算出来，不建表
3. **退化成工单码**：不贴位置码，维修工到场扫学生工单上的二维码（复用 `ticket_no`）

**决定**

选方案 1。

**理由**

| 方案 | 换来什么 | 代价 |
|---|---|---|
| 1 位置码 + 映射表 | 短码可手输、可重新生成，房间号怎么写都行 | 多一张表和一份房间数据 |
| 2 自解释编码 | 省一张表，可脚本批量生成二维码 | `room` 现在是自由文本 `varchar(32)`（如 `3-412`），要能算出来就必须给它加"可解析"的格式约束；房间号一变旧码直接失效 |
| 3 工单码 | 完全不用贴码、不用新表 | 丢掉"学生扫码带出楼栋房间"和"两端共用一个接口"这两个设计点 |

关键取舍：**方案 2 省下的那张表，是用"给房间号加格式约束"换来的**。房间号一旦出现 `A区201`、`图书馆-301` 这类写法，自解释编码就不成立——把不确定的业务约束塞进编码规则，比多维护一张小表风险更大。方案 3 则是为了省一张表，砍掉了项目里唯一一个跨端抽象。

另外要区分两个概念：**报修码是位置码，工单号才是某次维修的标识**。二者混用会导致"学生扫码时还没有工单"这个逻辑死结，所以一开始就把它们分开。

**后果**

- 正面：码是租户内的短字符串，H5 手输和二维码扫描走同一套逻辑；房间调整时改一行数据即可；`by-code` 接口的契约与"码怎么生成、怎么存"完全解耦
- 负面：
  - 多一张 `repair_code` 表和一份房间数据要维护（可按需生成，不必一次造全）
  - **「一房一码」由应用层保证，数据库不强制**：不给 `(building_id, room)` 建唯一索引，是因为逻辑删除后同一房间要能重新生成码，唯一索引会和 `deleted` 冲突——这是明确接受的妥协，对应 `idx_room` 那次校验查询
  - 引入了"打印并张贴二维码"这个**运维动作**，由学校上线时一次性完成（二维码内容就是 `code` 本身，前端用 qrcode 库渲染）。**它不是应用的运行依赖**，所以不影响开发进度
  - 码必须随机生成：顺序码能被枚举出全部房间，等于泄露房间清单

**取舍说明**：报修码特意没做成一码一工单，因为学生扫码的时候工单还不存在——它标识的是位置，工单号才是某次维修的标识。也没用自解释编码去省那张表：房间号是自由文本，要能算出来就得给它加格式约束，这是拿不确定的业务约束换一张小表，不划算。代价是一房一码数据库没法强制、只能应用层保证，这一点明确接受。

## ADR-005：AI 框架选 LangChain4j，且不引入它的 Spring Boot starter

- **状态**：已采纳（**待实现**：M4，pom 里尚未引入 LangChain4j）
- **日期**：2026-09-11

**背景**

AI 数据助手要做的链路是「自然语言 → Schema 检索 → 生成 SQL → 安全网关校验 → 执行 → 出图与结论」。其中用到框架能力的只有「模型对话 + 结构化输出」和「Schema 检索（向量检索）」，其余全是自己要写的工程逻辑。要定两件事：用哪套框架，以及怎么和 Spring Boot 集成。

**备选方案**

1. **Spring AI**：Spring 官方项目，与 Boot 自动装配一体，`ChatClient` 作统一入口；DeepSeek 兼容 OpenAI 接口，只改 base-url 即可
2. **LangChain4j**：生态更广，`AiServices` 声明式接口，对话记忆与 RAG 组件更成熟，接入的模型更多
3. **不用框架**：直接手写 HTTP 调 DeepSeek 的 chat/completions

**决定**

选 LangChain4j；但**不引入它的 Spring Boot starter**，只引入稳定的核心模块，自己写配置类构造 Bean。

**理由**

- 这个项目的 AI 部分很薄——两套框架在这里都只负责「把自然语言变成一条 SQL 字符串」，真正的技术在 Schema 检索、结构化输出提示词和 SQL 安全网关（见 ADR-003）。所以选择标准不是「谁更强」，而是「能力够用的前提下，谁的心智负担和长期维护成本更低」
- 后续要做 Schema 检索，LangChain4j 的 `AiServices`、对话记忆、RAG 组件更成熟，能直接复用，不必自己拼装
- **不引 starter 是因为它目前只有 beta**：核心 `langchain4j-open-ai:1.20.0` 是稳定版，而官方 Spring Boot starter 最新只到 `1.20.0-beta30`。本项目只需要一个 ChatModel Bean，用 `@Configuration` + `OpenAiChatModel.builder()` 二十来行就能替代 starter 的能力，不值得为此引入一个 beta 依赖
- DeepSeek 没有专用模块，官方推荐用 open-ai 模块 + 自定义 baseUrl（`https://api.deepseek.com/v1`），LangChain4j 的文档与集成测试就是这么用的
- 方案 3 被否：省掉一个依赖，但流式输出、结构化输出、重试都要自己写，且后续加 RAG 等于自己造轮子

**后果**

- 正面：
  - 后续 RAG / Schema 检索有现成组件，不用自己造
  - 只有稳定的核心模块进依赖树，没有 beta 依赖，升级节奏可控
  - 接入方式仍是配置驱动（base-url / api-key / model-name 走既有 `AI_MODEL_*` 环境变量），换模型不用改代码
- 负面：
  - 手写 `@Configuration` 构造 ChatModel，比引 starter 多约 20 行代码；等 starter 出稳定版可以再评估切回去
  - 没有 starter 就没有 `langchain4j.*` 配置属性绑定，模型参数（超时、温度等）得在配置类里自己从环境变量读
  - LangChain4j 声明 Jackson 2.22.x，而 Spring Boot 3.5.16 统一管理到 2.21.4，实际会用 2.21.4（同属 2.x，兼容）；若将来遇到 `NoSuchMethodError`，再把 `jackson-bom` 提到 2.22.x
  - 放弃了 Spring AI 的官方自动装配与 Spring 生态的一体化集成

**取舍说明**：框架改过一次——最初文档写的是 Spring AI，后来改用 LangChain4j，因为后续要做 Schema 检索，它的 RAG 组件更成熟。但没连 starter 一起引：核心是稳定版、starter 只有 beta，而这里只需要一个 ChatModel Bean，二十行配置类就能省掉一个 beta 依赖，这笔账划算。DeepSeek 没有专用模块，走 open-ai 模块加 base-url 就是官方用法。

## ADR-006：超时升级用同一套 ZSet 机制按节点实现；统计不建表、超时口径以动作记录为准

- **状态**：已采纳（**已实现**，M3）
- **日期**：2026-09-15

**背景**

M3 要做三件事：24h 未接单提醒、48h 未处理升级、验收超时自动关；外加统计看板（报修量、时长、超时率、满意度、师傅工作量）。两个问题需要先定：① 三条超时规则怎么组织，避免三套实现；② 统计里的"超时"怎么算，以及要不要为统计建汇总表。

**决定**

1. **三个超时节点共用一套机制**：Redis ZSet（ADR-001）按节点分 key（`ticket:timeout:{ACCEPT|PROCESS|EVAL}`，member = ticketId、score = 到期毫秒），秒级消费 + 每分钟兜底扫描；节点在业务流转处登记（派单登记 ACCEPT、接单登记 PROCESS、评价登记 EVAL），节点完成或到达终态时取消。
2. **超时动作一律"记一笔 ticket_log + 发通知"，只有验收超时会改状态**（50 → 60）：
   - `ACCEPT_TIMEOUT` / `PROCESS_TIMEOUT`：不是状态跃迁，记 `20 → 20` / `30 → 30` 的日志（与"到场 30 → 30"同一手法）
   - `AUTO_CLOSE`：真正的状态跃迁，操作者 = 0（系统）
   - **幂等靠 ticket_log 判重**：兜底扫描每分钟都会扫到同一批超期工单，不判重会把管理员刷屏
3. **不为统计建汇总表**：统计全部从 `ticket` / `ticket_evaluation` / `ticket_log` 现算，SQL 写在 Mapper XML。
4. **统计的"超时"以 ticket_log 里的超时动作为准**，不在统计 SQL 里重算阈值。
5. **阈值全部可配**（`REPAIR_TIMEOUT_ACCEPT_MINUTES` / `PROCESS_MINUTES` / `EVAL_MINUTES`），通知正文按实际阈值生成（演示调到 1 分钟时不会说谎成"24 小时"）。

**备选方案与放弃原因**

| 备选 | 为什么不用 |
|---|---|
| 三条规则各写一个定时任务扫库 | 三份重复逻辑；分钟级精度；库压力随工单量线性增长（ADR-001 已否掉轮询） |
| 统计建日汇总表（定时跑批写入） | 当前量级没有收益，却引入"汇总与明细不一致"和补数问题；真需要时再加汇总表/物化视图 |
| 统计 SQL 里直接用阈值算超时（`TIMESTAMPDIFF(...) > 阈值`） | 阈值可配置，抄进 SQL 后两处会悄悄漂移；且"已超阈值但调度器还没处理"的工单会被算成超时 |
| 超时直接改状态（如未接单自动转派） | 自动转派会绕过"谁负责哪栋楼"的人工判断；MVP 先提醒人，决策权留给后勤 |

**后果**

- 正面：三个节点只有一份机制与一份幂等实现；看板口径与超时动作同源（都来自 ticket_log），不会出现"看板说超时、日志里查不到"的矛盾；不新增表、不新增依赖（Excel 导出留到 P1）。
- 负面：
  - **"超时动作会写 ticket_log"成了隐含约定**，改判重逻辑时要连日志语义一起看
  - 超时率偏乐观：工单若在调度器触发前就被人工处理，不计入超时（有意选择——以实际发生的动作为准）
  - ZSet 按节点分 key 后，"取消该工单全部超时"要删多个 key（当前 3 个），新增节点时必须同步加进 `cancel`
  - 兜底扫描是全表跨租户的，会扫到历史遗留工单；处理方（调度器）必须容忍"状态已不是预期"并跳过

**取舍说明**：最初想给统计建日汇总表，理由是"看板要快"；但当前量级明细现算完全够（`idx_tenant_status` 覆盖大部分查询），而汇总表会带来对不上的风险。另一处纠结点是超时口径——用时间戳重算更"精确"，但阈值可配置后两处必然漂移，而且看板会显示"超时"却在日志里找不到对应的提醒。最后选了同源口径：**看板上的每个超时，后台都能找到那笔触发它的日志**——解释得清比算得准更重要。

## ADR-007：前端先与后端同仓（单仓），但守住边界以保留拆分路径

- **状态**：已采纳（**部分实现**：管理端脚手架就绪，页面开发中）
- **日期**：2026-09-15

**背景**

项目最初只规划了后端工程，但 `nginx/nginx.conf` 与 `docker-compose.yml` 早就按"单仓"写好了——挂载 `./web-admin/dist` 与 `./miniapp-h5/dist`，`docs/05` 也有一句"本地构建前端"。真正要做前端时，需要定：与后端同仓库，还是各自一个仓库。

**备选方案**

1. **单仓**：`web-admin/`（Vue 3 管理端）+ `miniapp-h5/`（uni-app）放在本仓库根目录，与后端平级
2. **前端独立仓库**：`repair-admin` / `repair-h5` 各一个
3. **不做前端**：交付定位为"后端 + Knife4j 接口文档"

**决定**

选方案 1（单仓），但把"将来可以便宜地拆成独立仓库"作为硬约束写进 `AGENTS.md` 3.1。

**理由**

- **现有部署链路就是按单仓写的**：nginx 的两个 location、compose 的两个 volume、部署文档的构建步骤都指向仓库内的 `dist` 目录；选方案 2 要先付一笔返工成本
- 这个项目的使用场景是"别人 clone 下来能跑通完整系统"（面试/演示），**单仓让"打开仓库 30 秒"的检验最容易过**；分仓会让人在后端仓库里看不到前端
- 前端两个工程本就是独立技术栈（Vue 3 后台 vs uni-app），放一起不会互相纠缠——"单仓"只是同一个 git 仓库，不是合并成一个工程

**代价与对策**

| 代价 | 对策 |
|---|---|
| 仓库变重、history 混在一起 | Commit scope 固定 `admin` / `h5`，将来按路径切分历史时是天然分界 |
| 后端 CI 可能被前端拖慢 | 前端 CI 独立成 workflow、按路径触发；后端构建里不出现 Node |
| 将来拆分要改部署配置 | 现在就明确边界（各带 package.json、不互相引用、产物不进后端 jar、后端不依赖前端），使拆分只改 nginx / compose / 部署文档三处 |

**将来真要拆的时候（保留的路径）**

```bash
git subtree split -P web-admin  -b admin-only   # 带历史切出
git subtree split -P miniapp-h5 -b h5-only
```

然后：新仓库接收 + 改 `nginx/nginx.conf` 挂载点 + 去掉 `docker-compose.yml` 两个 volume + 更新 `docs/05` 构建步骤 + **在 README 里补前端仓库链接**（否则又回到"打开仓库看不到全貌"）。

**负面后果**

- 单仓里后端测试与前端构建是两套工具链，新人容易搞混"提交前该跑哪个"（已在 AGENTS 第 8 节写清）
- 根目录会多出 `node_modules`（进 `.gitignore`）；前端变大后 clone 时间会明显增加——那时就是拆分的信号
- 这条决策**有过期条件**：当"前端构建拖累日常开发"或"前端需要独立发布节奏"时，就该执行上面的拆分

**取舍说明**：纯从架构洁癖看，分仓更干净；但当前阶段（一个人、演示型项目）"能跑通、能演示、边界清楚"比"部署链路解耦"更重要。所以选择用**边界约定**换**拆分自由**：现在省事，将来也不被动。
