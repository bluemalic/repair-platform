# 04 · 架构决策记录（ADR）

> 记录每个技术选择背后的「备选方案 → 取舍 → 后果」。没有这份记录，过几个月连自己都说不清当初为什么这么选。
>
> 用它记录两类事：**① 为什么采用这个方案**；**② 遇到阻碍时暂时妥协了什么、打算怎么还**。
> 只写"最终选了什么"不算 ADR——**"负面后果"这一栏不能省**。

---

## 模板

```markdown
## ADR-00X：<决策标题>

- **状态**：已采纳 / 已废弃 / 待定
- **日期**：2026-XX-XX
- **背景**：我们面临什么问题？约束条件是什么？
- **备选方案**：
  1. 方案 A —— 简述
  2. 方案 B —— 简述
  3. 方案 C —— 简述
- **决定**：选哪个
- **理由**：为什么是它？关键权衡点是什么？
- **后果**：
  - 正面 —— 得到了什么
  - 负面 —— 付出了什么代价，以后可能要还什么债
```

> **"后果"这一栏别省。** 只写优点的 ADR 是自夸，写了代价的才是工程判断。

## ADR-001：用 Redis ZSet 延迟队列替代 Spring Task 定时轮询

- **状态**：已采纳（**已实现**，M3 超时三节点用的就是它）
- **日期**：2026-09-11

**背景**
工单需要超时提醒：24 小时未接单提醒调度方、48 小时未处理自动升级。原教程做法是用 `Spring Task` 每分钟轮询数据库，扫描超时工单。

**备选方案**

1. **Spring Task 定时轮询**：每分钟 `select * from ticket where status in (...) and submit_time < now() - 24h`
2. **Redis ZSet 延迟队列**：把「到期时间戳」作为 score 存入 ZSet，由调度线程每秒 `ZRANGEBYSCORE` 取出到期任务
3. **RabbitMQ 延迟插件 / Kafka 延时消息**：用消息中间件原生延迟能力

**决定**
选方案 2。

**理由**

| 维度 | 定时轮询 | Redis ZSet 延迟队列 |
|---|---|---|
| 触发精度 | 最差 ±60s（轮询间隔） | 秒级 |
| 数据库压力 | 每分钟一次全表范围扫描，随工单量线性增长 | 无无效查询，只查真正到期的 |
| 资源空转 | 大部分轮询没有结果 | 空转成本极低 |
| 实现复杂度 | 最低 | 中等（需处理时间轮/单次扫描上限——**已实现**：兜底扫描带状态过滤 + 单轮 LIMIT 200 + 索引，见 `docs/02`） |
| 可靠性 | 依赖定时任务，多实例会重复执行 | 需加分布式锁或多实例下保证只消费一次 |

关键权衡：**轮询的"简单"是用数据库压力和触发精度换来的**。工单量小时看不出问题，但这是典型的"上线后随数据量恶化"的设计。

**后果**

- 正面：触发精度从分钟级降到秒级；数据库不再被无效扫描打扰；这个能力被复用到项目一的"优惠券到期"场景
- 负面：
  - 需要额外处理**多实例并发消费**（方案：`ZREM` 返回值判定，只有删除成功的实例才执行，天然去重）
  - Redis 重启需要保证 ZSet 不丢（方案：开 AOF + 兜底定时任务扫一次数据库补漏）
  - 比定时轮询多约 150 行代码

**取舍说明**：最初用的是定时轮询，后来发现两个问题——触发有最多 60 秒误差，而且每分钟都在扫一张越来越大的表。所以改成了 ZSet 延迟队列，用 `ZREM` 的返回值做多实例去重；但 Redis 重启有丢任务的风险，所以保留了一个低频兜底扫描。

## ADR-002：用 MyBatis 拦截器实现数据权限，而不是在每个 SQL 里手写条件

- **状态**：已采纳（**已实现**，M1/M2 落地；**租户层是后补的，见 ADR-008**）
- **日期**：2026-09-11

**背景**
三类角色的数据可见范围不同：学生只能看自己的工单；维修工看自己负责楼栋的工单**以及派给自己的单**（后者含跨楼栋的紧急抽调，见 ADR-008 的修订）；后勤管理看全部。系统有几十个查询工单的接口。

**备选方案**

1. **每个 SQL 手写 where**：在 Mapper XML 里为每条查询加 `and student_id = #{currentUserId}`
2. **Service 层统一封装**：在业务方法里调用 `setDataScope(query)` 后再执行
3. **MyBatis 拦截器自动注入**：拦截 SQL 解析 AST，根据当前登录角色自动拼上范围条件

**决定**
选方案 3。

**理由**

- 方案 1 的问题不是"麻烦"，而是**会漏**。只要有一个人新加接口时忘了写 where，就是一次越权漏洞，而且 code review 很难发现
- 方案 2 稍微好一些，但仍依赖"每个人都记得调用"
- 方案 3 把安全边界**收敛到框架层**：权限逻辑只写一次，新增接口零成本获得保护，**从"靠自觉"变成"默认安全"**

**后果**

- 正面：越权风险从"每个 SQL 手写 where"收敛到一处；新增业务接口自动受保护
- 负面：
  - SQL 解析有性能开销（方案：用 MyBatis-Plus 的 `TenantLineInnerInterceptor` 或自建 `InnerInterceptor`，只解析一次）
  - 复杂 SQL（多表 join、子查询）条件注入位置需要额外处理，要写测试覆盖
  - 调试时看不到完整的 SQL，需要开 SQL 日志

**取舍说明**：核心考虑是**默认安全**。手写 where 的问题不是麻烦，是它会漏——漏一次就是越权漏洞，而且 review 时肉眼很难发现。

## ADR-003：AI 生成的 SQL 必须经过数据权限拦截器与安全网关

- **状态**：已采纳（**四层已全部落地**：第 2、3 层是纯逻辑 + 33 条单测；第 1、4 层有真库集成测试。模型接入、两个接口、管理端页面与 20 问评测集见 `docs/07`）
- **日期**：2026-09-11（2026-09-25 补「落地时的修正」，2026-09-26 补「评测发现的三个问题」）

**背景**
AI 数据助手让模型根据自然语言生成 SQL。但模型是"不可信输入"——它可能生成 `select * from ticket where 1=1`（绕过租户隔离）、可能生成 `drop table`、也可能生成一条全表扫描的慢查询。

**备选方案**

1. **信任模型输出**：直接执行（**很多教程项目就是这么做的**）
2. **只在 Prompt 里约束**：在提示词里写"请只查询当前租户数据""不要生成 DML"
3. **独立的安全网关做代码级校验 + 复用数据权限拦截器**

**决定**
选方案 3。

**理由**

- 方案 1 是安全事故
- 方案 2 是**把安全寄托在模型身上**——同一个 prompt 换一个问题就可能失效，而且不同模型表现不一致，不可验证
- 方案 3 把安全从"模型自觉"变成"代码强制"：**不管模型生成什么，最后都过同一道闸门**

**具体闸门（四层）**

| 层 | 校验 | 拦截后返回 |
|---|---|---|
| 1 | 只读账号连接（数据库权限层面兜底） | —— |
| 2 | SQL 白名单：只允许 `SELECT`，禁 DDL / DML / 多语句 | `40002` |
| 3 | **强制走 MyBatis 数据权限拦截器**（复用 ADR-002 的能力） | `20004` |
| 4 | 超时熔断（>3s 中断）+ 返回行数上限（>1000 行截断） | `40003` |

**落地时的修正**（2026-09-25，写代码时发现的）

第 3 层"**强制走 MyBatis 数据权限拦截器**"这句话，在 AI 这条路上**不能照字面做**：

- 那个拦截器只覆盖 `ticket` / `notification` 两张表（ADR-008 的范围，AGENTS §5.6 写明了）。这在 Mapper 手写 SQL 的世界里是成立的——其它表的租户条件由每个查询自己写。但 **AI 生成的 SQL 没有"每个查询自己写"这一说**：`SELECT * FROM building` 会读到别家租户的楼栋，而拦截器根本不会看它一眼
- 所以落地时改成：**由安全网关自己在 AST 上给每张白名单表注入 `tenant_id = 当前租户`**，复用的是同一套手法（`TicketDataScopeHandler` 的别名优先限定、`AndExpression` 组合、jsqlparser 5.x 的 `ParenthesedExpressionList` 坑）。**语义没变**（仍然是"先租户、再角色"），只是执行者从拦截器换成了网关
- 附带得到一个好性质：注入条件是 **AND** 上去的。模型就算写了 `tenant_id = 999`，最终是 `tenant_id = 999 AND tenant_id = 本租户` → 空结果。**只能收窄、不能放宽**——比"检查模型有没有写租户条件"可靠得多
- 上面表里第 3 层那一格写的 `20004` 因此用不到：这一层的形态是**注入**而不是**拒绝**，没有"被拦下"的时刻。唯一会拒绝的情况是"某张白名单表没有 `tenant_id` 列"（那样根本没法限定租户），那种情况用 `40002`
- **角色维度暂不适用**：`ai:query` 只授后勤管理，而后勤在本租户内不受角色限制。将来若把问数开放给学生 / 维修工，网关必须补上角色维度——**同样不能只靠拦截器**，理由同上

还有两条实现期的取舍，一并记在这里：

- **表白名单是代码常量，不从 `information_schema` 读**：从库里读的话，"加一张表"就自动放开了它对 AI 的可见性——那正是"配置漂移导致越权"的形态，而且漂移时没有任何人做决定。现在新表必须显式加进 `SchemaWhitelist`，且只读账号的 GRANT 由同一份清单生成（两处不会漂）
- **多语句检测用 `parseStatements` 而不是 `parse`**：实测 jsqlparser 的 `parse()` 只解析第一条、**静默丢掉后面的**，`SELECT id FROM ticket; DROP TABLE ticket` 会"通过"。虽然返回的是改写后的 `toString()`（尾巴本来也执行不到），但把安全性建立在"解析器会丢尾巴"上太脆——所以显式数语句条数

**还要注入 `deleted = 0`**（2026-09-25，测试里抓到的）

项目的每一处查询都走 MyBatis-Plus，而它的**逻辑删除**会自动补上 `deleted = 0`——**AI 的 SQL 走裸 JDBC，绕过了那一层**。不补的后果是它把已删除的楼栋、已删除的工单一起算进去，于是"AI 说 6 栋楼、界面显示 5 栋"这种矛盾立刻出现，而口径不一致是最伤信任的一类问题。

- 这件事是测试抓到的：本机库里有一行逻辑删除的楼栋（`deleted = 1`），问"有几栋楼"真的多出来一栋——**只有拿真数据跑才会发现**
- 注入与否取决于那张表**有没有**这一列（注给没有该列的表会让 SQL 直接报"未知列"），所以网关依赖一个 `ColumnLookup`：生产由 `SchemaCatalog` 从 `information_schema` 提供，测试给假实现。这也是网关保持"纯逻辑可单测"的办法

**只读账号怎么来：应用启动时引导创建**（2026-09-25 定）

第 1 层需要一个只有白名单 SELECT 权限的数据库账号。"照文档执行一段 SQL"是个**记得做**的步骤，漏了它的现象是"问数报连接失败"，要绕一圈才知道是账号没建（同一个坑刚踩过：演示站重建前端漏了 `VITE_DEMO_ACCOUNTS`）。所以交给启动引导：

- 配了 `AI_DB_USERNAME` / `AI_DB_PASSWORD` 就一定会有账号，且**授权与白名单同源**（GRANT 语句由 `SchemaWhitelist` 生成，不会漂）
- 权限每次启动**收敛**而不是累加：先 `REVOKE ALL`，再按白名单 `GRANT SELECT`——有人手工给过额外权限也会被自动收回
- **口令每次启动同步**，与平台运营账号的"只建不改"**相反**：平台账号的口令是人的登录凭据，覆盖会把手改过的打回环境变量值；这个账号是应用自己要用的凭据，`.env` 就是它的唯一真相来源，改了就该生效
- 引导失败不阻断启动（AI 用不了是"少一个功能"）

**执行侧的两条实现选择**：

- **自己持有一个小连接池，而不是再声明一个 Spring `DataSource` bean**：加第二个 bean 就得给原数据源加 `@Primary`（改到既有装配）；自己持有还有个更重要的好处——**结构上保证 AI 的 SQL 永远不可能走到 root 连接上**（另一个账号、另一个池、不经过 MyBatis）
- **行数上限用 `setMaxRows(maxRows + 1)`**：多取的那一行用来判断"是否被截断"（取到第 maxRows+1 行说明后面还有），返回时只给 maxRows 行并置 `rowLimited`。比"在 SQL 上补 LIMIT"更准——补 LIMIT 之后就无从知道到底有没有更多行了

**评测发现的三个问题**（2026-09-26，20 问评测集跑出来的；现象→原因→修法见 `docs/07` §4）

这三条都不在单测的覆盖范围里，只有真调模型、真跑数据才会暴露：

1. **子查询绕过了租户注入**（数据泄露）：租户条件只注入外层 FROM / JOIN 的表，
   `SELECT (SELECT COUNT(*) FROM sys_user WHERE tenant_id <> 1) FROM building` 里括号那段**一个字都不改**
   ——实测能读到别家租户的计数。修法：**任何位置的子查询一律拒绝**，让模型改用 `LEFT JOIN`。
   没走"递归进子查询再注入"，理由是 fail-closed：多一种递归形状就多一处**静默**漏注入的可能
2. **LEFT JOIN 的注入落点错了**（答案静默出错）：反连接写法 `LEFT JOIN e ON ... WHERE e.id IS NULL` 里，
   注入到 WHERE 的 `e.tenant_id = 1` 会把"没匹配上"的行一起滤掉，LEFT JOIN 退化成 INNER JOIN
   ——实测答案从 6 变成 0。修法：**FROM 的表进 WHERE，JOIN 进来的表进它自己的 ON**；
   `RIGHT / FULL JOIN` 直接拒绝（可空一侧在左边，条件只能进 WHERE，同样会错）
3. **"完成"没有定义**（口径缺失，不是模型问题）：状态机里 40 / 50 / 60 都沾"完成"，
   提示词没定义 → 同一问题三轮给出两个不同数字。修法：口径清单里写清八个状态的语义与"完成"取哪几个

**后果**

- 正面：模型再"胡说"也不会造成越权或数据损坏；这套网关可以独立测试（不依赖模型）
- 负面：
  - 部分合理但复杂的 SQL 会被误拦（方案：白名单只放行 `SELECT`，其他走人工审核）
  - 需要维护一个只读数据库账号
  - 增加了"生成 → 校验 → 执行"的链路长度，需要记录每一步用于排查

**取舍说明**：原则是**不信任模型输出**。安全不能写在 Prompt 里，因为 Prompt 约束不了模型行为。所以做了一道独立的 SQL 安全网关：只读账号、白名单、强制走数据权限拦截器、超时和行数限制。这套网关不依赖模型，可以单独写测试。

> 🔥 **这一篇是整套设计里最关键的一环**：AI 被当作一个**不可信的外部依赖**在工程上处理，而不是"调个 API"。

## ADR-004：报修码用「位置码 + 映射表」，而不是自解释编码或工单码

- **状态**：已采纳（**已实现**：repair_code 表 + `/api/tickets/by-code/{code}` + 管理端生成 / 修改接口，2026-09-16 补齐）
- **日期**：2026-09-11

**背景**

学生报修和维修工到场都需要"扫码"这个入口：学生扫宿舍门口的码要自动带出楼栋和房间，省掉手填；维修工到场扫**同一个码**要验证"他确实到了这间房"，这是响应时长（到场时间 − 派单时间）的真实依据。两端必须共用一个后端接口（`GET /api/tickets/by-code/{code}`），否则将来从 H5 换成小程序就要改后端。

要决定的是：怎么把"码"和"楼栋 + 房间"对应起来。

**备选方案**

1. **位置码 + 映射表**：每房间一个短码，存 `repair_code(code, building_id, room)`，扫码查表定位
2. **自解释编码**：码由楼栋号 + 房间号 + 校验位算出来，不建表
3. **退化成工单码**：不贴位置码，维修工到场扫学生工单上的二维码（复用 `ticket_no`）

**决定**

选方案 1。

**理由**

| 方案 | 换来什么 | 代价 |
|---|---|---|
| 1 位置码 + 映射表 | 短码可手输、可重新生成，房间号怎么写都行 | 多一张表和一份房间数据 |
| 2 自解释编码 | 省一张表，可脚本批量生成二维码 | `room` 现在是自由文本 `varchar(32)`（如 `3-412`），要能算出来就必须给它加"可解析"的格式约束；房间号一变旧码直接失效 |
| 3 工单码 | 完全不用贴码、不用新表 | 丢掉"学生扫码带出楼栋房间"和"两端共用一个接口"这两个设计点 |

关键取舍：**方案 2 省下的那张表，是用"给房间号加格式约束"换来的**。房间号一旦出现 `A区201`、`图书馆-301` 这类写法，自解释编码就不成立——把不确定的业务约束塞进编码规则，比多维护一张小表风险更大。方案 3 则是为了省一张表，砍掉了项目里唯一一个跨端抽象。

另外要区分两个概念：**报修码是位置码，工单号才是某次维修的标识**。二者混用会导致"学生扫码时还没有工单"这个逻辑死结，所以一开始就把它们分开。

**后果**

- 正面：码是租户内的短字符串，H5 手输和二维码扫描走同一套逻辑；房间调整时改一行数据即可；`by-code` 接口的契约与"码怎么生成、怎么存"完全解耦
- 负面：
  - 多一张 `repair_code` 表和一份房间数据要维护（可按需生成，不必一次造全）
  - **「一房一码」由应用层保证，数据库不强制**：不给 `(building_id, room)` 建唯一索引，是因为逻辑删除后同一房间要能重新生成码，唯一索引会和 `deleted` 冲突——这是明确接受的妥协，对应 `idx_room` 那次校验查询
  - 引入了"打印并张贴二维码"这个**运维动作**，由学校上线时一次性完成（二维码内容就是 `code` 本身，前端用 qrcode 库渲染）。**它不是应用的运行依赖**，所以不影响开发进度
  - 码必须随机生成：顺序码能被枚举出全部房间，等于泄露房间清单

**取舍说明**：报修码特意没做成一码一工单，因为学生扫码的时候工单还不存在——它标识的是位置，工单号才是某次维修的标识。也没用自解释编码去省那张表：房间号是自由文本，要能算出来就得给它加格式约束，这是拿不确定的业务约束换一张小表，不划算。代价是一房一码数据库没法强制、只能应用层保证，这一点明确接受。

**实现约定（2026-09-16 补，管理端接口落地时定下）**

- **码用 `SecureRandom` 生成，不用 `Random`**：码是"能被猜的凭证"（ADR-009 的威胁模型就是枚举），可预测的伪随机序列会让"猜下一个码"变容易——这是与"随机生成"配套的一半
- **6 位数字且不以 0 开头**（100000–999999）：便于口述与手输；避开前导零，是因为"012345"很容易被漏掉第一位
- **落库靠 `uk_code` 兜底，先查一次只是减少可预见的冲突**：查与插之间仍有并发窗口，撞上时返回明确的重试提示（`10005`），不做"插入失败再换一个"的循环——那会让每次生成都去处理异常路径
- **一房一码严格到"停用的码也算占用"**：同一房间只要还有一条未删除的码就拒绝新建（否则同一房间留两行，这条不变量名存实亡）。换码的正式做法是在原码上「重新生成」（`PUT` 带 `regenerate=true`），而不是新建一条
- **没有删除接口**：不在使用的码**停用**即可（扫码返回 `20006`）。`repair_code` 不被其它表引用，所以这里不是"历史数据要留着"，而是"删了就得靠软删 + 全局过滤那套，不如停用直接"——与楼栋 / 类别的处理保持一致
- **建码时只要求楼栋存在且属于本租户，不要求楼栋启用**：允许"先把码备好、楼栋稍后开放"；停用楼栋下的码本身无害，学生扫码提交时会被 `submit` 的楼栋校验拦住（docs/03 §5.4）

**补充（2026-10-17）：公共区域码，以及"两条位置入口"**

原来的模型是"每间房一张码"。落地后发现一个现实问题：**公共区域（走廊、大厅、公共卫生间）
不可能一间房一码**，而要求人为了报修去满楼找码不现实。

决定：`repair_code` 加 `location_type`（V9），`location_type = 2` 表示公共区域，`room` 存区域名。
**一个区域一张码**，贴在楼层电梯口 / 大厅入口这类必经之处；同时 H5 报修页加"手动选位置"入口
（数据源就是报修码清单，`GET /api/locations`）。

这条补充**没有改变 ADR-004 的核心结论**——"位置用码表达、码是短凭证所以要限流"依然成立；
补的是码的覆盖范围：从"房间"扩到"房间 + 区域"。必须守住的不变量是
**每个可报修的位置都有一张码**：到场核验（`arrive`）靠它，两条入口因此共用同一套校验，
不为公共区域写特判。理由与边界见 `docs/01` §4.6。

## ADR-019：派单评分用「四项加权 + 逐项可解释」，只排序不自动派单

- **状态**：已采纳（**已实现**：V10 + `DispatchScoreService` + `/dispatch-candidates` + 管理端候选列表）
- **日期**：2026-10-17

**背景**

派单原来是纯人工：后勤从下拉里选一个人，服务端只校验「同租户 + 启用」，跨楼栋放行但留痕
（`docs/01` §4.2）。要解决的不是「自动派单」，而是**调度员看不到谁更合适**——
师傅的技能、负载、历史评分、负责楼栋分散在不同表里，选人靠记忆。

**决定**

1. **四个维度**：技能（是否擅长该类别）、满意度（历史平均评分）、负载（进行中单数）、
   距离（**楼栋归属的代理**：负责该楼栋 > 同区 > 跨区）
2. **权重走配置**：默认 技能 0.4 / 满意度 0.3 / 负载 0.2 / 距离 0.1（`repair.dispatch.weight-*`），
   总分按权重之和归一化——学校把权重改成 4/3/2/1 也不影响排序
3. **每个人返回四项得分 + 权重 + 人话说明 + 一句话理由**；前端渲染条形图，不自己算
4. **只排序，不自动派单**：派单仍走 `/dispatch` 由人点确认
5. **缺数据时中性降级**：没维护技能 / 没评价 → 0.5 中性分（新师傅不该永久垫底）；
   没设负责楼栋 → 距离按最差处理，并在明细里写明「未设置负责楼栋」

**数据从哪来**

| 维度 | 数据 | 说明 |
|---|---|---|
| 技能 | `worker_skill`（V10 新建） | 按报修类别标注，不是自由文本 |
| 满意度 | `ticket_evaluation.score` | 复用统计看板的「平均评分」口径，不另起一套 |
| 负载 | `ticket` 的 20/30/40 计数 | 一次 SQL 与满意度一起批量取（`DispatchMapper`） |
| 距离 | `worker_building` + `building.area` | **项目没有坐标，所以是业务代理，不是真实里程** |

**为什么不用机器学习模型**

- **数据量不够**：一所学校几十个师傅、几年的评价，训练不出可信模型；加权和在这个规模上是更稳的解
- **可解释性**：调度员要能问「为什么派他」——加权和可以逐项拆开，模型不能
- **维护成本**：模型要标注、重训、监控漂移；权重只要改配置

**为什么不做自动派单**（`docs/01` 的「明确不做」已经写明）

师傅请假、临时抽调、学校的特殊规则都要求人插手；自动派单会把「选错了」变成「要撤销的烂账」。
这也与 Agent / 分诊同一条哲学：**系统给建议、人做决定**。

**负面后果**

- 权重是**拍的**（0.4/0.3/0.2/0.1），没有数据支撑——所以做成配置并把明细摆出来，让学校按偏好调
- 「距离」是代理不是真实里程，跨区单的实际通勤成本可能被低估
- 技能需要人工维护；不维护只有中性分（有意为之：**缺数据不等于差**，但明细里会显示「未维护」）
- 满意度只看平均分，不看样本量——一条 5 星的师傅会和三十条 4.5 星的师傅接近，样本量的加权留待有数据后再说

**取舍说明**：这一条的核心不是「算法多聪明」，而是**把调度员的经验结构化成可检查的四个问题**
（干得了吗 / 干得好吗 / 现在忙吗 / 跑得值吗）。四项都能在界面上逐条核对，
这比一个说不清理由的排名更适合校园后勤这种"要跟人解释"的场景。

## ADR-020：租户配额、两级缓存、轻量指标——三个「够用就好」的取舍

- **状态**：已采纳（**已实现**：V11 + `TenantQuotaService` + `CacheConfig` + `MetricsRecorder`）
- **日期**：2026-10-18

### 一、租户配额用「账号数」，不用「工单数 / 存储量」

**背景**：多租户共用一套部署，"某个学校批量导入五千个学生"会拖垮所有人的库。配额是最便宜的一道闸。

**决定**：`tenant` 加 `max_students` / `max_workers`（`0` = 不限），建号与批量导入时校验，超限回 `30004`。
计数口径：`deleted = 0` 的**全部**账号（**含停用**）。

**为什么是账号数**：

- 计数走 `idx_tenant_type`，代价可忽略；而真正会把库撑坏的动作正是"批量导入"，账号配额正好挡在它前面
- 工单量 / 存储量属于**流量型配额**，更适合用限流与对象存储配额实现，且要实时统计，成本和复杂度都高得多

**两条实现细节**：

- **批量导入按整批校验**：一次导 500 个却只按 1 个校验，等于没有上限
- **不做并发强一致**：两个管理员同时建号可能各读到"还有一个位置"，最后超一两个。配额是保护性的**软上限**，
  不是计费凭证——为它加分布式锁不值得
- **停用也算占用**：停用不是删除，账号随时可能被重新启用；把停用当"空出位置"会让重新启用时悄悄超限

### 二、缓存只给「读得多、变得少」的两类数据

**缓存**：鉴权结果（用户 → 权限码 / 角色码，TTL 30 分钟）、启用中的报修类别（按租户，TTL 5 分钟）。

**不缓存**：工单、统计、通知——它们每次都可能不同，缓存只会制造不一致。

**为什么鉴权最值得缓存**：每个带 `@SaCheckPermission` 的请求都会回调 `StpInterface`，
原来每次都查 `sys_user_role` → `sys_role_permission` → `sys_permission` 三张表。

**实现上踩过的三个坑**（都写进了代码注释）：

1. **`@Cacheable` 的自调用不生效**：缓存方法必须是**另一个 Bean**（`AuthorizationCacheService`），
   否则 Spring 代理链断开，看着有缓存、实际每次回库，而且没有任何报错
2. **缓存 key 必须含租户**：`listEnabled(tenantId)` 把租户显式传进来，而不是在实现里取登录态——
   漏了就是把 A 校的字典返给 B 校（跨租户泄露）
3. **序列化必须读写对称**：Jackson 的默认类型信息**不写根数组的类型 id、读回来却要求**，
   报 `Could not resolve type id 'ticket:create'`。缓存值都是 `List<String>` / `List<CategoryVO>` 这类小对象，
   改用 **JDK 序列化**（天然对称），代价是 Redis 里看不出内容——可接受，缓存本来就是可丢的

**失效策略**：TTL 兜底 + **启动后清一次**（Redis 跨进程存活，`R__seed` 改了权限后必须作废旧口径，
见 `AuthorizationCacheBootstrap`）+ 类别的写操作 `@CacheEvict`。

**Redis 挂了不能让业务挂**：`CacheErrorHandler` 把缓存异常降级成"这次未命中"，
方法照常回库——与限流"Redis 故障时放行"是同一条原则：**缓存是加速器，不是正确性的依赖**。

### 三、可观测性只做「一个文本端点 + 两个业务指标」

**决定**：`spring-boot-starter-actuator` + `micrometer-registry-prometheus`，暴露
`health / info / metrics / prometheus`；**nginx 只反代 `/actuator/health`**，所以
`/actuator/prometheus` 只能从容器网络 / 本机访问。

**不上** Prometheus / Grafana 容器：2C2G 装不下，采集侧留给真正需要的时候（现在没有第二个服务要监控，
一个文本端点已经够"看一眼"）。

**只记两个指标**：

| 指标 | 标签 | 回答什么问题 |
|---|---|---|
| `repair.ticket.events` | `event`（动作枚举）、`tenant` | 平台在发生多少业务动作、哪个学校量大 |
| `repair.ai.calls` | `kind`（问数 / Agent 编排 / 维修建议）、`result` | AI 花了多少次调用（直接对应成本） |

**标签基数**：`event` 是封闭枚举、`tenant` 是个位数到几十——都不会撑爆时间序列。
**不要把工单号、用户 ID 加进标签**：那是时序库最常见的自杀方式。

**测试里的坑**：Spring Boot 3 在 `@SpringBootTest` 里**默认关闭可观测性导出**（`ObservabilityContextCustomizer`），
测试上下文里根本没有 Prometheus 注册表——`/actuator/prometheus` 恒 404。
在统一的 `IntegrationTest` 上加 `@AutoConfigureObservability`，**不要只加在某个测试类上**：
换注解组合会多起一个 Spring 上下文，而 Sa-Token 的静态字段在多上下文下会串（见该注解的类注释）。

**取舍说明**：这三件事都是"保护性设施"——配额防一个租户拖垮所有人，缓存防鉴权把数据库打满，
指标让"出没出事"不靠翻日志。它们的共同点是**都不改变业务语义**，所以可以独立于业务迭代。

## ADR-022：学校统一身份认证走「协议适配器 + 一次性登录码」，并自带 Mock IdP

- **状态**：已采纳（已落地：OAuth2 授权码 + PKCE、CAS、Mock IdP、平台配置接口）
- **日期**：2026-10-19

**背景**

账号方案是"统一初始口令 + 首登强制改密"，ADR-011 把"对接学校统一身份认证（CAS / 教务系统）"
记成将来的方向。真实场景里学生的身份本来就由学校认证体系统管——平台不该维护学生的口令。
阶段 7 把这个方向做成：**登录的第二个入口**，与账号密码并存。

约束：

1. **不引 Spring Security**（AGENTS §3）——它的过滤器链与自动装配会架空 Sa-Token 的登录态体系；
   Spring Authorization Server 是"做一个 IdP"，而这里要的是"接别人的 IdP"，方向相反；
2. **不新增依赖**：Spring 自带的 `RestClient` + JDK `HttpClient` 就够了（两种协议都是
   "两次 HTTP 调用 + 解析一个 JSON"）；
3. 每所学校一个 IdP（地址、协议、凭据都不同）；
4. H5 与小程序两端的能力要一致——但小程序端没有 `location`，SSO 需要 web-view 中转，
   本期先只做 H5 与管理端（见"不做"）。

**决定**

1. **协议适配器**：`SsoProvider` 只有两个方法（给浏览器授权地址、用回调参数换身份）。
   两个实现：`OAuth2SsoProvider`（授权码 + PKCE S256）、`CasSsoProvider`（ticket 校验，
   JSON 优先、XML 兜底）。新增协议 = 加一个 `@Component`，工厂自动收。
2. **登录编排复用账号密码那一套**：认证通过后不另写一套发 token 的逻辑，而是调
   `AuthService#completeLogin`（阶段 7 把它从 `login()` 里抽出来）——发 token、绑租户、
   写"待改密 / 用户类型"会话标记、写登录审计，全部同一处。这就是"SSO 只是第二个登录入口"的落地。
3. **token 绝不进 URL**：回调只带一个**一次性登录码**（Redis，默认 120 秒、`GETDEL` 消费），
   前端拿码换 token。state 同样一次性（默认 300 秒）。回调链接被重放、跨站登录伪造都被这一条挡住。
4. **平台不自动建号**：IdP 只证明"这个人是这所学校的 20260001"，账号必须先由学校在后台建好
   （配额、角色、数据权限都不该被外部认证系统绕过）。没有账号时明确提示"联系学校后勤"。
5. **配置在平台库**：`tenant_sso_config` 与 `tenant` 一样只存在于平台库——登录时还不知道该去哪个租户库
   （ADR-021）。平台运营（`tenant:manage`）维护；**密钥只回"是否已配置"**，不回显、不进审计。
6. **落点不可由请求指定**：成功/失败都只跳回配置里的 `admin_redirect_url` / `h5_redirect_url`，
   请求参数只能选 ADMIN / H5。否则这个接口就是开放重定向。
7. **自带 Mock IdP**（`/api/mock-idp/**`，默认关闭）：同时实现两种协议，让整条链路在本机与演示站
   能真跑通。它不做口令校验，所以**只能演示用**；关闭时所有端点 404。

**CAS 的一个坑（写在这里免得再踩）**

CAS 只回 `ticket`，不会把我们的 `state` 带回来。所以 **state 嵌在 `service` 的查询串里**
（`service = 回调地址?state=...`，CAS 会在后面追加 `&ticket=...`）。这要求学校的 CAS 对 `service`
的登记允许带查询串（多数按前缀 / 正则匹配，允许）。

**后果**

- 正面：登录从"只有口令"变成"口令 + 学校身份体系"；账号密码通道完全不受影响（同一套会话与审计）。
- 负面：
  - `client_secret` 存在平台库的**明文列**里（不是加密存储）。理由：当前部署是单实例、DB 访问本来就是
    最高权限；密钥管理服务（KMS）不在本期。接口不回显、审计不落，是这条的边界；
  - 平台运营配置的 URL 会被服务端请求（换取 token / 校验 ticket）——这是**可信运营者**的输入，
    不做 SSRF 防护；换成"学校自己填"就必须加白名单；
  - 统一认证登录同样受"首登强制改密"约束（本地口令可能还是初始口令），账号会被挡在改密页；
  - **小程序端未接**：只支持 H5 与管理端。
- 不做：自建 IdP；SAML；LDAP；小程序端 SSO；自动建号 / JIT 账号。

**取舍说明**：这一步买的是"校园系统对接能力"——真实交付时学校一定会问"能不能用我们自己的统一认证"。
做成适配器而不是写死某一种协议，是因为 CAS 与 OAuth2 在国内高校里各占一半，
而两者的差异只有"怎么问 IdP 要身份"这一层。

## ADR-021：租户隔离从「共享表 + tenant_id」升级为「每租户一个 database」

- **状态**：已采纳（**三步全部落地**：路由与建库、存量租户搬迁工具、定时任务按租户遍历；实现时改了两处边界、补了搬迁的校验与切换细节，见文末「落地时的修正」）
- **日期**：2026-10-18

**背景：现模型强在哪、弱在哪**

现状是"共享库 + 共享表 + `tenant_id` 列"：`ticket` / `notification` 由拦截器统一注入租户条件，
**其余表靠 400 多处手写 `tenant_id`**（AGENTS §5.6）。写得对，隔离就成立；**漏写一处，就是静默的跨租户读写**。

而学校侧有两类共享表答不了的需求：**"我们学校的数据能不能单独备份/导出/迁走"**、
**"你们升级能不能不影响其他学校"**。

**决定**

1. **一台 MySQL 实例上，每个租户一个 database**（`repair_t1`…）。不拆实例、不分片——资源仍是共享的，
   这一点必须在文档里说清楚：**拿到的是"数据与结构互不干扰"，不是"性能互不干扰"**。
2. **控制面留共享库 `repair`**：`tenant`、`sys_user`、`sys_user_role`、`sys_role`、
   `sys_permission`、`sys_role_permission`。理由：登录时**还不知道**该去哪个租户库，
   必须先按 `tenantCode` 定位租户、再验证账号；把账号表拆进各租户库会把登录变成"先猜库"。
3. **数据面进各租户库**：`ticket` / `ticket_log` / `ticket_evaluation` / `ticket_collaborator` /
   `building` / `worker_building` / `worker_skill` / `ticket_category` / `repair_code` /
   `notification` / `audit_log` / `knowledge_entry`。
4. **路由**：每租户一个 `HikariDataSource`（**懒建 + 小池 + 空闲回收**）+ `AbstractRoutingDataSource`，
   lookup key = 登录态里的 `tenantId`；**`lenientFallback = false`**——未知租户直接报错。
5. **每租户一个数据库账号**（只授它自己那个库）：第二道防线。路由写错时表现为"无权限 / 表不存在"的**报错**，
   而不是安静地读到别家的数据。
6. `tenant_id` 列**保留**（双保险），现有查询一条不用改；**无登录态的定时任务改为遍历所有租户**。
7. **存量数据迁移**：
   a. 新租户：建库 → Flyway 跑数据面迁移 → 建租户账号；
   b. 存量租户：建库 → Flyway 建表 → **分批搬数据**（`INSERT INTO 新库.表 SELECT … FROM 共享库.表 WHERE tenant_id=?`）
      → 校验（行数 + 关键列校验和）→ 切它的路由 → 观察；
   c. **切换用"停写窗口"，不做双写**：本项目的部署是单实例、可短暂停写；双写的复杂度与一致性风险
      远大于几分钟不可写。共享库保留到确认后再归档。
   d. 每个租户独立可重跑：某校搬到一半失败，只影响它自己。

**spike 实测（2026-10-18，两个临时库，跑完即删）**

- **Flyway × N**：Flyway 11.7.2 + `flyway-mysql` 对两个空库各跑出 **12 条历史**（V1..V11 + `R__seed`），
  关键表都建出来；对已迁移的库再跑一次 `pending = 0`；动 A 库的历史不影响 B 库。
  → 结论：**每租户库各自跑迁移这件事成立**。
- **路由不串库**：每租户一个池、**每个池只给 1 条连接**（故意逼复用），A → B → A 依次切换，
  每次读到的都是自己的数据；`lenientFallback = false` 时未知租户抛
  `Cannot determine target DataSource`。
  → 结论：**每租户独立池 + fail-closed 可以做到不串库**。
- **反例**：默认的 `lenientFallback = true` 会把未知租户**静默**路由到默认库（实测读到了默认库的数据）——
  这正是"配错了也不报错、只是读到别家数据"的形态，实现里必须显式关掉。
- **附带发现**：`R__seed.sql` 里含着平台与租户 1 的行。正式实现要把迁移脚本拆成
  **控制面**与**数据面**两套：数据面种子只建该租户的类别/楼栋等，不建平台租户与角色。

**代价与边界（写在这里，避免被当成遗漏）**

- **连接预算**：2C2G 上不能"每租户一个 12 连接的池"。方案是模板小池（2~3 条）+ 懒建 + 空闲回收，
  池数 = 活跃学校数；容量估算写进部署文档。
- **跨租户能力**：平台域本来就不看业务数据（ADR-012），AI 问数只在租户内——这一点让本方案在本项目里成本很低；
  若将来要做"跨学校对比报表"，要单独设计（控制面聚合或跨库 UNION）。
- **AI 只读账号**：每租户一个账号，只授它自己库的白名单表；`sys_user` 在控制面，
  AI 查询引用它时要带控制面库名前缀，由 `SchemaWhitelist` / 网关统一处理（实现时补）。
- **工作量的大头不是路由**，而是**迁移工具 + 按租户切换 + 验证**；路由代码本身只有一两百行。

**不做**

- 每租户一个实例（成本、运维是另一个量级）；
- 分片、读写分离；
- "边跑边迁"的双写切换（用停写窗口，简单可控）。

**取舍说明**：这一条买的是**运维与合规能力**（逐租户升级 / 备份 / 导出 / 下线，串库会报错），
不是性能。对本项目"少数几所学校"的规模，共享表本来也够用；做它的理由是：
学校会问"数据能不能单独给我们"，而这是共享表答不了的。

**落地时的修正（2026-10-18，第 1 步「路由与建库」实现完之后）**

写这一节是因为**实现时改了两处边界，原因都是"动手才看得见"的事实**。上面「决定」里的 1、6、7 不变。

**修正一：租户库装**完整**的租户侧 schema，不再按「控制面 / 数据面」切账号与角色。**
原方案是"账号与角色留在共享库、只把业务表搬走"。落地时发现它会在三个地方产生跨库读写：

- 统计看板按师傅分组要 `JOIN sys_user`（`StatisticsMapper.xml`），工单在这边、姓名在那边；
- 通知要按角色反查收件人（`sys_role` / `sys_user_role`），而发通知是在工单事务里；
- 学生 / 维修工列表、派单评分都要连 `sys_user` 与 `worker_skill` / `worker_building`；
- 更要紧的是**事务**：账号与审计经常在同一个业务动作里一起写（建号即留痕），跨库就没有原子性——
  而 MySQL 没有 XA，只能靠补偿，等于把"一次动作"拆成两段还要自己兜底。

改成"租户库装完整一套"之后，租户的一次业务就是**它自己库里的一个事务**，上面四条全部消失。
角色与权限是**平台内置行**（`tenant_id = 0`），在平台库与每个租户库里各有一份同样的副本，
由可重复迁移 `db/tenant/R__seed.sql` 保持同步（应用启动时为每个租户库跑一遍）。
这样 `SchemaWhitelist` 与 AI 的 SQL 网关**一个字都不用改**（下面「代价与边界」里那条"要带控制面库名前缀"作废）。

**修正二：路由不用父类的 `targetDataSources` 映射，改成显式覆盖 `determineTargetDataSource()`。**
`AbstractRoutingDataSource` 的映射是 `afterPropertiesSet()` 时的**快照**，而租户池是**运行时懒建**的
（今天开通的学校，明天才有人访问），快照装不下；而它的 `lenientFallback` 语义正是"找不到键就用默认库"。
现在路由决策写成三段显式代码：键为空 / 键=平台库 → 平台库；否则 → 那个租户的池。
**没有第四段**，所以它比 `lenientFallback = false` 更严（spike 里那条反例守的就是这件事）。
校验被前移到了 `TenantSchemaCatalog`：租户不存在直接抛 30003，绝不回落到平台库。

**落地时明确推迟的两件事（不是忘了）**

- **每租户一个数据库账号**（原决定 5）：它要有一套凭据保管与轮换机制（口令存哪、怎么改），
  而当前部署的应用账号本来就有全部库的权限，加了账号也挡不住"路由写错"。**隔离现在靠路由 + `tenant_id`
  两道，靠的是"报错"而不是"权限不够"**。推迟到有凭据管理之后。
- **每租户数据库账号**（原决定 5）之外的推迟项已经没有了：**第 3 步（定时任务按租户遍历）已落地**，
  所以把在用的学校切过去是安全的（下面补了它的三条实现细节）。

**落地之后的结构（一份速查）**

| 东西 | 在哪 | 说明 |
|---|---|---|
| `tenant`（学校名录） | 只在平台库 | 登录第一站要先按编码找到学校，才知道去哪个库 |
| 平台账号（`tenant_id = 0`）、平台自己的审计 | 平台库 | 平台运营不进任何学校的库 |
| 学校自己的账号 / 角色 / 授权 / 业务表 / 审计 | 它自己的库 | 17 张表，含 `sys_user` / `sys_role` / `sys_permission` |
| 迁移脚本 | `db/migration`（平台库）与 `db/tenant`（租户库） | 两套独立历史；**改表结构要改两处**，有 `TenantSchemaParityTest` 逐列逐索引比对 |
| 路由键的来源 | `tenant.db_schema` → `TenantSchemaCatalog`（带缓存） | 全链路唯一一处"把 tenantId 翻译成库名" |
| 请求上的路由键 | `TenantRoutingInterceptor`（order **-1**，最早） | 必须在登录校验之前：注解鉴权本身就要查租户库里的角色表 |
| 平台运营操作某个学校 | `TenantRoutingContext.call(库名, …)` | 例如"给它加一个管理员"：账号写它的库，审计写平台库 |

**第 2 步（搬迁工具）落地时补的三条细节**

1. **校验要逐表、要看内容，不能只数行数**：行数只能发现"少搬了"，发现不了"搬串了"——
   `INSERT INTO 新库.表 SELECT * FROM 平台库.表` 是按**列位置**映射的，两侧列顺序一旦不同就会静默错位。
   所以校验先比对两侧的列结构（列名 / 顺序 / 类型），再比 `COUNT(*)` 与**全列校验和**
   （`SUM(CRC32(每行各列拼起来))`）。它挡三类事故：漏搬、源库在搬完之后又被写过、两侧建表脚本漂开。
2. **切换前必须再校验一次，不一致就拒绝**（而不是"相信上次搬完的结果"）：这中间可能隔了几小时，
   而源库一直在接写入。预检放在切换里，是"切换是唯一改变行为的一步"这条性质的直接推论。
3. **切换窗口用内存标记挡住该校请求**（而不是只靠"操作时没人用"）：翻转那几秒里该校的请求直接返回
   `10005` + "正在切换数据库，请稍后重试"。挡的是**该校**，平台运营自己不受影响——否则这一步就没法执行。
   用内存集合而不是 Redis：单实例部署，它只活几秒，放 Redis 反而要多考虑"进程崩了谁清标记"。

**搬迁工具的接口形态**：三个平台接口（`GET .../database`、`POST .../database/copy`、
`POST .../database/switch`）而不是命令行脚本——它是平台运营的日常动作，与"开通学校"同一类，
用同一套鉴权（`tenant:manage`）与审计（新增动作码 `TENANT_DATABASE_COPY` / `TENANT_DATABASE_SWITCH`）。
**复制阶段可以在学校正常使用时做**（源库只读、不加锁），切换才需要几秒的安静时刻。

**第 3 步（定时任务按租户遍历）落地时补的三条细节**

1. **延迟队列的成员带"租户 ID"而不是库名**：调度器没有登录态，消费一条任务时要知道去哪个库；
   而成员是**登记当时**写下的，学校搬家之后那个库名就不对了。存租户 ID、消费时经
   `TenantSchemaCatalog` 解析成**当前**库名，切换前后登记的任务都会落到正确的库上
   （成员格式 `租户|工单`，上线前的老成员只有工单 ID，按平台库处理——那批学校都还没搬家）。
2. **兜底扫描逐库跑**：一次 SQL 只能看到一个库，所以每轮对"平台库 + 每个已搬家的学校库"各扫一次
   （每个库在自己的路由键下执行）。扫出来的任务带着 `tenant_id`，处理时再解析成当前库名——
   即便扫到搬家前留在平台库的旧副本，处理也会落到那所学校**现在**的库上。
3. **处理逻辑按任务所属租户钉路由**：`TicketTimeoutHandler` 的每个回调先解析库名、再整段处理
   （工单 / 流转日志 / 通知 / 指标都在同一个库里）。演示重置同理（租户行在平台库读，演示数据写进
   这所学校自己的库）。**这一条之所以只改几十行，是因为租户库装的是完整的一套**（修正一）——
   处理逻辑一个字没改，只是"连到哪个库"变了。

**新增的四个约束（写进 AGENTS §6）**：改租户侧表结构要改两份脚本；`tenant` 表的读写一律钉在平台库上
（`TenantRoutingContext.callControl`）；**不许在事务里换租户**（换不了连接，只会静默写错库——
`TenantRoutingContext` 会直接拒绝这种写法）。

## ADR-005：AI 框架选 LangChain4j，且不引入它的 Spring Boot starter

- **状态**：已采纳（**已引入**：`langchain4j-open-ai:1.20.0`，模型接入已落地）
- **日期**：2026-09-11

**背景**

AI 数据助手要做的链路是「自然语言 → Schema 检索 → 生成 SQL → 安全网关校验 → 执行 → 出图与结论」。其中用到框架能力的只有「模型对话 + 结构化输出」和「Schema 检索（向量检索）」，其余全是自己要写的工程逻辑。要定两件事：用哪套框架，以及怎么和 Spring Boot 集成。

**备选方案**

1. **Spring AI**：Spring 官方项目，与 Boot 自动装配一体，`ChatClient` 作统一入口；DeepSeek 兼容 OpenAI 接口，只改 base-url 即可
2. **LangChain4j**：生态更广，`AiServices` 声明式接口，对话记忆与 RAG 组件更成熟，接入的模型更多
3. **不用框架**：直接手写 HTTP 调 DeepSeek 的 chat/completions

**决定**

选 LangChain4j；但**不引入它的 Spring Boot starter**，只引入稳定的核心模块，自己写配置类构造 Bean。

**理由**

- 这个项目的 AI 部分很薄——两套框架在这里都只负责「把自然语言变成一条 SQL 字符串」，真正的技术在 Schema 检索、结构化输出提示词和 SQL 安全网关（见 ADR-003）。所以选择标准不是「谁更强」，而是「能力够用的前提下，谁的心智负担和长期维护成本更低」
- 后续要做 Schema 检索，LangChain4j 的 `AiServices`、对话记忆、RAG 组件更成熟，能直接复用，不必自己拼装
- **不引 starter 是因为它目前只有 beta**：核心 `langchain4j-open-ai:1.20.0` 是稳定版，而官方 Spring Boot starter 最新只到 `1.20.0-beta30`。本项目只需要一个 ChatModel Bean，用 `@Configuration` + `OpenAiChatModel.builder()` 二十来行就能替代 starter 的能力，不值得为此引入一个 beta 依赖
- DeepSeek 没有专用模块，官方推荐用 open-ai 模块 + 自定义 baseUrl（`https://api.deepseek.com/v1`），LangChain4j 的文档与集成测试就是这么用的
- 方案 3 被否：省掉一个依赖，但流式输出、结构化输出、重试都要自己写，且后续加 RAG 等于自己造轮子

**后果**

- 正面：
  - 后续 RAG / Schema 检索有现成组件，不用自己造
  - 只有稳定的核心模块进依赖树，没有 beta 依赖，升级节奏可控
  - 接入方式仍是配置驱动（base-url / api-key / model-name 走既有 `AI_MODEL_*` 环境变量），换模型不用改代码
- 负面：
  - 手写 `@Configuration` 构造 ChatModel，比引 starter 多约 20 行代码；等 starter 出稳定版可以再评估切回去
  - 没有 starter 就没有 `langchain4j.*` 配置属性绑定，模型参数（超时、温度等）得在配置类里自己从环境变量读
  - LangChain4j 声明 Jackson 2.22.x，而 Spring Boot 3.5.16 统一管理到 2.21.4，实际会用 2.21.4（同属 2.x，兼容）；若将来遇到 `NoSuchMethodError`，再把 `jackson-bom` 提到 2.22.x
  - 放弃了 Spring AI 的官方自动装配与 Spring 生态的一体化集成

**取舍说明**：框架改过一次——最初文档写的是 Spring AI，后来改用 LangChain4j，因为后续要做 Schema 检索，它的 RAG 组件更成熟。但没连 starter 一起引：核心是稳定版、starter 只有 beta，而这里只需要一个 ChatModel Bean，二十行配置类就能省掉一个 beta 依赖，这笔账划算。DeepSeek 没有专用模块，走 open-ai 模块加 base-url 就是官方用法。

**落地时的修正**（2026-09-25，引入依赖时实测的）

上面说"只有稳定的核心模块进依赖树，没有 beta 依赖"——**这句话不完全对**，实测依赖树是这样：

```
dev.langchain4j:langchain4j-open-ai:1.20.0
├── langchain4j-core:1.20.0
├── langchain4j-http-client:1.20.0
├── langchain4j-http-client-jdk:1.20.0 (runtime)   ← JDK HttpClient，没引 OkHttp / Retrofit
├── langchain4j-reactive-streaming:1.20.0-beta30   ← ⚠️ 这个还是 beta
├── jackson-annotations 2.21 / core 2.21.4 / databind 2.21.4（与 Boot 管理的一致，无冲突）
├── com.knuddels:jtokkit（token 计数）
└── io.smallrye.reactive:mutiny-zero
```

- **starter 确实避开了**（它仍是 beta），但 open-ai 模块**自身**会强制带进一个 beta 的 reactive-streaming（compile 作用域、非 optional）
- 没把它 exclude：`OpenAiChatModel` 的类型签名里就有该模块的流式接口，排掉它可能在类加载时就炸（而且流式问数正要用它）。所以选择"接受 + 在这里写清楚"，而不是让文档继续声称依赖树里没有 beta
- 顺带确认了两件好事：Jackson 冲突没有发生（ADR 里预判过这个风险），HTTP 客户端走 JDK 自带、没引 OkHttp/Retrofit 那套
- **没有用 `AiServices` 的注解式接口**（上面提过它的组件成熟）：系统提示词要按从库里读出来的表结构动态拼，而注解的值只能是编译期常量，硬套就得把提示词绕成 `{{变量}}` 模板传参。所以直接发 `SystemMessage` + `UserMessage` 两条消息，提示词在代码里一眼可见——少一层需要理解的黑箱
- **模型客户端懒建、不参与启动**：没配 Key 时应用照常起，第一次问数才报 `40004`（与"应用启动不依赖 MinIO"同一条原则）。实测：不带 Key 启动上下文正常

## ADR-006：超时升级用同一套 ZSet 机制按节点实现；统计不建表、超时口径以动作记录为准

- **状态**：已采纳（**已实现**，M3）
- **日期**：2026-09-15

**背景**

M3 要做三件事：24h 未接单提醒、48h 未处理升级、验收超时自动关；外加统计看板（报修量、时长、超时率、满意度、师傅工作量）。两个问题需要先定：① 三条超时规则怎么组织，避免三套实现；② 统计里的"超时"怎么算，以及要不要为统计建汇总表。

**决定**

1. **三个超时节点共用一套机制**：Redis ZSet（ADR-001）按节点分 key（`ticket:timeout:{ACCEPT|PROCESS|EVAL}`，member = ticketId、score = 到期毫秒），秒级消费 + 每分钟兜底扫描；节点在业务流转处登记（派单登记 ACCEPT、接单登记 PROCESS、评价登记 EVAL），节点完成或到达终态时取消。
2. **超时动作一律"记一笔 ticket_log + 发通知"，只有验收超时会改状态**（50 → 60）：
   - `ACCEPT_TIMEOUT` / `PROCESS_TIMEOUT`：不是状态跃迁，记 `20 → 20` / `30 → 30` 的日志（与"到场 30 → 30"同一手法）
   - `AUTO_CLOSE`：真正的状态跃迁，操作者 = 0（系统）
   - **幂等靠 ticket_log 判重**：兜底扫描每分钟都会扫到同一批超期工单，不判重会把管理员刷屏
3. **不为统计建汇总表**：统计全部从 `ticket` / `ticket_evaluation` / `ticket_log` 现算，SQL 写在 Mapper XML。
4. **统计的"超时"以 ticket_log 里的超时动作为准**，不在统计 SQL 里重算阈值。
5. **阈值全部可配**（`REPAIR_TIMEOUT_ACCEPT_MINUTES` / `PROCESS_MINUTES` / `EVAL_MINUTES`），通知正文按实际阈值生成（演示调到 1 分钟时不会说谎成"24 小时"）。

**备选方案与放弃原因**

| 备选 | 为什么不用 |
|---|---|
| 三条规则各写一个定时任务扫库 | 三份重复逻辑；分钟级精度；库压力随工单量线性增长（ADR-001 已否掉轮询） |
| 统计建日汇总表（定时跑批写入） | 当前量级没有收益，却引入"汇总与明细不一致"和补数问题；真需要时再加汇总表/物化视图 |
| 统计 SQL 里直接用阈值算超时（`TIMESTAMPDIFF(...) > 阈值`） | 阈值可配置，抄进 SQL 后两处会悄悄漂移；且"已超阈值但调度器还没处理"的工单会被算成超时 |
| 超时直接改状态（如未接单自动转派） | 自动转派会绕过"谁负责哪栋楼"的人工判断；MVP 先提醒人，决策权留给后勤 |

**后果**

- 正面：三个节点只有一份机制与一份幂等实现；看板口径与超时动作同源（都来自 ticket_log），不会出现"看板说超时、日志里查不到"的矛盾；不新增表、不新增依赖（Excel 导出留到 P1）。
- 负面：
  - **"超时动作会写 ticket_log"成了隐含约定**，改判重逻辑时要连日志语义一起看
  - 超时率偏乐观：工单若在调度器触发前就被人工处理，不计入超时（有意选择——以实际发生的动作为准）
  - ZSet 按节点分 key 后，"取消该工单全部超时"要删多个 key（当前 3 个），新增节点时必须同步加进 `cancel`
  - 兜底扫描是全表跨租户的，会扫到历史遗留工单；处理方（调度器）必须容忍"状态已不是预期"并跳过
  - **兜底扫描的成本约束**（2026-09-16 补齐，见 ADR 后续修订）：三条扫描都必须带"状态过滤 + 单轮 LIMIT"，
    评价那条还要 JOIN `ticket` 限定 `status = 50`——少了状态过滤，已处理的工单会被每分钟重复扫到、
    结果集只增不减；少了 LIMIT，一次会把历史上所有超期工单拉进内存。这两点曾只承认了"正确性代价"而漏了"成本代价"
  - **登记基准必须与兜底基准一致**：曾出现 ZSet 用"接单时刻 + 48h"、兜底用"派单时刻 + 48h"的漂移，
    被兜底"先赢 + 日志判重"掩盖着；现在 `registerProcess` 显式接收 `dispatchTime` 作为基准

**取舍说明**：最初想给统计建日汇总表，理由是"看板要快"；但当前量级明细现算完全够（`idx_tenant_status` 覆盖大部分查询），而汇总表会带来对不上的风险。另一处纠结点是超时口径——用时间戳重算更"精确"，但阈值可配置后两处必然漂移，而且看板会显示"超时"却在日志里找不到对应的提醒。最后选了同源口径：**看板上的每个超时，后台都能找到那笔触发它的日志**——解释得清比算得准更重要。

## ADR-007：前端先与后端同仓（单仓），但守住边界以保留拆分路径

- **状态**：已采纳（**部分实现**：管理端脚手架就绪，页面开发中）
- **日期**：2026-09-15

**背景**

项目最初只规划了后端工程，但 `nginx/nginx.conf` 与 `docker-compose.yml` 早就按"单仓"写好了——挂载 `./web-admin/dist` 与 `./miniapp-h5/dist`，`docs/05` 也有一句"本地构建前端"。真正要做前端时，需要定：与后端同仓库，还是各自一个仓库。

**备选方案**

1. **单仓**：`web-admin/`（Vue 3 管理端）+ `miniapp-h5/`（uni-app）放在本仓库根目录，与后端平级
2. **前端独立仓库**：`repair-admin` / `repair-h5` 各一个
3. **不做前端**：交付定位为"后端 + Knife4j 接口文档"

**决定**

选方案 1（单仓），但把"将来可以便宜地拆成独立仓库"作为硬约束写进 `AGENTS.md` 3.1。

**理由**

- **现有部署链路就是按单仓写的**：nginx 的两个 location、compose 的两个 volume、部署文档的构建步骤都指向仓库内的 `dist` 目录；选方案 2 要先付一笔返工成本
- 这个项目的使用场景是"别人 clone 下来能跑通完整系统"（面试/演示），**单仓让"打开仓库 30 秒"的检验最容易过**；分仓会让人在后端仓库里看不到前端
- 前端两个工程本就是独立技术栈（Vue 3 后台 vs uni-app），放一起不会互相纠缠——"单仓"只是同一个 git 仓库，不是合并成一个工程

**代价与对策**

| 代价 | 对策 |
|---|---|
| 仓库变重、history 混在一起 | Commit scope 固定 `admin` / `h5`，将来按路径切分历史时是天然分界 |
| 后端 CI 可能被前端拖慢 | 前端 CI 独立成 workflow、按路径触发；后端构建里不出现 Node |
| 将来拆分要改部署配置 | 现在就明确边界（各带 package.json、不互相引用、产物不进后端 jar、后端不依赖前端），使拆分只改 nginx / compose / 部署文档三处 |

**将来真要拆的时候（保留的路径）**

```bash
git subtree split -P web-admin  -b admin-only   # 带历史切出
git subtree split -P miniapp-h5 -b h5-only
```

然后：新仓库接收 + 改 `nginx/nginx.conf` 挂载点 + 去掉 `docker-compose.yml` 两个 volume + 更新 `docs/05` 构建步骤 + **在 README 里补前端仓库链接**（否则又回到"打开仓库看不到全貌"）。

**负面后果**

- 单仓里后端测试与前端构建是两套工具链，新人容易搞混"提交前该跑哪个"（已在 AGENTS 第 8 节写清）
- 根目录会多出 `node_modules`（进 `.gitignore`）；前端变大后 clone 时间会明显增加——那时就是拆分的信号
- 这条决策**有过期条件**：当"前端构建拖累日常开发"或"前端需要独立发布节奏"时，就该执行上面的拆分

**取舍说明**：纯从架构洁癖看，分仓更干净；但当前阶段（一个人、演示型项目）"能跑通、能演示、边界清楚"比"部署链路解耦"更重要。所以选择用**边界约定**换**拆分自由**：现在省事，将来也不被动。

## ADR-008：租户与角色两层范围条件收敛到同一个拦截器，租户先注入

- **状态**：已采纳（**已实现**）
- **日期**：2026-09-16

**背景**

数据权限拦截器（ADR-002）只实现了角色维度：学生=本人、维修工=负责楼栋、**后勤=不限制**。
（2026-09-27 补：维修工这一条后来扩成「负责楼栋 **或** 派给自己的单」——可见范围必须与操作权一致，否则跨楼栋强制派单会造出没人能操作的单，见 `docs/01` §4.2。）
"不限制"在字面上等于"跨租户全可见"——虽然当时是单租户演示，但 `tenant_id` 字段从 M1 起就在每张表上，
`docs/01` 也写着"多租户隔离走同一层拦截器，在数据权限条件之前注入"，**文档在描述一个还没实现的行为**。

更麻烦的是第二轮评审指出的对比：M3 新增的统计模块**自己手写**了 `t.tenant_id = #{tenantId}`，
于是同一仓库里出现两套可见范围规则（ticket 主链路无租户维度、通知按 receiver_id、统计按租户），
面试被问"多租户怎么隔离的"时，文档答案和主链路代码对不上。

**备选方案**

1. **用 MyBatis-Plus 的 `TenantLineInnerInterceptor`**：框架自带，配一个 `TenantLineHandler` 即可
2. **在现有 `TicketDataScopeHandler` 里加租户维度**，与角色条件 AND 起来
3. **每个 Mapper 手写 tenant_id 条件**（= 统计模块现在的做法，推广到全项目）

**决定**

选方案 2。

**理由**

| 维度 | MP 租户插件（1） | 扩展现有 handler（2） | 手写（3） |
|---|---|---|---|
| 与角色条件的顺序 | 两个插件叠加执行，顺序靠配置约定，容易配错 | **同一个方法里显式 AND，顺序即代码** | 靠人记住 |
| 系统上下文（定时任务要跨租户） | 需要额外的忽略名单 | 已有"无登录态不注入"的分支，天然支持 | 各自判断 |
| 改动面 | 新增插件 + 处理器 + 配置 | 改一个类 + 登录时写一次 Session | 每个查询改一遍，且会漏 |

关键点：**租户是第一层，角色是第二层**。后勤管理不再"跨租户全可见"，而是"本租户内不受限"——
这个语义差别正是之前文档与实现对不上的地方。

**配套**

- 登录时把 `tenantId` 写进 Sa-Token Session（`CurrentTenantService.bind`），拦截器与统计都从 Session 读：
  否则每个请求都要多查一次 `sys_user`（评审也点了这条）
- `dispatch()` 增加"师傅必须属于本租户"校验；跨租户师傅与"不存在"返回**同一个错误**，不泄露别家资源的存在
- 统计 SQL 保留显式的 `t.tenant_id` 作为双保险，注释说明"拦截器也会注入，这里是显式声明"

**后果**

- 正面：新增接口**默认安全**（不写任何条件就自带租户隔离）；文档、主链路、统计三处口径统一；
  "多租户怎么做的"可以答："一个拦截器管两层，租户先注入"
- 负面：
  - 拦截器每请求要拿一次登录态与租户 → 用 Session 缓存换掉了查库，但 Session 缺失时会回查一次（自愈分支）
  - **系统上下文仍不注入**（定时任务要跨租户处理），所以"系统上下文可以跨租户"这件事必须继续写在注释里，
    否则将来有人以为所有查询都自动带租户
  - 测试数据必须显式给 `tenant_id`（懒省事直接插库的脚本要注意）

**取舍说明**：MP 自带的租户插件看起来更"标准"，但它与角色条件是两个插件、顺序靠约定，
而这里恰恰需要"租户严格先于角色"的语义；且系统上下文要跨租户，用插件反而要额外写忽略名单。
扩展同一个 handler 让两层条件的顺序写在代码里，读代码就能确认，比拼配置更可靠。

## ADR-009：报修码接口用「Redis 固定窗口 + 注解」限流，且 Redis 故障时放行

- **状态**：已采纳（**已实现**：`RateLimit` 注解 + `RateLimitInterceptor`，挂在 `GET /api/tickets/by-code/{code}` 与 `POST /api/worker/tickets/{id}/arrive`）
- **日期**：2026-09-16

**背景**

报修码是 6 位数字、租户内唯一（ADR-004）。这意味着它同时是：

1. **位置信息的钥匙**——查到一个码就知道某栋某房间存在（校园场景下算隐私）
2. **全项目唯一可以被"猜"出来的凭证**——其余接口的入参要么是雪花 ID（19 位，猜不出来）、要么需要密码

`docs/01` §5 把"报修码随机生成、防枚举"写进了非功能需求，但 M2 落地时只实现了**前半句**：
码确实随机（迁移脚本 `R__seed.sql` 里那几个是演示用固定码），**防枚举没有实现**——一个登录账号
写个脚本就能把六位数字空间跑一遍。这是"需求写了、代码没做"的缺口，比没写需求更危险，
因为它会让人以为已经防住了。

**备选方案**

1. **Nginx `limit_req`**：在入口挡住，不消耗应用资源
2. **Guava `RateLimiter` / Bucket4j 单机内存限流**：加个计数器，零外部依赖
3. **Sentinel / Spring Cloud Gateway**：能力最全，带控制台
4. **Redis 固定窗口（Lua `INCR` + `EXPIRE`）+ 注解标记接口** ← 选定
5. **数据库计数**：每次请求一条 SQL 统计窗口内次数

**决定**

选方案 4。

**理由**

| 维度 | 1 Nginx | 2 单机内存 | 3 Sentinel | 4 Redis + 注解 | 5 DB 计数 |
|---|---|---|---|---|---|
| 计数维度 | **只能按 IP** | 按用户 | 按用户 | **按用户** | 按用户 |
| 多实例部署 | 正确 | **每实例各一份，实际阈值 ×N** | 正确 | 正确 | 正确 |
| 新增依赖 | 无（改配置） | 新增库 | **新增库 + 组件** | **无** | 无 |
| 本地/测试可见 | **绕过 nginx 就没有限流** | 有 | 有 | 有 | 有 |
| 每请求成本 | 无 | 无 | 低 | 一次 Redis 往返 | **一次 SQL** |

关键取舍有两处：

- **按用户而不是按 IP**：这个接口**必须登录**（docs/03 §4），所以"用户"是天然维度，且比 IP 准
  （校园网大量 NAT，按 IP 限流会误伤同网段的其他学生）。Nginx 的 `limit_req` 恰好只能按 IP，
  所以它在"能挡住谁"这件事上并不比应用层强；又因为它是配置而非代码，测试环境（直连 8080）
  根本不存在限流——**限流必须能在测试里被验证**，否则就是"文档写了、实际不确定"。
- **为什么不用滑动窗口/令牌桶**：固定窗口在窗口边界理论上允许 2 倍突发（这一分钟最后一秒打满、
  下一分钟第一秒再打满）。但这里的目标是"防枚举"——把 100 万次尝试的成本从几分钟抬到几天，
  边界处多放 60 次对这个目标毫无影响；而滑动窗口要在 ZSet 里存每个请求的时间戳，
  内存与两次往返的开销换来的精度在这里没有价值。

**配套**

- 计数键 = `rate:{登录用户}:{Controller.method}`。**不能用 `requestURI`**：路径里带着用户这次
  尝试的报修码，用它当键会让每次猜码各自独立计数，限流等于不存在（`RateLimitTest` 有一条
  用例专门守着这件事）
- `INCR` 与 `EXPIRE` 写在**一段 Lua** 里：分两次调用时，那个把计数从 0 变 1 的请求若在两步之间
  失败，键就永久没有 TTL，这个用户会被自己的计数一直挡在门外
- **Redis 不可用时放行**，而不是"计数失败就拒绝"。这条同时写进 `docs/01` §5 的降级策略：
  限流防的是滥用、不是业务正确性，为了它把扫码报修整条链路拦住，代价远大于收益
- 阈值集中在 `RateLimitRule`（`REPAIR_RATE_LIMIT_MAX_REQUESTS` / `_WINDOW_SECONDS`，默认 60/60s），
  **不写在注解上**：阈值是按环境调的运行参数（演示/压测会放宽），写进注解就成了编译期常量
- 两个拦截器的 order 显式写死（Sa-Token 0、限流 1）：限流按登录用户计数，必须先有登录态
- 到场接口的请求体里也带报修码（服务端要复核，否则前端比对等于没比对），所以同样标注限流

**后果**

- 正面：`docs/01` 的"防枚举"从文档变成可执行、可测试的行为；超限统一返回已预留的 `10004`，
  **没有新增错误码**；不引入任何依赖，Redis 本来就是硬依赖（Sa-Token / 延迟队列 / 工单号都在用）
- 负面：
  - **按用户计数挡不住"批量账号"**——换个账号就是新桶。真正的防线是"码随机、不可枚举"（ADR-004），
    限流只是把成本抬高；这条要继续讲清楚，不能吹成"防住了"
  - **固定窗口边界可突发**（最多 2× 阈值），是有意接受的精度损失
  - Redis 故障期间不限流（有意的降级），即"Redis 挂掉 = 这道防线暂时消失"
  - 阈值按"接口方法"分桶，同一个人在两个接口上各有 60 次额度；若要"同一用户跨接口合计"，
    需要给注解加 `key()` 属性并改计数键——目前没有这个需求

**取舍说明**：这道限流的定位是**抬高枚举成本**，不是"安全边界"。所以凡是在"更准"与"更简单、
更可验证"之间冲突的地方，都选了后者（固定窗口而非滑动窗口、应用层而非网关、放行而非拦死），
并在 ADR 里把代价写出来。真正的安全边界是码的随机性与"一房一码由应用层保证"（ADR-004）。

## ADR-010：表结构交给 Flyway 管，`docs/schema.sql` 退役

- **状态**：已采纳
- **日期**：2026-09-22

**背景**

表结构一直由一个 `docs/schema.sql` 负责：它挂在 MySQL 容器的 `docker-entrypoint-initdb.d` 上，**只在数据卷为空时执行一次**。这个安排在第一台机器上很好用，但项目已经部署到公网，问题就露出来了：

- **库里一旦有数据，改表就只剩"手工进容器 ALTER"这一条路**：没有版本、没有记录，换台机器要重来一遍，忘了哪台改过就是事故。当时有两台环境（本机 + 服务器），再加一台就彻底说不清
- **它和 `docs/02-数据库设计.md` 是两份会各自过期的事实**：AGENTS 里那条"改表要同步改两处"，靠的是人记得
- 而且这套路径还会**静默写坏中文**：容器里 `mysql` 命令行客户端的默认 `character_set_client` 是 latin1（实测），直接执行 `.sql` 时文件里的 UTF-8 字节被逐字节当成 latin1 再转存，每个中文变成两个乱码字符。**它不报错、看起来像灌成功了**——我们是在部署上线当天才通过页面上的一片 `åŽŠå‹¤...` 发现它的

**备选方案**

1. **继续手工 ALTER，把步骤写进部署文档**：改动最小。但"记得做、记得在哪台做过"这件事本身就不可靠，而且多环境要各做一遍、无法核对
2. **`schema.sql` 继续做全量初始化，另建一个增量脚本目录**：两份事实并行，全量那份迟早忘了同步——新库建出来会缺列，而这正是要防的事
3. **引入 Flyway，让迁移脚本成为表结构的唯一执行真相**（后文详述）
4. **引入 Liquibase**：能力更强（支持回滚、跨数据库抽象、变更日志可用 XML/YAML 描述）。但功能大部分与"只用 MySQL 的单体应用"无关，配置面更大、要学一套新的 DSL

**决策**

选 **3**，并且把 `docs/schema.sql` 整个删掉（不做"全量 + 增量"两份），职责重新划分：

| 内容 | 落点 |
|---|---|
| 建表（14 张表） | `src/main/resources/db/migration/V1__baseline.sql` |
| 基础数据（租户/角色/权限点/楼栋/类别/报修码） | `R__seed.sql`（可重复迁移，改了自动重跑） |
| 设计说明与字段语义 | `docs/02-数据库设计.md`（保留，人读） |

关键配置就两条：`spring.flyway.baseline-on-migrate=true` 与 `baseline-version=1`。

**理由**

- **有版本、有记录、可核对**：`flyway_schema_history` 回答了"这台库跑到哪个版本了"，多环境对齐不再靠记忆
- **已有库能平滑接管**：`baseline-on-migrate` 在"库里有表但没有迁移历史"时把当前状态标记为基线，而不是报错或试图重建；空库则不受影响（非空才基线），老老实实从 V1 建起。**两条路径都实测过**
- **新增权限码只改一个文件**：`R__seed.sql` 是可重复迁移，校验和一变就重跑；内部幂等——平台定义的数据 upsert，租户自己的数据"存在即不动"，角色-权限授予则是"删掉重建，收敛到清单"
- **顺带根治了 latin1 那个坑**：迁移走 JDBC，字符集由连接串保证，不经过命令行客户端。实测空库跑完，`1号楼` 的字节是 `31E58FB7E6A5BC`（正确 UTF-8）
- **替换掉了一个文档同步点**：原来的"`schema.sql` + `docs/02`"变成"迁移脚本 + `docs/02`"——数量没变，但其中一份从"要人记得执行"变成了"机制保证会执行"

**负面后果**

- **应用启动现在依赖"数据库可用 + 迁移成功"**。这与项目其它地方的降级策略（Redis 挂了限流放行）**方向相反**，是有意为之：表结构不对时应用本来也无法正确工作，宁可不启动，也不要"跑起来了但用的是旧表结构"
- **失败的迁移会被记入历史并阻塞后续启动**：MySQL 下 DML 迁移失败不会自动回滚记录，必须手工清掉 `flyway_schema_history` 里 `success = 0` 的那行（`flyway repair` 的等价操作），否则每次启动都报"检测到失败的迁移"。恢复步骤已写进 `docs/05`
- **迁移脚本一经执行就不能再改**：改了校验和会被判定为不一致，只能新增脚本。这条约束必须在协作时说清楚，否则新人很容易直接改 V1
- **多了一个依赖**（`flyway-core` + `flyway-mysql`；后者必须单独引入，否则报 `Unsupported Database: MySQL`）
- **`baseline-on-migrate` 会掩盖结构差异**：如果某台库的实际结构与 V1 不一致，基线会把它当成"V1 已应用"直接跳过。所以给已有库首次接管前**必须做一次表结构核对**（方法见 `docs/05`）——这是本方案唯一的信任前提，不能省
- 首次接管的库上 `R__seed.sql` 会真的跑一遍（`DELETE` + 重建三个内置角色的授权）。语义是"收敛到清单"，所以结果幂等；但**它确实会覆盖手工调整过的内置角色授权**——若某台部署依赖这种手工调整，接管前先记下来

## ADR-011：学生账号用「统一初始口令 + 首登强制改密」，不做随机口令导出

- **状态**：已采纳
- **日期**：2026-09-22

**背景**

在这之前，学生账号只能靠插库或初始化脚本预置——学校要新增一个学生、或者一届新生入学，管理员在界面上没有任何入口。这不是"少一个便利功能"，而是**平台无法独立运行**：真实交付给一所学校时，账号必须能由校方自己维护。

于是要决定"初始口令怎么发"。约束有三条，都绕不开：

1. **项目明确不做短信 / 邮件通道**（`docs/01` 的"明确不做"），所以口令只能靠线下渠道分发
2. **学号是公开信息**——同一个班里所有人都知道彼此的学号
3. **一届新生是批量进来的**，一个个设口令不现实

**备选方案**

1. **初始口令 = 学号后 6 位**：最省事，学生自己就能算出来。但正因为如此，同学之间可以互相登录（学号公开 + 口令可推导），而且**在本人激活之前**这个窗口是敞开的
2. **系统随机口令 + 一次性导出清单**：每个账号一个随机口令，导出一张"学号 → 初始口令"的表交给学校分发。安全性最好，但要多做导出功能，而且那张清单本身成了需要安全传递的敏感文件（打印、传递、回收），学校侧的成本转嫁得并不轻
3. **统一初始口令 + 首次登录强制改密**：所有账号一个口令，学生首次登录必须改成自己的
4. **对接学校统一身份认证（CAS / 教务系统）**：真实场景里的正解——学生的身份本来就由学校自己的认证体系统管，平台不维护学生口令。
   **已完成（阶段 7，见 ADR-022）**：CAS 与 OAuth2 两种协议 + 演示用 Mock IdP，作为**登录的第二个入口**与账号密码并存

**决策**

选 **3**，并把 **4 记为将来的方向**（需要学校配合，不在本期）。

实现上只要两样东西：`sys_user` 加一列 `must_change_password`（迁移脚本 `V2__student_account.sql`），外加一个拦截器。未改密的账号只放行 `/api/auth/**`（改密 / 登出 / 看当前用户），其它接口一律回 `10003` + "请先修改初始口令"。

**理由**

- **它把风险窗口收敛到"首登之前"**：方案 1 的风险在整个账号生命周期里都存在（口令一直可推导），方案 3 只在学生激活前存在，而那正是学校自己的发放流程能覆盖的时段
- **学校侧零额外成本**：不用印发口令清单，口令就写在"发给班级的那张通知"上
- **前端的跳转不算数，所以服务端也拦了一道**：只做前端跳转的话，绕过它照样能调接口——"强制"就名不副实了
- **标记只占一列 + 一次 Session 读写**：登录时写进 Sa-Token Session（那里本来就存租户），拦截器每请求读 Session 而不查库；改密成功后该账号所有会话被注销，标记随之消失，不需要单独清理

**负面后果**

- **在本人激活之前，知道学号的人可以抢先登录并改掉口令**——把真正的学生锁在外面，得找后勤重置。这是"统一口令"的固有风险，技术手段消除不了，只能靠"后勤尽快发放、学生尽快激活"压缩窗口。**这一点必须让部署方知道**，不能只说"有强制改密就没问题了"
- **冻结式体验**：未改密的账号除了改密什么也做不了（有意的）。如果学生一直不改，他会一直看到"请先修改初始口令"，客服成本落在后勤身上
- **批量导入单次 500 条**：两万名学生要分 40 次导入。这是有意给事务大小设的上限，不是能力不足
- 方案 2（随机口令）被搁置了，但它**不需要再改表**——真要换成它，只是"生成口令"和"导出清单"两处的事，`must_change_password` 与强制改密的拦截都不用动

## ADR-012：平台运营身份用「租户 0 + user_type=4」，域收口靠拦截器而不是逐接口加权限码

- **日期**：2026-09-22
- **状态**：已采纳（**已实现**）

**背景**

`docs/06` 里曾经明确写着"没有独立的平台运营后台，新增租户靠脚本或直接写库"。这在单所学校时成立，但一旦要接第二所学校，它就是个硬缺口：**开通一所学校需要同时建租户和它的第一个管理员账号**，而这两件事都没有入口。`docs/00` 的缺口表把"租户入驻 + 后勤管理员自身找回密码"列成"接第二所学校前必须补"。

同时还有第二个问题：后勤管理员忘记口令时没有任何出路。项目明确不做短信 / 邮件（docs/01 §4），没有自助找回的通道，所以只能由平台侧核验身份后代为重置——**而这需要一个平台侧的身份**。

**备选方案**

1. **另开一套平台登录入口 + 独立的平台账号体系**：`POST /api/platform/auth/login`，只收账号密码
2. **平台 = 租户 0，复用现有登录**：`tenant` 表加 `id = 0` 一行（`code = platform`），平台账号就是 `sys_user` 里 `tenant_id = 0` 的记录
3. **不做界面，开通学校仍靠脚本**（保持 `docs/06` 的原状）

**决策**

选 **2**。

**理由**

- **"0 = 平台"不是新发明的约定，是把它补齐**：`sys_role.tenant_id = 0` 早就被定义为"平台内置角色"（docs/02 §3.2），`sys_permission` 本来就是全局的。租户 0 只是同一句话的另一半
- **登录契约一个字不改**：认证、按「租户 + 账号」限流（key 自然变成 `rate:login:0:<账号>`）、会话绑定、首登强制改密、`LoginVO` 全部复用。方案 1 要把这套东西再写一遍，而且多出一个匿名的登录端点
- **平台账号天然看不到租户数据**：数据权限拦截器会给它的查询注入 `tenant_id = 0`，而租户 0 没有任何工单——不需要在拦截器里加"平台豁免"这种分支（豁免分支正是最容易写漏的地方）
- **域收口放在拦截器里，而不是"给平台角色只授一个权限码"**：这是本次最要紧的一条。权限码是"有注解才生效"的白名单机制，而项目里有三个接口**没有任何权限码**（`GET /api/categories`、`POST /api/files/upload`、`GET /api/tickets/by-code/{code}`，三个端都要用，一直只要求"登录"）。只授一个码挡不住它们——平台账号能真的调通、能在对象存储里以租户 0 的前缀写文件。所以换成正向陈述：**平台账号被关在 `/api/platform/**` 里**（`PlatformScopeInterceptor`，order 3）。它不依赖任何接口记得加注解，以后新增的租户接口自动被挡住
- **不做自助找回是刻意的**：短信 / 邮件被明确排除（跨端前提 + 零成本），安全问题那种"找回"在校园场景里等于没有（同学之间互相知道生日）。平台侧重置 + 重置后强制改密，是唯一诚实且能落地的答案

**负面后果**

- **`tenant` 表里多了一行不是学校的记录**：所有"列出全部租户"的地方都必须显式排除 `id = 0`。当前只有平台端的列表一处（已排除），但这个约束是隐式的——新增任何"查租户"的代码都要记得它
- **平台账号的可见范围很窄（有意为之）**：它连"某学校本月报修多少单"都看不到。运营视角上这是缺的，将来要做就得新开聚合接口并重新论证隐私边界
- **停用学校要遍历该租户的账号逐个踢下线**（一次查询 + N 次 Redis 往返）。本项目这个规模没问题，用户上万时应改成"请求时校验租户状态"。这个边界写进了 docs/03 §5.5，免得将来被当成 bug
- **平台账号没有创建接口**：只能由环境变量引导（`REPAIR_PLATFORM_BOOTSTRAP_*`）。好处是没有接口能造出平台账号；代价是忘记它的口令时要"删掉账号 + 重启"，多了一步手工 SQL（docs/05 §4.3）
- ~~**`TicketDataScopeHandler` 对未知角色落到"学生口径"而不是拒绝**~~ **已于 2026-10-14 修复**：改为返回恒假条件（`1 = 0`）——未知角色与"一个角色都没有"的账号**一条工单也看不到**。选"拒绝"而不是"猜一个最像的角色"，是因为**出错的方向比出错本身更重要**：漏配一个角色的可见范围时，恒假立刻表现成"我的列表空了"（基层会报上来），学生口径则会安静地给出一批越权可见的单、而且条件看着还挺克制（`student_id = 我`），在评审里看不出来。用条件而不是抛异常同样是刻意的：对调用方来说"这个人确实没有单"和"这个人被拒绝"表现一致，不把一次数据配置疏忽升级成 500。测试见 `TicketDataScopeHandlerTest#unknownRoleSeesNothing`；连带把多角色账号的优先级（ADMIN → WORKER → STUDENT → 拒绝）也用测试钉住了

## ADR-013：流式问数只流「阶段」，用 fetch 而不是 EventSource

- **状态**：已采纳（已实现：`GET /api/ai/query/stream`，契约见 `docs/03` §5.6）
- **日期**：2026-09-26

**背景**
一次问数要等两次模型调用（出 SQL、出结论），十几秒里页面上什么都没有。要把中间结果提前给用户，
就得选传输方式与"流什么"这两件事。

**备选方案**

1. **不流式**：只保留 `POST /api/ai/query`，前端一直转圈到出结果
2. **`EventSource` + 逐字流式**：浏览器原生 SSE 客户端，模型 token 一到就推一个字
3. **`fetch` 读流 + 阶段流式**：SSE 只推"SQL 已定""数据已到""结论已出"三帧

**决定**
选 **3**。

**理由**

- 方案 2 的死穴是 `EventSource` **不能带 `Authorization` 头**，token 只能拼进 URL——而 URL 会进
  nginx 访问日志、浏览器历史与 Referer。为了一个便利丢掉凭据卫生，不划算
- **逐字流式在这个场景收益极低**：结论只有一两句话（几十个字），为它引入 `StreamingChatModel`
  等于多一条模型调用路径（另一套提示词入口、另一套异常翻译、另一套假实现），换来的只是"字一个一个出现"
- 用户真正难熬的是**前十几秒的空白**：一次问数里"生成 SQL"占小头、"等结论"占大头。
  把 SQL 与数据两帧提前推出去，用户就能先看到"它打算怎么查"和表格 / 图
- 还有一条工程上的理由：ADR-003 的四层闸门是**拿到完整 SQL 之后**才生效的。
  逐字吐出未校验的 SQL，等于把没过闸门的东西摆到用户面前

**负面后果**

- **`fetch` 读流要自己解析 SSE 帧**（`api/ai.ts` 里几十行）：`event:` / `data:` 分帧、`\r?\n` 兼容、
  认不出的事件名要跳过（旧前端不能被新事件打翻）。比 `EventSource` 多了一份要维护的代码
- **`GET` 的问题文本会进 access log**：换 POST 可以避免，但 GET 更贴"一次读取"的语义，
  且入参能复用同一个 DTO（校验规则只有一份）。这个取舍写进了 `docs/03` §5.6
- **错误有两条通道**：工作开始前是 JSON、开始后是 `error` 帧。分界写清楚了，但前端要按它分两支
  （统一收敛在 `handleError`，用户看到的提示只有一种）
- **不逐字流式的体验上限就在那里**：结论仍然是"整句蹦出来"。将来真要做逐字，改动落在
  `LangChainAiAssistant` 与 `AiQueryProgress` 上，前端不用动（帧格式不变）

## ADR-014：Excel 导出用 EasyExcel（并接受它已停止更新的代价）

- **状态**：已采纳（已实现：`GET /api/admin/statistics/export`，契约见 `docs/03` §5.4.1）
- **日期**：2026-09-28

**背景**
统计看板的数字要能落进 Excel 带走（月底汇总、存档上交）。项目此前没有任何 Excel 相关依赖，
而且 `docs/01` 里还有一条方向相反的理由：学生名单批量导入**刻意**选了"粘贴文本"而不是 Excel 上传，
就是为了不引 POI。所以这次得说清"为什么这里引得起"。

**备选方案**

1. **零依赖 CSV**：`text/csv` + UTF-8 BOM，代码量最小
2. **Apache POI 直写**（`poi-ooxml` 的 `SXSSFWorkbook`）：自己抓行和单元格
3. **EasyExcel**（`com.alibaba:easyexcel`）：POI 之上的一层"对象列表 → 工作表"封装

**决定**
选 **3**。

**理由**

- 方案 1 省掉了依赖，但**交付物不对**：学校拿到的是"一个需要先用 Excel 打开再另存为的文本文件"——
  中文要靠 BOM 才不乱码、数字会被当文本、多工作表无从谈起。导出是给别人看的交付物，不是内部中间格式
- 方案 2 只差一层封装：`SXSSFWorkbook` + 逐行 `createRow`，四张表就是四段同构的"列序 + 取值"代码。
  而且**省不下体积**——POI 本身就是这 21MB 里的大头（12.5MB），EasyExcel 自己的 core 只有 550KB
- 方案 3 的写法是"字段加 `@ExcelProperty`，把对象列表交给它"，多一张表就是多调一次 `write`
- 顺带还有一条非技术理由：它是国内做 Java 报表最容易查到文档的选择，
  **一个只用得上 5% 功能的库，也应该是那个"接手的人一眼认得"的库**

**负面后果**

- **`com.alibaba:easyexcel` 是已停止更新的坐标**：最后一个版本 4.0.3（2024-08），此后作者把项目
  更名为 FastExcel（`cn.idev.excel:fastexcel`）继续维护。这个决定等于**接受它不会再收到安全修复**；
  真出现 CVE 时按上述坐标迁移——API 基本一致，是**几十行的改动，不是重写**
- **多进来 21 个 jar、约 21MB**（poi + poi-ooxml + poi-ooxml-lite + xmlbeans + ehcache +
  commons-csv + jaxb…），而本项目导出的只有几百行。这个体积是为"将来可能有的明细导出"提前付的；
  写在这里是因为它在 `mvn dependency:tree` 里一眼可见，不写下来就会变成"谁也不知道为什么这么大"
- **有两个版本不是 EasyExcel 自己测过的**：它声明 `ehcache 3.9.11`、`slf4j 1.7.36`，
  而 Spring Boot 的依赖管理把两者抬到 `3.10.9` / `2.0.18`。当前用例（多 sheet、自动列宽、读回）正常；
  将来升级 Spring Boot 后若它出怪问题，第一个该看的就是这里
- POI 走的是 `log4j-api` 而不是 slf4j。之所以没在日志里多出一套配置，是因为
  `spring-boot-starter-logging` 已经带了 `log4j-to-slf4j`，POI 的日志会被转发进 Logback——
  这是**依赖它**而不是配置出来的结果，换日志实现时要重看一眼

**没变的决定**：学生名单导入**仍然是粘贴文本**。两个场景的取舍可以相反，因为"Excel"在两个方向上的含义不同：
那里是**输入**格式——列顺序、合并单元格、编码全是不确定项，为了读懂别人的文件要写一堆兼容逻辑；
这里是**输出**格式——格式完全由我们决定，读的人是人不是程序。**同一个词，两个方向，结论可以不同。**

- 接口从 1 个变 4 个，Controller 各自注入需要的域。`TimeoutHandler` 的测试
  从注入 `TicketService` 改为注入 Handler——超时回调没有 HTTP 端点，是六步里
  唯一需要改测试的一步
- 跨域的顺序编排（如派单后登记超时节点）现在是 Assignment 域调用
  `TimeoutService`，比原来同类私有方法互调多一层依赖——值得，这层依赖在
  docs/06 的时序图上可见
- 分六个 PR 意味着中间态必须能编译：共享口径必须先行抽取，否则每个域都得
  复制一份

**为什么是这个顺序**

先抽 `TicketTransitionSupport`（#86/#88）再拆域（#89/#90/#91/#92）是这次唯一
重要的执行决策——蓝图归蓝图，没有共享容器的先行抽取，拆分只会把一处口径
复制成四份。

## ADR-016：Redis 淘汰策略用 volatile-lru，且共享一个库、靠前缀而非 DB 号区分用途

- **状态**：已采纳（已实现）
- **日期**：2026-10-14

**背景**

M5 之前这台 Redis 上已经住着五类键，却一直没有回答"内存写满时谁应该先被淘汰"：

| 键 | TTL | 丢了会怎样 |
|---|---|---|
| `ticket:timeout:ACCEPT` / `ticket:timeout:EVAL`（ZSet） | **无** | 那些工单**再也不会**被超时提醒 / 自动关闭，且全程没有任何报错 |
| `ticket:no:seq:{date}`（工单号序号） | 2 天 | 序号重来，`uk_ticket_no` 挡下重复，表现为建单偶发失败 |
| `rate:*`（限流计数） | 窗口秒数 | 限流窗口提前结束，可被继续消耗 |
| `audit:login:*`（登录去重） | 到当天结束 | 同一天多记一条登录事件（`AuditServiceImpl` 已按"照记"处理） |
| Sa-Token 会话 | 由 Sa-Token 管 | 用户需要重新登录 |

当时的配置是 `--maxmemory-policy allkeys-lru`——**它对这些键一视同仁**。而上面这张表里
只有一行是"丢了不可恢复"的：超时队列。`allkeys-lru` 会在内存吃紧时把一个只写过一次、
之后长期不动的 ZSet 当成"最久未使用"淘汰掉，正好是最不该动的那个。

真正让这件事变成"必须现在做"的是下一阶段的字典/权限缓存：加缓存等于主动往这个已经
接近上限的库里塞更多可淘汰数据，**它会把淘汰从"理论上可能"推到"实际上会发生"**。

**备选方案**

1. 保持 `allkeys-lru`，靠"内存够用"这个前提——但那个前提正是加缓存要打破的
2. 换 `volatile-lru`：**只淘汰设了 TTL 的键**，无 TTL 的键永不被淘汰
3. 换 `noeviction`：内存满时写入直接报错——缓存写失败会连累业务写路径，最差
4. 给缓存单开一个 Redis 容器（或换个 DB 号）

**决策**

选 **2**，并且**继续共用一个库（DB 0），靠键前缀区分用途**（缓存键统一 `cache:` 前缀）。

**理由**

- **`volatile-lru` 恰好精确命中要害**：全项目只有超时队列两类键没有 TTL，
  于是"无 TTL 的不淘汰"这条规则等价于"只保护超时队列"。一行配置换掉一个静默的数据丢失，
  这是本次性价比最高的改动
- **被淘汰的那些键都是可恢复的**：会话过期要重新登录，限流计数提前归零只是少挡一会儿，
  工单号冲突有唯一索引兜底。**降级方向是"麻烦"，不是"数据没了"**——这才是可以接受的取舍
- **不做成环境变量**：它是个安全开关。留一个 `${REDIS_MAXMEMORY_POLICY:-...}` 就等于留了
  一个能被误改成 `allkeys-lru` 的口子，而这个错误的表现是"半年后某批工单悄悄没超时"，
  没人查得出来。写死在 `docker-compose.yml` 里，改动必须过代码评审
- **不上独立 DB 号**：`maxmemory` 与 `maxmemory-policy` 都是**实例级**的，DB 号既不隔离内存、
  也不隔离淘汰——它换来的只有 `FLUSHDB` 的方便和 `DBSIZE` 的干净，代价却是多一套
  `RedisConnectionFactory` / `RedisTemplate` Bean，以及**堵死将来上 Redis Cluster 的路**
  （Cluster 只有 DB 0）。观测需求用 `SCAN MATCH cache:*` 就能满足，比多一个 Bean 便宜

**验证方式**

不是"相信文档"：起一个一次性 Redis（`--maxmemory 4mb`），先写一个 600KB 的无 TTL 键，
再写 8MB 带 TTL 的键把内存压满。`volatile-lru` 下无 TTL 键 **EXISTS = 1**（存活，淘汰的
60+ 个键全是有 TTL 的）；换成 `allkeys-lru` 重跑同一个脚本，同一个键 **EXISTS = 0**（被淘汰）。
验证脚本与结论记在 PR 里，不是一遍性的手工观察。

**负面后果**

- **会话变成了可淘汰的**：内存真满时活跃用户可能被登出。接受这个降级的前提是
  "内存真满"本身不该发生——`REDIS_MAXMEMORY` 是 256mb，而当前用量是它的零头，所以这是
  一道**兜底防线**而不是日常路径。真出现就得扩容，不该靠调策略绕开
- **新增无 TTL 的键会绕开这道防线**：以后往 Redis 写任何东西，如果忘了设 TTL，它就成了
  "永不被淘汰"的——既占着内存不走，又享受着保护。**约定：除超时队列外，所有键必须带 TTL**；
  这条要在每次新增 Redis 用途时对照一遍
- **`volatile-lru` 的语义依赖"有 TTL 的键足够多"**：如果一个库里所有键都没有 TTL，
  它在内存满时表现得和 `noeviction` 一样（写入报错）。本项目不会——会话键始终在，
  但如果将来把会话挪走（比如换成本地内存会话），这条前提就要重新检查

## ADR-017：AI Agent 用「手写编排循环 + 工具白名单」，且 Agent 不写库

- **状态**：已采纳（已实现）
- **日期**：2026-10-16

**背景**

M4 的 AI 能力是**单轮**的：一句话进 → 生成 SQL → 执行 → 总结（ADR-003 / ADR-013）。
下一阶段要做的是"从查数工具到 AI 系统"：报修受理与智能分诊需要**多轮对话 + 调用工具**
（问用户缺什么、去查本租户的楼栋与类别），而不是一次问答。

三件事必须先定下来，否则实现会各走各的：编排怎么做、Agent 能不能写库、失败与成本怎么控。

**决策一：编排循环手写，不引入 `AiServices`**

LangChain4j 的声明式 `AiServices`（`@Tool` + 代理接口）能把工具调用写得很好看，但它在
`dev.langchain4j:langchain4j` 主包里，**项目只引了 `langchain4j-open-ai`**（core + open-ai 传输层）。
更重要的是：用 `AiServices` 会把**步数上限、工具白名单、人工确认点、轨迹记录**这四件事
交给框架的黑盒——而这四件恰恰是本项目要能讲清楚的部分。

所以：用 core 里已有的 `ToolSpecification` / `ToolExecutionRequest` / `ChatRequest` **手写循环**。
这不是"重复造轮子"——循环本身只有几十行，而它换来了四件能自己控制的事。

> 旁证：core 1.20.0 里这些类都在（`unzip -l` 亲自确认过），所以**零新增依赖**。
> 而 ADR-005 定的调子就是"只引稳定核心"，这条决策与它一致。

**决策二：Agent 不写库，只产出「草稿 / 建议」**

受理 Agent 只输出**工单草稿**（类别、紧急度、位置、描述、建议标题），落单仍然由前端调
**现有的** `POST /api/student/tickets`；分诊只输出**建议值**，由调用方决定是否采用。

理由：

- **权限与审计零新增面**：落单走的是早已验过数据权限、租户校验、审计、限流的那条链。
  Agent 若自己写库，就要把上面每一条再实现一遍，而且是在"模型可能胡来"的前提下
- **模型的不确定性被隔离在"建议"层**：它说错了，用户改一下就行；它说对了，用户省一步。
  这条边界让"AI 出错"从事故降级成不便
- 与 ADR-003 一脉相承：那次是"AI 生成的 SQL 必须过安全网关"，这次是"AI 的结论必须经人确认"

**决策三：工具白名单，且**不**把报修码查询交给模型**

首版只暴露两个**只读**工具：本租户的启用中楼栋、本租户的启用中类别。

**明确不暴露 `GET /api/tickets/by-code/{code}`**：那是防枚举面（6 位码可猜，所以有 `@RateLimit`，ADR-009）。
把它交给模型，等于让"猜码"这件事绕过了限流那一层——模型可能为了确认位置连打几十次。
位置信息的正确来源是：用户在界面上扫码/手输 → 由现有接口解析出 `buildingId` → 作为**入参**交给 Agent。

> 判断标准：**凡是"能被暴力枚举"或"会产生写副作用"的能力，都不进工具白名单。**
> 工具是给模型用的手，不是给模型用的权限。

**实现要点**

- 循环依赖一个项目自己的接口（`AgentModel`：给它消息与工具清单，它回"要调工具"或"给答案"），
  **不把 langchain4j 的类型泄漏进编排层**。于是测试可以塞一个脚本化的假实现，整条循环不花钱就能测
  （与 `AiAssistant` 可替换成假实现是同一个思路）
- **步数上限**（默认 6）与**工具白名单**都在循环里强制；未知工具直接拒绝，不交给模型重试
- **多轮会话存 Redis**，键 `agent:intake:{tenantId}:{userId}`，**带 TTL**（30 分钟）——
  遵守 ADR-016 的"除超时队列外所有键必须带 TTL"；历史长度也在这里截断（成本控制）
- **轨迹**（每一步调了哪个工具、耗时、结果摘要）随响应返回并落日志；
  **用户原始输入不落日志**（AGENTS §5.8），只记步数与工具名
- 复用现有 AI 错误码（40004 模型不可用等），**不新造**；"信息还没问全"不是错误，是一轮正常的追问

**负面后果**

- 手写循环意味着以后要用 LangChain4j 的新特性（记忆压缩、结构化输出、多 Agent 协作）时得自己接，
  而 `AiServices` 生态里这些是现成的。这个代价接受，因为本项目要的是"能讲清楚"而不是"接得快"
- 两个只读工具的能力很有限：首版的分诊质量取决于提示词与类别表，不取决于工具。
  后续若要让 Agent 查"这栋楼历史上这类问题的平均处理时长"，要新增工具并重新论证白名单边界
- 会话存 Redis 意味着**重启 Redis 会丢会话**（2026-10-16 换镜像时实测过数据集会被重置），
  表现是"对话要重新开始"——可接受，不是数据丢失

## ADR-018：维修知识库用「关键词检索 + 服务端核对引用」，向量检索留接口不落地

- **状态**：已采纳（表与权限点已落：`V8__knowledge_entry.sql` / `R__seed.sql`；服务与前端随后）
- **日期**：2026-10-17

**背景**

阶段 2 要做的是"师傅在工单详情里要一份排查建议"。原料是知识库条目（现象 → 处理步骤），
链路上有三个决定要定：**怎么检索**、**生成怎么调模型**、**凭什么相信模型没瞎编**。

约束都是既成事实，不是偏好：

- 项目唯一的模型 provider 是 DeepSeek，**它只有 chat/completions，没有 embedding 接口**
- Redis 用的是官方 `redis:7-alpine`（**没有 RediSearch / 向量索引**），而 ADR-016 已经把键空间约定写死
- 部署机是 2C2G 的轻量服务器
- ADR-005 里写着"后续要做 Schema 检索，LangChain4j 的 RAG 组件更成熟"，`docker-compose.yml` 里还留着
  一句"embedding 方案已放弃"——**那条从来没有正式决策过**，这一条把它补上

**备选方案**

1. **关键词检索**：MySQL 8 自带的 `FULLTEXT ... WITH PARSER ngram`（中文 2-gram，不需要外部分词器）
2. **向量检索**：embedding + 向量库（LangChain4j 的 `EmbeddingStore` 那一套）
3. **全量塞提示词**：条目少，干脆把整本知识库放进系统提示词

**决定**

1. 检索走**关键词**：`MATCH(title, symptom, tags) AGAINST (? IN NATURAL LANGUAGE MODE)`，**类别优先**
   （工单有类别就先看该类别与通用条目），取前 5 条；
2. 检索抽成接口 `KnowledgeRetriever`，关键词是默认实现；**向量实现留位不留代码**；
3. 生成**只调一次模型**（不套 Agent 循环），要求它输出带引用的结构化 JSON，而
   **服务端核对每条引用是否来自本次检索结果**，引不到的直接丢；
4. 检索零命中就**如实说没有**，而且**不调模型**——没有原料就不生成，省一次钱。

**理由**

| 维度 | 关键词（选定） | 向量（留接口） | 全量塞（否） |
|---|---|---|---|
| 新增依赖 | **0**：MySQL 自带 ngram | embedding 服务 + 向量存储，两样都要新依赖 | 0 |
| 成本 | 0（检索不花钱） | 每次入库与查询都要调 embedding | 0，但每轮提示词都带整本库 |
| 可解释 | 命中哪些词、分数多少，能直接给用户看 | 相似度不透明 | —— |
| 数据量适配 | 一所学校几十条，够用 | 上万条才见优势 | 条目一多就撑爆上下文 |
| 中文效果 | 实测可用（见下） | 同义改写更好 | —— |

**实测证据**（2026-10-17，本地 MySQL 8，`ngram_token_size = 2`，4 条样本条目）：

- 「我们宿舍的门锁好像坏了，钥匙插进去转不动」→ 只命中「门锁卡住」，score 3.62
- 「宿舍门锁转不动」→ score 2.54
- 无关查询「电梯坏了」→ **零命中**（正是要的行为：没答案就说没答案）

> 这是设计阶段先做的一次小实验：先证明 ngram 对中文口语的召回够用、且不会误召回，才敢把它当默认方案。
> 实验用的是临时库，跑完就删了（不是"我觉得 ngram 应该能行"）。

**向量实现的前置条件**（将来要做，先补一条 ADR，别直接改代码）

1. 一个 embedding 服务：自建（本地模型在 2C2G 上不现实）或第三方（新依赖 + 新账单）
2. 向量存储：换 `redis-stack`（会推翻 ADR-016 的既有约定，要重新论证）或引入 pgvector 之类
3. 条目的**增量更新**：新增 / 修改时同步向量，以及历史条目的首次灌库

**配套（实现按这个来）**

- 表 `knowledge_entry`（V8）：带 `tenant_id`，**不在拦截器覆盖名单里**，所以所有查询显式写租户条件；
  一律用 `status` 停用而不是删除——条目会被历史建议引用
- 权限码 `knowledge:manage` 管管理端维护；师傅端的建议接口沿用 `ticket:list:assigned`
  （能看这张单才能要建议，与分诊用 `ticket:dispatch` 是同一个口径），限流档位 `ai`
- **接口不写库**：建议只是建议，怎么做仍是人的判断
- `tags` 是**给同义词留的旋钮**："渗水" 命中不了 "漏水" 是关键词方案最大的弱点，管理端表单要写清
- 知识库内容会进提示词 → 这是新的注入面。缓解：条目只出现在"参考资料"段落、长度截断、
  **而且这条链上没有任何工具**（模型无法借知识库内容触发任何动作）

**负面后果**

- **同义词 / 口语改写的召回弱**：靠 `tags` 人工补，规模上千条后要重估（那时向量才划算）
- 一次生成意味着**没有多轮追问**（"再查查别的可能"要用户自己改描述重问）；真需要时把检索包成工具
  交给 ADR-017 的循环即可——接口已经在那儿了
- 知识库质量直接决定建议质量，而**这是产品问题不是技术问题**：所以管理端页面要做得让人愿意填

**取舍说明**：这一条的核心不是"关键词比向量好"，而是**在当前约束下（没有 embedding 服务、
不能用带向量的 Redis、数据量小），关键词是唯一零依赖且可解释的选项**；而真正决定这套东西能不能被信任的
是第 3 条——引用核对。没有它，RAG 就退化成"模型自由发挥 + 我们假装它读过资料"。
